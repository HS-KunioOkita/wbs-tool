# 後続設計プラン

要件定義の結果に基づき、以降の設計工程の実施可否を以下のように判定する。各工程は必要最低限の粒度で実施する。

## 規模感サマリ

- ユースケース数: 9
- エンティティ数: 3
- 外部システム連携: なし
- 想定アクター数: 1（利用者）
- 主要な非機能制約:
  - ローカル PC 上で動作する Web アプリケーション
  - データストアは SQLite
  - 対応環境は Chrome × macOS × 1280×720 以上

## 設計工程の要否

| ------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |

## スキップ判断の根拠

### コンポーネント設計をスキップした理由

- 単一プロセスのモノリス構成を想定しており、コンポーネント間の物理境界・通信プロトコル・配置差異が存在しないため。
- アーキテクチャ設計のレイヤ分割（プレゼンテーション / ドメイン / データアクセス）でモジュール責務を整理できれば、追加の分解は過剰と判断する。
- 将来的にデスクトップアプリ化（Tauri 等）やネットワーク越し利用へ拡張する場合は、その時点で改めてコンポーネント設計を起こす。

### インフラ設計をスキップした理由

- 動作環境がローカル PC に限定されており、サーバ冗長化、ネットワーク設計、監視・ログ基盤、バックアップ運用などの設計対象が存在しないため。
- SQLite ファイルの配置場所・バックアップは利用者が OS の機能で管理する前提で合意済み（非機能要件にてバックアップ要件はスキップ）。
- 配置構成（ローカル PC・SQLite）は NFR-004 に明記済みであり、これ以上の設計は不要。

## 申し送り事項

要件定義段階では決められないが、設計以降で確定すべき論点を列挙する。

1. **Web アプリの起動方式 / プロセス構成**
   - 決定すべき内容: フロントエンドとバックエンドを単一サーバプロセスで提供するか、フロントエンドを静的ファイルとして配信しバックエンドを別プロセスにするか。あるいは Tauri / Electron のような組込みランタイムを使うか。
   - 想定選択肢: (a) Node.js + Express 等の単一サーバ起動、(b) 静的フロント + ローカル API サーバ、(c) Tauri / Electron による配布。
   - 決定責任者: アーキテクチャ設計担当

2. **PDF 出力方式**
   - 決定すべき内容: ブラウザ側で生成する（jsPDF / pdfmake / html2canvas + 印刷 API 等）か、バックエンド側で生成する（Puppeteer / wkhtmltopdf 等）か。
   - 想定選択肢: (a) クライアント生成（オフライン完結、フォント等の制約あり）、(b) サーバ生成（高品質だが依存が増える）。
   - 決定責任者: アーキテクチャ設計担当 / UI 設計担当

3. **ガントチャート描画方式**
   - 決定すべき内容: 既存ライブラリ（dhtmlx-gantt / frappe-gantt / Gantt-Schedule-Timeline-Calendar 等）を採用するか、自前で SVG / Canvas に描画するか。
   - 想定選択肢: (a) ライブラリ採用（実装が短縮できるが、ドラッグ&ドロップや依存線表示の挙動がライブラリの仕様に縛られる）、(b) 自前実装（自由度が高いが工数増）。
   - 決定責任者: アーキテクチャ設計担当 / フロントエンド実装担当

4. **親タスク期間の自動算出のトリガと粒度**
   - 決定すべき内容: 子タスク更新時に親タスクの期間を即時再算出するか、表示時に都度算出するか（永続化の有無）。
   - 想定選択肢: (a) 永続化（DB に再算出後の値を保持）、(b) 都度算出（DB には子タスクのみ持ち、親は導出値）。
   - 決定責任者: クラス設計担当 / データ設計担当

5. **進捗の親への集約有無**
   - 決定すべき内容: 親タスクの進捗を子タスクの進捗から自動算出するか、親タスク独自の値として保持するか。本要件定義書では親タスクの進捗の挙動を明示していないため、設計工程で意思決定が必要。
   - 想定選択肢: (a) 子の進捗の重み付き平均（期間の長さで重み付け等）で自動算出、(b) 親タスク独自に進捗を保持できる、(c) 親タスクは進捗値を持たない。
   - 決定責任者: クラス設計担当 / HCD 設計担当

6. **循環参照（親子 / 依存関係）の検出アルゴリズム**
   - 決定すべき内容: タスク数が増えたときの検出方法（毎回 DFS で判定、隣接行列を保持、推移閉包を維持、等）。
   - 想定選択肢: (a) 都度 DFS（実装は単純、500 タスクなら性能十分）、(b) 永続化された推移閉包テーブル（更新コスト増、参照コスト減）。
   - 決定責任者: クラス設計担当 / データ設計担当

7. **「期限超過」の判定基準日**
   - 決定すべき内容: 「今日」をどう取得するか（PC のローカル時刻、UTC ベース、利用者が任意の基準日を設定可能か）。
   - 想定選択肢: (a) PC のローカル時刻固定、(b) 利用者が基準日を画面上で変更可能（リハーサル目的）。
   - 決定責任者: HCD 設計担当 / 機能設計担当

8. **SQLite ファイルの配置場所と複数プロジェクトの保存単位**
   - 決定すべき内容: 全プロジェクトを 1 つの SQLite ファイルに格納するか、プロジェクト 1 つにつき 1 ファイルとするか。配置先のデフォルトパス。
   - 想定選択肢: (a) 単一 DB ファイル、(b) プロジェクト単位の DB ファイル（利用者がフォルダで管理しやすい）。
   - 決定責任者: アーキテクチャ設計担当 / データ設計担当
