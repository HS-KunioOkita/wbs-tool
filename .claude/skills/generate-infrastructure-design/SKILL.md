# インフラ設計の作成
要件定義書およびアーキテクチャ設計書から、基本設計の仕上げとなるインフラ設計書を作成してください。

## Goal
可用性・性能・セキュリティ・運用性という非機能要件を、過不足の少ない実行基盤構成として定義する。

「過不足が少ない」とは、要件とアーキテクチャで想定された構成要素が実環境で動き続けるために必要な基盤要素は漏らさず、一方で現時点の要件では正当化できない要素（想像上のピーク向けの先取り冗長化・使い所のない高級マネージドサービス・過剰な多層防御・将来のマルチリージョン妄想など）は含めない、という意味である。判断に迷ったら、対応する要件 ID（特に NFR-NNN）または構成要素 ID（COMP-NNN）に紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて代替案セクションで記録する。

## 位置付け（要件定義・アーキテクチャ設計・詳細設計との関係）
本スキルは `/generate-requirements` と `/generate-architecture-design` の成果物を主な入力とし、実装・運用着手の出発点となる**物理構成レベル**の合意を作る。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 特に非機能要件 `NFR-NNN`（可用性・時間効率性・セキュリティ・運用・制約）を基盤構成で実現する責任を負う。目標値（稼働率・RTO / RPO・性能指標など）はここでインフラ側の実現方式（HA / DR・冗長化・スケール戦略）に翻訳する。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - 構成要素一覧（`COMP-NNN`）と主要な通信・連携（`LNK-NNN`）、および「インフラ設計への申し送り（`HO-I-*`）」を出発点とする。`COMP-NNN` を実環境のノード／マネージドサービスへ配置し、`LNK-NNN` を実経路（ネットワーク・プロトコル・セキュリティ境界）へ具体化する。
- 下流（詳細設計）: `docs/design/` 配下の機能単位・画面単位の詳細設計。本ドキュメントは詳細設計に対して「どのインフラ前提（接続先エンドポイント・認証方式・監視 SLA・デプロイ手順）に依存してよいか」を示す。
- 下流（運用・SRE）: 詳細な Runbook、手順書、IaC コード、具体のアラート閾値、オンコール体制。これらは本ドキュメントの上に積み上げて作られる。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**実環境に落とし込むレベル**の話であり、アプリケーション内部のロジックには踏み込まない。

- システム全体の稼働環境（クラウド / オンプレ / ハイブリッド）と主要利用サービス
- 物理配置（リージョン / アベイラビリティゾーン / データセンタ / ネットワークゾーン）
- アーキテクチャ `COMP-NNN` とインフラノード／サービスの対応付け
- ネットワーク構成（VPC / サブネット / セキュリティグループ / ファイアウォール / ロードバランサ / 踏み台 / VPN / 専用線・境界の切り分け）
- 可用性設計（冗長化方式・フェイルオーバー機構・障害ドメイン分離）
- スケーリング設計（スケールアウト・スケールアップ・自動／手動の判断基準・発動条件）
- セキュリティ設計（認証・認可の基盤側責務、通信経路の暗号化、鍵・証明書管理、データ保護、監査ログの収集点）
- 運用設計（監視・ログ集約・アラート・オンコール連携点）
- バックアップ / リカバリ（RPO / RTO の担保方式、取得方式、保管先、復旧手順の概要）
- デプロイ戦略（CI/CD パイプライン、リリース方式、環境分離、ロールバック方針）

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、紛れ込むと議論が停滞するため、該当工程への申し送り事項に退避させる。

**アーキテクチャ設計で決めるべきこと（上流へ差し戻し）**
- コンポーネントの責務境界・同期／非同期の区切り・認証認可の責務位置など、論理構成そのものに関する判断。インフラ側では論理構成を所与として扱い、物理配置で実現する。

**詳細設計（機能 / 画面単位）で決める**
- アプリケーションのビジネスロジック・画面 UI・クラス設計・詳細コード
- 個別 API の項目レベル仕様・DDL・ORM マッピング
- 個別業務のリトライ回数・タイムアウト値・冪等キー設計（方針はインフラ側でも示すが、値の確定は詳細設計）

**運用・SRE 詳細設計で決める**
- 各アラートの具体閾値（CPU 80% など）・オンコールシフト・エスカレーション先名
- Runbook（障害発生時の手順書）の本文
- IaC の具体コード（Terraform / CloudFormation / Ansible の実装）

例外: 上記に属する項目でも、インフラ構成判断の根拠として最小限明示すべき場合は触れてよい（例: 「NFR-00X の稼働率 99.95% を満たすため Multi-AZ Active-Standby を採用」のように、根拠となる要件・目標値を示す）。ただし Runbook 本文・IaC コードには踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。特に `non-functional.md` の `NFR-NNN` は本設計の目標値となる。
- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）も既定の入力とする。存在すれば必ず参照する。特に `COMP-NNN`（構成要素）・`LNK-NNN`（通信・連携）・`HO-I-*`（インフラ設計への申し送り）は本設計の出発点となる。
- 追加で $ARGUMENTS にファイルパス・テキスト（クラウド契約上の制約、社内ネットワーク標準、既存運用監視基盤の前提など）が渡された場合はそれを併用する。
- 要件定義書またはアーキテクチャ設計書が存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえで、インフラ判断の根拠を明示する（抽出した暗黙前提は末尾の「リスク・懸念点」に「要件未確定として進めた前提」として記載する）。

## 出力ファイル
- `docs/design/infrastructure/infrastructure.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: インフラ設計は「全体の物理構成の辻褄」（ある経路がネット → セキュリティ → 認証 → 監視 → バックアップ → 復旧まで一貫して設計されているか）を読み手が 1 本の流れで検証できることが最重要であるため。IaC コードや Runbook は詳細設計・運用設計として別途配置し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体像 → 配置 → ネットワーク → 非機能（可用性・スケール）→ セキュリティ → 運用（監視・BK/DR・デプロイ）→ 採用理由 → 却下理由 → 懸念点」の順に、外側（全体）から内側（運用手段）・過去の判断（理由）・未解決（リスク）へと辿れるよう意図しているため、順序は固定する。

1. 構成概要
2. システム構成図
3. コンポーネント配置
4. ネットワーク構成
5. 可用性設計
6. スケーリング設計
7. セキュリティ設計
8. 運用設計（監視・ログ・アラート）
9. バックアップ / リカバリ
10. デプロイ戦略
11. 採用理由
12. 代替案と採らない理由
13. リスク・懸念点

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/infrastructure-template.md`](templates/infrastructure-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. 構成概要
- システム全体の稼働環境を 1 段落（数文）で要約する。クラウド / オンプレ / ハイブリッドの別、採用するクラウドベンダー（または具体の DC）、特徴的な設計方針（例: 「東京リージョン Multi-AZ」「マネージド中心・運用負荷を最小化」「オンプレ DB＋クラウドアプリの二層構成」）を 2〜3 点挙げる。
- 利用する主要サービス／製品を箇条書きで列挙する（ロードバランサ・コンピュート・DB・オブジェクトストレージ・キュー・CDN・監視・CI/CD 等）。選定の根拠は本章では簡記に留め、詳細は「11. 採用理由」に集約する。
- 想定する前提・非前提（スコープ外）を箇条書きで明記する。特に「既存の社内ネットワーク・既存監視基盤・既存 IdP の利用を前提とする」「本番・検証・開発の 3 環境を扱い、ステージング相当は本ドキュメントでは扱わない」など、後続判断の前提を明示する。

### 2. システム構成図
- 物理構成を Mermaid `flowchart` で 1 枚図示する。粒度はインフラ論点が辨別できる単位（ロードバランサ・ノード群・DB・ストレージ・外部接続点・運用管理経路）とし、アプリの関数・クラス粒度までは降りない。
- **アーキテクチャ設計の論理図との違い**: アーキ側が論理責務配置のみを示したのに対し、本章では**リージョン / AZ / VPC / サブネット / ネットワークゾーン（公開網 / DMZ / プライベート）**を `subgraph` で明示する。ロードバランサ・踏み台・NAT・ゲートウェイなどネットワーク機器・境界は本章で描く。
- 外部アクター（利用者・運用者・外部システム・IdP など）をシステム境界の外に描き、入出力経路（インターネット経由 / 専用線 / VPN など）を太線または注記で区別する。
- 構成図に登場する主要要素は必ず「3. コンポーネント配置」または「4. ネットワーク構成」の表で `INF-NNN` / `NET-NNN` として拾われていることを、章末で突き合わせる。

### 3. コンポーネント配置
- アーキテクチャの `COMP-NNN` を、実環境でどのインフラ資源（ノード／マネージドサービス）に載せるかを表で対応付ける。列:
  - `INF-NNN` / 名称 / 配置先（具体のクラウドサービスまたはホスト群）/ 種別（コンピュート / DB / キャッシュ / メッセージング / ストレージ / ネットワーク機器 / マネージドサービス 等）/ 対応 `COMP-NNN`（複数可）/ 主な役割 / 冗長化方針（章 5 で詳述）の概要 / 関連 NFR
- `INF-NNN` は `INF-001` から採番する。1 つの `COMP-NNN` が複数のインフラ要素に分かれる場合（例: API コンポーネント → コンテナ基盤 + オートスケーラ + ALB）、それぞれに別 `INF-NNN` を与え、対応する `COMP-NNN` を同じ値で参照する。
- 逆に、アーキ側に現れない**インフラ固有の要素**（ロードバランサ・WAF・踏み台・CDN・Secret 管理サービス・監視エージェント・ログ集約基盤など）もここで独立した `INF-NNN` として列挙する。これらは `COMP-NNN` 列を「該当なし（インフラ固有）」としつつ、「役割」列で何のために置くかを一文で明示する。
- 章末で「アーキ側のすべての `COMP-NNN` が本章のいずれかの `INF-NNN` に配置されているか」を突き合わせる。漏れがあれば、それは構成漏れか、アーキ側のコンポーネントが物理的には別要素に吸収される根拠を示す。

### 4. ネットワーク構成
- ネットワーク要素を表形式で列挙する。列:
  - `NET-NNN` / 名称 / 種別（VPC / サブネット / セキュリティグループ / ルートテーブル / NAT / ゲートウェイ / VPN / 専用線 / ロードバランサ / WAF / CDN / DNS 等）/ 範囲（リージョン / AZ / アカウント）/ 配置する `INF-NNN`（複数可）/ 許可する通信（概要）/ 関連 `LNK-NNN`（アーキ側）
- **ゾーニング**: ネットワークゾーン（公開網 / DMZ / プライベート / 管理用）の設計方針を冒頭で明示する。どのゾーンに何を置くか、ゾーンをまたぐ通信の基本方針（どちら向きを許可するか・必ず LB / ゲートウェイ経由にするか）を示す。
- **アーキ側 `LNK-NNN` の経路具体化**: アーキの主要通信・連携（特にユーザ応答経路と外部サービス連携）を、本章のどの NET／SG を通るかで実経路として示す。代表経路 1〜3 本を、Mermaid `flowchart` で上から下へ矢印を追える形で図示すると読み手に伝わりやすい。
- 外部との接続（インターネット経由 / 専用線 / VPN）の終端点・プロトコル・許可元を明示する。IdP・決済・メール・通知などの外部 SaaS との接続経路（FQDN 許可・IP 許可リスト方式・Private Link 等）を `NET-NNN` として扱う。

### 5. 可用性設計
- 冗長化方針を `INF-NNN` 単位で整理する。表の列:
  - `INF-NNN` / 冗長化方式（Active-Active / Active-Standby / Multi-AZ / シングル AZ / Read Replica / キュー滞留 等）/ 障害ドメイン分離の粒度（AZ 分離 / リージョン分離 / ラック分離）/ フェイルオーバー機構（自動 / 手動）/ 目標稼働率 / RTO 目標 / 根拠 `NFR-NNN`
- 「冗長化しない」判断をする `INF-NNN` は、その根拠（コスト・要件で不要・復旧手順で十分）を明記する。暗黙の SPOF を残さないため、すべての `INF-NNN` について冗長化方針を 1 行は書く。
- 単一障害点（SPOF）が残る場合は、本章末で「許容 SPOF 一覧」として、影響範囲と許容理由・復旧手順の参照先を表でまとめる。
- DR（災害復旧）については、対象範囲（業務継続対象のユースケース）と方式（別リージョン Active-Standby / バックアップ取り置き → 手動復旧 等）を明記する。対象外であればその旨と理由（コスト・要件で不要）を書く。

### 6. スケーリング設計
- スケーリング方針を `INF-NNN` 単位で整理する。列:
  - `INF-NNN` / スケール手段（スケールアウト / スケールアップ / 両方 / 非対応）/ 発動トリガ（CPU・リクエスト数・キュー長・時間帯・手動 等の概要）/ 想定最小〜最大の粒度（例: 2〜10 台、vCPU 2〜16）/ 制約（DB 接続数上限・ライセンス上限・外部サービスのスロットリング等）/ 関連 `NFR-NNN`
- **具体の閾値（CPU 80% など）は運用・SRE 詳細設計で確定**するため、本章では「発動トリガの種別（指標）と大まかな方向性」に留める。閾値までは決めない。
- スケール不可能な要素（例: 単一の書き込み可能 DB ノード・外部 SaaS のレート制限）を明示する。これらは可用性・性能の天井になるため、想定負荷の上限と突破時の対応方針（キュー滞留で吸収 / 利用者へのエラー表示 等）を書く。
- ピーク時負荷想定が要件で示されていれば、その値を引用し、スケール構成で吸収できる範囲を記述する。示されていなければ「要件未確定」として「13. リスク・懸念点」に退避させる。

### 7. セキュリティ設計
- 認証・認可・通信保護・データ保護・監査の観点でインフラ側の責務を整理する。アーキ側で決めた認証認可の**論理責務位置**を前提として、それを物理的に実現する基盤構成を示す。
- 典型的に書くべき項目:
  - **認証**: 利用者認証の基盤（IdP 接続方式・プロトコル：OIDC / SAML 等・MFA の有無・アカウントライフサイクル）/ 運用者認証（SSO・踏み台・特権ユーザ管理）/ システム間認証（サービスアカウント・API キー・短期トークン・mTLS）
  - **認可**: 基盤レベルの認可境界（ネットワーク分離・IAM ロール・Secret 権限・管理コンソールアクセス）。アプリ内の業務権限判定はアプリ責務（詳細設計）として扱うが、それを支える鍵・ロールの払い出しポリシーは本章で決める。
  - **通信保護**: インターネット経路の TLS（証明書発行・更新・最低バージョン）、内部通信の暗号化要否、VPN / 専用線の暗号化、WAF の配置点、DDoS 対策の有無
  - **データ保護**: 保存時暗号化（ディスク・DB・ストレージ）、鍵管理（KMS・HSM）、機微データの取り扱い境界、ログから機微項目を落とす方針
  - **監査ログ**: 誰が何をしたかを残す必要のある操作（管理コンソールアクセス・Secret 参照・特権操作）、集約先、保管期間、改竄検知の有無
- 各項目は対応する `NFR-NNN`（真正性・機密性・完全性・責任追跡性・否認防止）に紐付ける。紐付かないものは過剰対策の疑いがあるため、「12. 代替案」に退避するか根拠を追記する。

### 8. 運用設計（監視・ログ・アラート）
- 監視・ログ・アラートを、「何を観測するか」「どのコンポーネントで生成／集約されるか」「誰が受け取るか」の 3 観点で整理する。表の列:
  - `OPS-NNN` / 観点（監視項目 / ログ種別 / アラート）/ 対象 `INF-NNN` / 収集・集約手段（エージェント・マネージドサービス等）/ 保管期間の方針 / 通知先（運用チーム / オンコール / 利用者）/ 関連 `NFR-NNN`
- **監視**: リソース監視（CPU / メモリ / ディスク / ネットワーク）、アプリ監視（エラーレート・レイテンシ・スループット）、業務監視（重要ユースケースの成功率）、外形監視（利用者視点でのエンドポイント到達性）を区別して、どれを採るか・採らないかを決める。
- **ログ**: アプリケーションログ・アクセスログ・監査ログ・インフラログ（ロードバランサ / WAF / DB スローログ等）を区別し、生成元 `INF-NNN`・集約先・保管期間の方針を書く。機微データをログに出さない方針も本章で言及する。
- **アラート**: アラートは「何を判定して、誰に、どの経路で」を決める。具体の閾値値・オンコールシフトは運用・SRE 詳細設計に委ねる（閾値を先に固めるとチューニングの余地がなくなるため）。
- 運用時間帯（24/365 / 営業時間のみ 等）と対応体制の前提（要件側で定まっている `NFR-NNN` を引用）を章末で確認する。

### 9. バックアップ / リカバリ
- バックアップ対象・方式・保管先・保管期間・復旧手順概要を `INF-NNN` 単位で整理する。列:
  - `INF-NNN` / バックアップ対象（DB / ファイル / 設定 等）/ 取得方式（スナップショット / 論理ダンプ / レプリケーション / バージョン管理 等）/ 取得頻度 / 保管先・保管期間 / RPO 目標 / RTO 目標 / 復旧手順の概要 / 根拠 `NFR-NNN`
- **RPO / RTO**: 要件で目標値が示されている `NFR-NNN` を引用し、本インフラ構成で達成可能かを記述する。達成できない場合はリスクとして「13. リスク・懸念点」に退避する。
- **復旧手順の概要**: 「どの手順書を、誰が、どの順で叩くか」の骨格までを書く。手順書の本文（具体コマンド・チェックポイント）は運用・SRE 詳細設計で作成する。
- 論理削除・誤削除からの復旧（ポイントインタイムリカバリ等）と、物理障害からの復旧（再構築・レプリカ昇格等）を分けて書く。それぞれで RPO / RTO が異なることが多い。

### 10. デプロイ戦略
- CI/CD パイプライン、リリース方式、環境分離、ロールバック方針を整理する。
- **環境分離**: 本番 / 検証 / 開発など本プロジェクトで扱う環境を列挙し、それぞれの用途・利用者・データ区分（本番データを扱うか）・アクセス制限を明示する。環境間でどれが同等構成でどれが縮小構成かを示す。
- **CI/CD パイプライン**: ビルド → テスト → デプロイの段階と、ゲート（自動テスト合格・セキュリティスキャン・承認）を段階表として整理する。採用する CI/CD 基盤の種別（SaaS / 社内ホスト）まで示す。具体のワークフロー YAML は本ドキュメントでは扱わない（運用・SRE 詳細設計で作る）。
- **リリース方式**: Blue-Green / カナリアリリース / ローリングアップデート / メンテナンス停止 のいずれを採るか、対象の `INF-NNN` ごとに決める。DB のスキーマ変更はリリース方式と整合するか（後方互換があるか・ダウンタイムが必要か）を必ず言及する。
- **ロールバック**: 各 `INF-NNN` について、ロールバック可能か・可能な場合の方法（古い成果物への切替・DB は別対応 等）を書く。特に DB はロールバック困難な場合が多いため、スキーマ変更の前方互換化方針を明示する。
- 本番リリースに関わる**承認フロー**（誰が承認するか・本番適用可能時間帯）の骨格を書く。個別の承認者名・シフトは運用・SRE 詳細設計に委ねる。

### 11. 採用理由
- 各主要判断（クラウドベンダー選定・マネージド vs 自前運用・Multi-AZ 採否・DR 構成・CI/CD 基盤 等）について、「なぜこの構成にしたか」を要件 ID と結びつけて記述する。形式: 箇条書きで「判断 → 紐付く `NFR-NNN` / `UC-NNN` / `COMP-NNN` / `HO-I-*` → 根拠（要件のどの条件を満たすため・どの申し送りに応えるため）」。
- 技術選択（特定のクラウドサービス・運用基盤）を伴う場合、以下を必ず明示する。
  - 決め手となった非機能要件（`NFR-NNN`）
  - 想定スケール・運用規模の前提（概算値・仮置きの根拠も可）
  - 社内標準 / 既存契約 / 既存資産の制約
  - コスト面の前提（ざっくりの月額レンジで可、ただし「規模感を示すための仮値」であることを明記）
- 「よく使われているから」「慣れているから」のような要件に紐付かない採用理由は書かない。紐付けられない場合は「12. 代替案」で整理する。

### 12. 代替案と採らない理由
- 主要判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`。
- 最低でも以下のインフラ設計上の判断については検討の痕跡を残すことを推奨する（該当しなければ「検討不要と判断した理由」を 1 行で）。
  - 稼働環境（クラウド A / クラウド B / オンプレ / ハイブリッド）
  - 計算資源の形態（VM / コンテナ / サーバレス）
  - データストアの具体サービス（マネージド DB A / マネージド DB B / 自前運用 等。種別はアーキ側で決定済みである前提）
  - 可用性レベル（Single-AZ / Multi-AZ / Multi-Region）
  - DR 方式（DR なし / バックアップ取り置き / 別リージョン Active-Standby）
  - CI/CD 基盤（SaaS 型 / 社内ホスト型）
- 「再検討条件」は将来の保守性を左右するため、具体の閾値で書く（例: 「同時利用者が想定の 10 倍になった場合」「月額が X 万円を超えた場合」「規制でデータ国外保管が禁止された場合」）。

### 13. リスク・懸念点
- 現時点で未解消のリスク・前提の脆さを列挙する。列: `RISK-NNN / 内容 / 影響範囲（INF / NET / OPS / 業務）/ 顕在化条件 / 暫定対応 / 運用・詳細設計への申し送り`。
- リスクの典型カテゴリ:
  - クラウドベンダー障害時のフォールバック
  - 性能試算の不確実性（想定負荷と実負荷の乖離）
  - コスト超過（予算超過・想定外のサービス利用）
  - 既存ネットワーク・既存監視基盤・既存 IdP との接続の脆さ
  - 鍵・証明書・ライセンスの更新漏れ
  - 外部サービスのレート制限・障害
  - 運用・オンコール体制の未確定
  - 法令・規制適合（データ所在地・保存期間・個人情報保護）
- 「要件未確定のまま進めた前提」もここに含める。確認先と、確認できなかった場合の最悪ケース影響を併記する。

## 図解の記法ルール
要件定義書・アーキテクチャ設計書と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。用途と推奨ダイアグラム:

- システム構成図 / ネットワーク経路図: `flowchart` または `graph`
  - **アーキ側との違い**: リージョン / AZ / VPC / サブネット / ネットワークゾーン（公開網 / DMZ / プライベート / 管理用）を `subgraph` で明示する。ロードバランサ・NAT・踏み台・ゲートウェイなどネットワーク機器を図示する
  - 外部アクター（利用者 / 運用者 / 外部 SaaS）はシステム境界の外に描き、接続経路（インターネット経由 / 専用線 / VPN）を注記する
- 障害時のフェイルオーバー・リリースフロー等の手順系: `sequenceDiagram` または `flowchart`（判断分岐含む場合）
- リリースパイプラインの段階表現: `flowchart LR`（左→右に段階を並べる）

## ID 体系
本ドキュメント内で採番する ID は以下。要件定義書・アーキテクチャ設計書側の ID（`UC / NFR / COMP / LNK / HO-I` など）はそのまま参照し、再採番しない。

- `INF-NNN` インフラリソース（ノード / マネージドサービス / ネットワーク機器 等）
- `NET-NNN` ネットワーク構成要素（VPC / サブネット / SG / ルート / LB / WAF / DNS 等）
- `OPS-NNN` 運用項目（監視・ログ・アラート・バックアップ・デプロイ段階 等）
- `ALT-NNN` 代替案
- `RISK-NNN` リスク・懸念点

一度採番した ID は変更しない。削除された要素は表から消さず、ステータスを「廃止」としてトレーサビリティを残す方針でもよい（プロジェクトのポリシーに従う）。

## 要件定義書・アーキテクチャ設計書との紐付け
- すべての `INF-NNN` は、少なくとも 1 つの `COMP-NNN` または `HO-I-*`（インフラ設計への申し送り）に紐付けて「なぜ必要か」を説明できる状態にする。紐付かない `INF-NNN` は過剰構成の疑いがあるため、「12. 代替案」として扱うか、必要性の根拠を追記する（例: 監視・踏み台のようにインフラ固有の基盤要素は `COMP-NNN` に直接紐付かないが、`NFR-NNN` には紐付く）。
- すべての `NFR-NNN`（特に可用性・時間効率性・セキュリティ・運用時間・バックアップ・規制適合）について、本ドキュメントのどの章・どの `INF-NNN` / `OPS-NNN` が担保するかを説明できる状態にする。担保できていない `NFR-NNN` はリスクとして「13. リスク・懸念点」に退避する。
- アーキテクチャ設計書の `HO-I-*`（インフラ設計への申し送り）について、本ドキュメント内で回答済み・保留・差し戻しのいずれかに分類する。保留・差し戻しは「13. リスク・懸念点」に理由付きで記載する。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を明記して残すほうがよい。

### 1. 単一障害点（SPOF）が隠れていないか
- すべての `INF-NNN` について冗長化方針（冗長化する / しないを含めて）が「5. 可用性設計」で 1 行以上記載されているか。
- 「冗長化しない」と決めた要素について、許容理由と復旧手順の参照先が書かれているか。暗黙の SPOF が残っていないか。
- アーキ側の `LNK-NNN`（特にユーザ応答経路上）が、通る `INF-NNN` のどれかで切れると業務が止まる箇所を洗い出したか。

### 2. セキュリティ境界が明確か
- ネットワークゾーン（公開網 / DMZ / プライベート / 管理用）がどこで切れるかが構成図・`NET-NNN` 表から読み取れるか。
- 外部からの入口（インターネット / 専用線 / VPN）と、内部から外部への出口（NAT / Private Link / 直接）のそれぞれに、認可・検査の責務がどの `INF-NNN` / `NET-NNN` にあるかが明示されているか。
- 運用者アクセス経路（踏み台 / SSO / 特権管理）が利用者アクセス経路と別経路になっているか、あるいは同一経路とする場合の追加管理策が書かれているか。
- 鍵・証明書・Secret の保管と参照権限が `INF-NNN` として扱われているか。

### 3. スケーラビリティが要件と整合しているか
- 要件側で想定されているピーク負荷・利用者数（`NFR-NNN` 時間効率性・容量満足性）を、どの `INF-NNN` のどのスケール手段で吸収するかが言語化されているか。
- スケール不能な要素（書き込み可能 DB・外部サービスのレート）が特定され、突破時の挙動が書かれているか。
- 「自動 / 手動」のスケール判断が要素ごとに明示されているか（自動化の要求度は運用コストと連動する）。

### 4. 運用で困らないか（監視・ログ・BK/DR）
- リソース・アプリ・業務・外形の各監視観点について、採る／採らないが `OPS-NNN` で明示されているか。採らない観点はその根拠が書かれているか。
- すべての `INF-NNN` について、何らかの監視・ログがかかっているか。完全に無監視の `INF-NNN` がないか。
- バックアップ対象の各 `INF-NNN` について、RPO / RTO 目標と本構成での達成見込みが書かれているか。達成できないものはリスクに退避されているか。
- デプロイについて、環境分離・リリース方式・ロールバック方針の 3 点が揃っているか。特に DB スキーマ変更の前方互換化方針が言及されているか。

### 5. コストとトレードオフが明示されているか
- 採用した主要構成（Multi-AZ / マネージド利用 / DR 構成 / 24/365 監視 等）について、「コストを払ってでも得たい要件（`NFR-NNN`）」がペアで記述されているか。
- 代替案（`ALT-NNN`）に「コスト面で不採用」や「コスト面で採用」の判断が、ざっくりの規模感（月額レンジ・オーダー）付きで書かれているか。
- 将来の再検討条件（`ALT-NNN` の再検討条件列）に、コスト・規模の閾値が具体的に書かれているか。

### 6. 粒度の侵食が起きていないか
- **上向きの侵食**（アーキ設計へ踏み込んでいる）: コンポーネントの責務再定義・同期／非同期の境界・認証認可の責務位置など、論理構成そのものを本ドキュメントで変えていないか。変えたい場合はアーキ側への差し戻しとして扱う。
- **下向きの侵食**（運用・SRE 詳細設計へ踏み込んでいる）: 個別アラートの具体閾値（CPU 80% など）・Runbook 本文・IaC の実装コード・オンコールシフトが紛れていないか。紛れていたら「運用・詳細設計への申し送り」として切り出す。
- **横向きの侵食**（アプリ詳細設計へ踏み込んでいる）: ビジネスロジック・画面 UI・クラス設計・DDL・ORM マッピングが紛れていないか。

### 7. 図・表・ID の整合
- 構成図に登場するすべての要素が「3. コンポーネント配置」または「4. ネットワーク構成」の `INF-NNN` / `NET-NNN` として存在するか。
- `INF-NNN` の冗長化／スケール／セキュリティ／監視／BK/DR／デプロイの各章への展開漏れがないか。
- アーキ側の `COMP-NNN` がすべていずれかの `INF-NNN` に配置されているか。`HO-I-*` に対する回答・保留がすべて説明されているか。
