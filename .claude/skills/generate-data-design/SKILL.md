# データ設計の作成
要件定義書およびアーキテクチャ設計書から、基本設計の起点となるデータ設計書を作成してください。

## Goal
業務要件に対応したデータ構造のたたき台を、過不足の少ない粒度で示す。

「過不足が少ない」とは、要件・ユースケース・アーキテクチャで扱うデータを漏れなく保持できること、かつ現時点の要件では正当化できない要素（先取りの履歴テーブル・使い所のない汎用属性・過剰な正規化／非正規化など）は含めない、という意味である。判断に迷ったら、対応する要件 ID（UC-NNN / ENT-NNN / NFR-NNN）または構成要素 ID（COMP-NNN）に紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて代替案・注意事項に記録する。

## 位置付け（要件定義・アーキテクチャ設計・詳細設計・インフラ設計との関係）
本スキルは `/generate-requirements` と `/generate-architecture-design` の成果物を入力とし、詳細設計・実装の出発点となる**論理データモデル**を固める。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 特に `functional.md` の「データ定義（ENT-NNN）」は本ドキュメントの出発点となる。要件側はデータの塊を粗粒度で列挙したものであり、本スキルで属性・主キー・関連・整合性を肉付けする。
  - 各 `usecase.md` の「アクターがCRUDする情報」で要求されている操作が、設計エンティティ側に過不足なく反映されるかを検証する。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - データストア責務を持つコンポーネント（`COMP-NNN`）・区分「DB」や「キャッシュ」・非同期境界の分離（`LNK-NNN` の同期／非同期）を参照し、どのデータがどのコンポーネント配下で保持されるかを明らかにする。
- 下流（詳細設計）: `docs/design/` 配下の機能・画面単位の詳細設計、および物理テーブル設計／索引／SQL／ORM マッピング。
- 下流（インフラ設計）: ストレージエンジン・ディスク容量見積り・バックアップ方式・レプリケーション構成。本スキルでは扱わない。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**論理データモデルレベル**の話であり、DBMS 固有の型・構文・チューニングには踏み込まない。

- エンティティ（テーブル相当の保存単位）の洗い出し
- 各エンティティの主な属性（名称・意味・論理的な型：文字列／数値／日付／真偽値／列挙／参照 等）
- 主キー（PK）・識別子・代替キー（UK／自然キー）
- エンティティ間の関連（多重度・依存の強さ・所有関係）
- 生成・更新・削除のライフサイクル（いつ生まれ・どう変わり・どう消えるか）
- 削除方針（論理削除 / 物理削除 / アーカイブ）
- 状態を持つエンティティの状態遷移
- 整合性制約（必須 / 一意 / 参照整合性 / 値の範囲・列挙 / エンティティ横断の業務制約）
- 監査・履歴の必要性（作成者・更新者・作成日時・更新日時・履歴テーブル・論理削除フラグ 等）

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、データ設計が定まった後の工程で決める。粒度が崩れると議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**詳細設計（機能 / 画面単位・物理テーブル設計）で決める**
- DBMS 固有の型指定（例: `VARCHAR(255)` / `NVARCHAR` / `TEXT` / `NUMERIC(10,2)` のいずれを使うか）
- 索引戦略（どの列に索引を張るか・複合索引の順序・部分索引・カバリング索引）
- 正規化の物理的な崩し方（性能のためのデノーマライズ、マテリアライズドビュー、サマリテーブル）
- パーティショニング／シャーディングの具体設計
- SQL / DDL / ORM 実装コード
- プロシージャ・トリガ・ビューの実装

**インフラ設計で決める**
- DBMS 製品・バージョン選定（「関係モデル」「ドキュメント」等の**種別**はアーキテクチャで、具体製品はインフラで）
- ストレージ容量見積り・IOPS 見積り
- バックアップ方式・レプリケーション構成・DR 構成

例外: 上記に属する項目でも、論理モデル判断に直結する場合（例: 「外部 SaaS の既存スキーマと揃える必要があり、属性名と型の論理指定が契約上固定されている」）は、前提として最小限言及する。ただし具体 DDL には踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。
- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）も既定の入力とする。存在すれば必ず参照する。
- 追加で $ARGUMENTS にファイルパス・テキストが渡された場合はそれを併用する。
- 要件定義書またはアーキテクチャ設計書が存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえで、データ設計判断の根拠を明示する（抽出した暗黙前提は「6. 注意事項」の「前提の脆さ」として記載する）。

## 出力ファイル
- `docs/design/data/data-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: データ設計は「エンティティ間の辻褄」「業務ライフサイクルの一貫性」を読み手が 1 本の流れで検証できることが最重要であるため。テーブル毎の詳細な物理設計は、詳細設計工程で機能単位・画面単位の別ファイルに展開し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体方針 → 個別エンティティの俯瞰 → 個別エンティティの詳細 → 関係性 → 横串の制約 → 未決事項」の順に理解できるよう意図しているため、固定する。

1. データ設計方針
2. エンティティ一覧
3. 各エンティティ詳細
4. 関連図
5. 整合性ルール
6. 注意事項

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/data-design-template.md`](templates/data-design-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. データ設計方針
- 本データ設計全体を貫く方針を、箇条書きで 3〜6 点程度にまとめる。論理モデルレベルの判断のみを扱い、物理設計や製品固有事項には踏み込まない。
- 典型的に書くべき方針:
  - **採用するデータモデル種別**: 関係モデル / ドキュメント / KVS 等（アーキテクチャ設計の `ALT` で決定された結果を再掲する。ここで新たに決めるのではなく、アーキ側の決定を前提とする）。
  - **キー方針**: サロゲートキー（連番 ID / UUID 等の論理扱い）を基本とするか、自然キーを基本とするか。併用する場合は判定基準。
  - **識別の粒度**: 人・組織・案件といった主要な登場概念を、一意に識別する単位（テナント単位 / 利用者単位 / 組織単位 等）。マルチテナントの有無と適用範囲。
  - **削除方針**: 論理削除（削除フラグ）を基本とするか、物理削除を基本とするか。例外的に反対を採るエンティティの判定基準。
  - **履歴・監査方針**: 監査項目（作成者・更新者・作成日時・更新日時）を全エンティティで持つか、特定エンティティのみか。履歴テーブルを持つ条件。
  - **状態管理の表現**: 状態を持つエンティティを識別するための列（`status` / `state` 等）の命名・値集合の方針。状態遷移の管理位置（列挙型で持つか、別テーブルに履歴化するか）。
  - **参照整合性の方針**: 外部キー制約を論理モデル上で宣言するか（物理 FK を張るかどうかは詳細設計）、アプリケーション側で担保するか。
- 「流行っているから」「慣れているから」といった要件・アーキに紐付かない方針は記載しない。

### 2. エンティティ一覧
- システムが保持する論理エンティティを表形式で列挙する。列:
  - `ENT-NNN` / 名称 / 区分（マスタ / トランザクション / 集計 / ルックアップ / ログ・監査 等）/ 概要 / ライフサイクル（長期保持 / 有効期限あり / 世代管理あり 等の概要）/ 保持責務を担う COMP / 関連 UC・ENT（要件側）
- **`ENT-NNN` は要件定義書の `ENT-NNN` と同一の ID 空間を使う。**要件側で既に採番されている ID はそのまま引き継ぎ、設計段階で分割・派生させる場合は新しい番号を採番して「由来 ENT」列で要件側の元 ID を参照する（例: 要件 `ENT-007 注文情報` を `ENT-007 注文` と `ENT-020 注文明細` に分ける、など）。
- 「区分」は性格を示す。典型:
  - **マスタ**: 業務の軸となる静的データ（利用者・顧客・商品 等）
  - **トランザクション**: 業務イベントで都度発生するデータ（注文・入金・契約 等）
  - **集計**: 他エンティティから派生する計算結果（月次サマリ 等）
  - **ルックアップ**: 区分値・選択肢など小規模な参照用データ
  - **ログ・監査**: 追記のみで更新・削除されない記録
- 「保持責務を担う COMP」列には、アーキテクチャ設計書の `COMP-NNN`（区分「DB」等）を記入する。複数存在する場合は主たる保持先を記載し、副次的なコピー（キャッシュ・検索インデックス等）は注意事項に回す。

### 3. 各エンティティ詳細
各エンティティについて、以下のサブ見出しで詳細を記述する。粒度の揃えやすさと横並び比較を重視し、すべてのエンティティで同じテンプレートに沿って書く（該当なしの節は「該当なし」と明記し、省略しない）。

`#### ENT-NNN 名称`

- **概要**: 何を表すエンティティか、1〜2 文で記述。要件定義書の `ENT-NNN` と対応する場合は由来を示す。
- **属性一覧**: 表形式で列挙する。列:
  - `属性名（論理） / 論理型 / 必須 / 役割（PK / UK / FK / 値 / 監査 / 派生） / 値の範囲・列挙値 / 概要`
  - **論理型**は DBMS 非依存の表記（例: 文字列 / 整数 / 数値（小数） / 真偽値 / 日付 / 日時 / 列挙 / 参照（`ENT-NNN`）/ バイナリ）。具体型（`VARCHAR(255)` 等）は書かない。
  - **PK** は主キー、**UK** は代替キー（業務的に一意な別の識別子）、**FK** は他エンティティへの外部参照。役割が複数ある場合は併記する（例: `PK, FK`）。
  - **監査** は作成者・更新者・作成日時・更新日時などの監査項目。
  - **派生** は他の属性や他エンティティから計算される値（例: 合計金額）。派生項目は保持すべきか算出すべきかを注意事項で論じる候補になる。
- **キーの考え方**: PK にサロゲートを使う場合は業務的な UK も必ず記載する。自然キーを PK にする場合はその妥当性（不変性・重複しないことの保証）を一文で述べる。
- **ライフサイクル**:
  - 生成契機: 誰が・どの UC で・どの LNK 経由で作るか（例: 「UC-007 によって利用者が作成」）
  - 更新契機: どの属性がどの UC で更新されうるか（全属性一覧は不要、更新されうる軸のみ）
  - 削除方針: 論理削除 / 物理削除 / アーカイブ / 削除不可（追記のみ）のいずれか。削除不可の場合は保存期間の要件（NFR-NNN との紐付け）を記載する。
- **状態遷移**（状態を持つエンティティのみ）: 状態を表す列と取りうる値、主要な遷移をサブ節で記述する。図は「4. 関連図」ではなく本節で `stateDiagram-v2` として配置してよい。
- **監査・履歴**: 監査 4 項目（作成者・作成日時・更新者・更新日時）を持つか。履歴テーブルを別途設ける場合は、履歴を取る属性の範囲と、履歴から参照する UC（例: 「UC-013 予実管理表で過去の値を参照するため」）を記載する。
- **備考**: 詳細設計に回す論点（索引候補・性能懸念・非正規化の可能性）は、詳細設計への申し送りとして「6. 注意事項」に集約する。ここには**論理モデルレベルの**補足のみを書く。

属性に個別 ID を採番しない（属性は `ENT-NNN` のスコープ内で属性名により一意となるため、横断参照の必要がない）。整合性制約のうち、複数エンティティ・複数属性にまたがるものは「5. 整合性ルール」で `RULE-NNN` として採番する。

### 4. 関連図
- エンティティ間の関連を Mermaid の `erDiagram` で 1 枚（または主題別に複数枚）配置する。
- 要件定義書の `erDiagram` と齟齬がないかを確認する。要件側は「データの塊」粒度でしか描かれていないため、設計で分割・追加したエンティティが増えることは自然だが、削除や意味の変更があるなら要件側のメンテナンスを促す（注意事項に記載）。
- 図の記法:
  - 属性も含めて記述する（要件側は属性を書かないが、設計側では書く）。主要属性に絞ってよい（PK / 主要な FK / 業務的に重要な UK）。
  - 多重度は `||--o{` のような標準記法を使う。識別関連・非識別関連の区別を意識する。
  - 図に載せにくい多対多の関係（中間テーブルを介するもの）は、中間テーブルをエンティティとして明示的に登場させる。
- 関連ごとに以下を表形式で整理する。列: `REL-NNN / 親エンティティ / 子エンティティ / 多重度 / 参照の向き / 依存の強さ（親が消えると子も消えるか） / 関連の意味（業務上の何を表現するか） / 関連 UC`。
- 循環参照や自己参照（階層構造・ツリー構造）がある場合は、必ず本節で明示し、意味と終端条件を記述する。

### 5. 整合性ルール
- 複数エンティティ・複数属性にまたがる業務制約を、`RULE-NNN` として表形式で列挙する。列:
  - `RULE-NNN / 内容 / 対象エンティティ（ENT-NNN） / カテゴリ / 違反時の扱い / 関連 UC・BRU・NFR`
- カテゴリの典型:
  - **必須性**: 条件付きの必須（他属性の値に応じて必須となるもの）
  - **一意性**: 複数列の組み合わせでの一意、部分一意（論理削除を除いた一意 等）
  - **参照整合性**: FK の整合性、削除時の連鎖挙動（禁止 / 連鎖 / NULL 化）
  - **値域・状態遷移**: 状態列の許容遷移、数値の範囲、日付の前後関係
  - **業務ルール**: 要件定義書の `BRU-NNN` がデータ整合性として表現されるもの（例: 「確定後の注文は金額を変更できない」）
- 違反時の扱いは「登録拒否 / 警告表示 / 自動補正 / ログ記録のみ」等で記述する。拒否の場合は、どのレイヤで拒否するか（データ層 / アプリケーション層 / 画面入力段階）の方針を明示する（実装位置の最終確定は詳細設計だが、方針は本章で決める）。
- 整合性ルールのうち、要件定義書の `BRU-NNN` に由来するものは `BRU-NNN` を参照する。新たに発見された業務ルールは、要件側に追加すべきか本データ設計内に閉じるかを判断し、要件側に波及させる場合は関連 ID を添える。

### 6. 注意事項
注意事項は単一の表ではなく、以下 3 区分で整理する。混在させると読み手の対応先が曖昧になる。

#### 6.1 リスク・懸念点
- `RISK-NNN / 内容 / 影響範囲（ENT / REL / RULE / 業務） / 顕在化条件 / 暫定対応 / 詳細設計への申し送り`
- 典型カテゴリ:
  - 非正規化の誘惑（参照性能のために冗長属性を持ちたくなる箇所）
  - 履歴の取り方（全部取る / 主要変更のみ / 取らない）が要件と合っているか
  - 論理削除による参照・一意性制約の扱い（削除済みを除いた一意性など）
  - 外部システムから取り込むデータの権威性（自システムが正本か、外部が正本か）
  - マスタ変更時のトランザクション側への波及（過去データの表示時に「当時の値」を出すか、「現在の値」を出すか）
  - 多通貨・多言語・タイムゾーンの保持粒度
  - 監査項目の保存期間と、法令・規制（データ保存期間要件）との整合
  - 要件未確定のまま進めた前提

#### 6.2 代替案と採らない理由
- 主要な論理モデル判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`。
- 最低でも以下については検討の痕跡を残すことを推奨する。該当しなければ「検討不要と判断した理由」を 1 行で記す。
  - **キー方針**: サロゲート vs 自然キー
  - **削除方針**: 論理削除 vs 物理削除 vs アーカイブ
  - **履歴の持ち方**: 履歴テーブル vs 変更ログ vs 持たない
  - **エンティティ分割**: 1 つのエンティティに集約するか、複数に分けるか（典型: 住所を利用者に埋め込むか、別エンティティに切り出すか）
  - **派生項目の扱い**: 保持するか都度算出するか
- 物理設計寄りの判断（索引・正規化崩し・パーティション 等）は本章では取り上げず、詳細設計の代替案検討で扱う。

#### 6.3 後続工程への申し送り事項
- 本データ設計では決め切らない論点を、**工程別**に分けて記録する。

**詳細設計（機能・画面単位 / 物理テーブル設計）への申し送り**: 表形式で記載。列: `HO-D-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- 索引戦略（どの列に張るか・複合索引の順序）
- 具体の DBMS 型指定
- 物理的な正規化崩し（非正規化するか、マテリアライズドビューを使うか）
- パーティショニング・シャーディング
- ORM マッピング・プロシージャ・トリガ・ビューの実装

**インフラ設計への申し送り**: 表形式で記載。列: `HO-I-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- DBMS 製品・バージョン選定
- ストレージ容量・IOPS 見積り
- バックアップ方式・レプリケーション構成

## 図解の記法ルール
要件定義書・アーキテクチャ設計書と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。

- エンティティ関連図: `erDiagram`
  - 要件定義書側の `erDiagram` は「塊と多重度」のみを描く粒度である。本ドキュメントの `erDiagram` は**属性（主要なもの）と多重度**を描く。
  - 主要属性に絞ってよい。PK、業務的に意味の強い UK、主要 FK、状態を表す列を中心にする。すべての属性を図に入れると可読性が落ちるため、属性一覧は「3. 各エンティティ詳細」の表で網羅し、図はあくまで俯瞰とする。
- 状態遷移: `stateDiagram-v2`
  - 状態を持つエンティティがある場合に使う。取りうる状態・遷移契機・終端を明示する。
  - 遷移契機は UC-NNN / LNK-NNN など、他のドキュメントとの紐付けを併記する。

## ID 体系
本ドキュメント内で採番・参照する ID は以下。

- `ENT-NNN` エンティティ（要件定義書の `ENT-NNN` と**同一 ID 空間**。要件側で既採番の ID を引き継ぎ、必要に応じ新規採番する）
- `REL-NNN` エンティティ間関連
- `RULE-NNN` エンティティ横断の整合性ルール
- `ALT-NNN` 代替案（本ドキュメント内の局所 ID）
- `RISK-NNN` リスク・懸念点（本ドキュメント内の局所 ID）
- `HO-D-NNN` / `HO-I-NNN` 後続工程（詳細設計 / インフラ設計）への申し送り事項

既存 ID は再採番しない。廃止するエンティティ・関連はステータス「廃止」としてトレーサビリティを残すか、要件側との整合を取ってから削除するかを、プロジェクトのポリシーに従って選ぶ。

## 要件定義書・アーキテクチャ設計書との紐付け
- すべての `ENT-NNN` は、少なくとも 1 つの `UC-NNN` または `NFR-NNN` に紐付けて「なぜ必要か」を説明できる状態にする。紐付かないエンティティは過剰設計の疑いがあるため、「6.2 代替案」で不採用として整理するか、必要性の根拠（典型: 監査ログなど NFR 由来）を追記する。
- すべての `ENT-NNN` は、保持責務を担う `COMP-NNN`（アーキテクチャ設計書の構成要素）に紐付けて保持場所を明示する。紐付かない場合は、アーキテクチャ側に保持責務のコンポーネントが存在しないということなので、アーキ側に戻って構成要素を追加する。
- 各 `usecase.md` の「アクターがCRUDする情報」に挙がっている ENT-NNN × 操作が、本ドキュメントのエンティティのライフサイクル・属性でサポートされることを確認する。C（作成）できる情報は作成契機があり、U（更新）できる情報は更新対象となる属性が識別されていること。
- 要件定義書の `BRU-NNN` のうち、データ整合性として表現されるものは `RULE-NNN` として再表現し、`BRU-NNN` を参照する。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を「6. 注意事項」に明記して残すほうがよい。

### 1. 画面・API で必要なデータが過不足なく保持できるか
- 各 `usecase.md` の基本フロー・代替フロー・例外フローで入出力されるデータ項目が、いずれかのエンティティの属性として存在するか（または派生で作れるか）。
- 画面の一覧・詳細・検索条件で扱う項目が、対応するエンティティ属性と結びつくか。検索用にのみ必要で本体に持つべきでない項目が、誤って本体属性として入り込んでいないか（典型: 画面表示用の整形済み文字列）。
- 外部システムから受け取るデータ（`SIF-NNN` / `CIF-NNN`）のうち、保持すべきものが対応エンティティに含まれているか。逆に、受け取るだけで保持不要なデータが誤って属性化していないか。

### 2. 状態遷移に必要な属性があるか
- 状態を持つエンティティに、状態を表す列（`status` 等）と、遷移契機を特定するための属性（遷移日時・遷移者・前状態 等、必要に応じて）が揃っているか。
- 要件側の `stateDiagram-v2` に登場する状態が、属性の列挙値として過不足なく表現されているか。
- 状態遷移に付随する副作用（例: 「承認されたら承認日時を記録する」）が、対応する属性で表現できるか。

### 3. 削除時の扱い（論理 / 物理 / アーカイブ / 削除不可）が妥当か
- 各エンティティの削除方針が「1. データ設計方針」の全体方針と整合しているか。例外を採る場合はその理由が明記されているか。
- 論理削除を採るエンティティで、一意性制約（UK）が「削除済みを除いた一意」になるべきかが検討されているか（典型: 同じメールアドレスの利用者を削除 → 同一メールアドレスで再登録可としたい、など）。
- 参照元がある状態での削除可否（FK 先を先に削除できるか）が、関連表または整合性ルールで明確になっているか。
- 法令・規制・監査要件（データ保存期間）で「一定期間削除不可」が定められているエンティティについて、削除方針と期間が `NFR-NNN` と整合しているか。

### 4. 履歴・監査の必要性が検討されているか
- 監査 4 項目（作成者・作成日時・更新者・更新日時）の採否がエンティティ単位で判断されているか。全エンティティ共通の方針を採るか、例外を置くか。
- 「過去の値を参照する必要があるか」が、エンティティごとに UC-NNN と紐付けて検討されているか（典型: マスタ変更時に過去のトランザクションで「当時の値」を出すか、「現在の値」を出すか）。
- 履歴テーブルを設けるエンティティと、列挙値や上書き更新で十分なエンティティの線引きが明確か。
- 監査ログ用のエンティティ（`COMP` 区分がログ・監査のもの）が、要件側の責任追跡性（A-6 / NFR-NNN）を満たすか。

### 5. 粒度の侵食が起きていないか
- **下向きの侵食**（本ドキュメントに物理設計が紛れている）: DBMS 固有の型指定・索引・パーティション・DDL・ORM マッピングのいずれかが紛れていないか。紛れていたら「6.3 詳細設計への申し送り」に切り出す。
- **横向きの侵食**（本ドキュメントにインフラ設計が紛れている）: 具体 DBMS 製品名・バージョン・容量見積り・バックアップ方式などが紛れていないか。紛れていたら「6.3 インフラ設計への申し送り」に切り出す。
- **上向きの侵食**（本ドキュメントに要件が紛れている）: 新しい業務ルールや未定義の UC が発生していないか。発生していたら、要件定義書側の更新候補として「6.1 リスク・懸念点」に記録し、要件側との同期方針を明記する。
- **空洞化**: 論理モデル粒度で決めるべき話（キー方針・削除方針・履歴方針・参照整合性）が「詳細設計で決める」に丸投げされていないか。ここで決め切る。

### 6. 図と表の整合
- `erDiagram` に登場するエンティティが、すべて「2. エンティティ一覧」に存在するか。
- `erDiagram` に描かれた関連が、すべて「4. 関連図」の関連表（`REL-NNN`）に存在するか。
- `stateDiagram-v2` に登場する状態が、対象エンティティの属性一覧の列挙値として存在するか。
- 図にだけあり表にないもの、表にだけあり図にないものがないか。
