# HCD / UI・UX 設計の作成
要件定義書を主入力として、基本設計のインタフェース設計に先立つ HCD（人間中心設計）／ UI・UX 設計書を作成してください。

## Goal
ユーザーが**迷わず・効率よく・ストレスなく**目的を達成できる体験を、インタフェース設計（画面項目・API 契約）の上流として**論理レベルで**整理する。

「論理レベル」とは、各体験設計項目について「誰が」「何の状況で」「何を成し遂げたくて」「どういう手順をたどり」「どこで迷い・間違い・困るか」「どう気付き・どう回復するか」までが、要件定義書（`UC-NNN` / `BRU-NNN` / 非機能要件の使用性系）と矛盾なく一義に読み取れる状態を指す。逆に、画面のピクセル配置、UI コンポーネント名、文言の最終表現、API の JSON スキーマ、内部クラス構造など、インタフェース設計以降で変わりうる詳細には踏み込まない。判断に迷ったら、要件 ID（`UC-NNN` / `BRU-NNN` / `NFR-NNN`）に紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて注意事項に記録する。

## 位置付け（要件定義・インタフェース設計・詳細設計との関係）
本スキルは `/generate-requirements` の成果物を入力とし、`/generate-interface-design` の出発点となる**体験設計（論理 UX 契約）**を固める。インタフェース設計（`UI-NNN`・`VR-NNN`・`ERR-NNN`）と並列で独立に動くのではなく、**インタフェース設計の上流**として、先に「何のために・どんなユーザーが・どんな手順で」を確定させる位置付けをとる。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - `UC-NNN`（ユースケース）・`BRU-NNN`（業務ルール）・使用性系の `NFR-NNN`（学習容易性・操作効率・エラー耐性・アクセシビリティ・満足度）を、誰がどんな状況で何を達成したいのかという**体験の文脈**に写像する。
  - 各 `usecase.md` の基本／代替／例外フローで登場するアクターの行動を、本ドキュメントのタスクフロー（`FLW-NNN`）として UX 観点で肉付けする。
  - 使用性要件が要件側で弱い／欠けている場合は、本ドキュメントで暗黙前提として扱い、6.1 リスクに記録して要件側への逆流候補とする。
- 下流（インタフェース設計）: `docs/design/interface/interface-design.md`
  - 本ドキュメントの `JOB-NNN`（主タスク）・`FLW-NNN`（タスクフロー）・`UXI-NNN`（UX 課題）・`FB-NNN`（フィードバック設計）・`A11Y-NNN`（アクセシビリティ）は、インタフェース設計で `UI-NNN`（画面・対話）に落とし込まれる際の**根拠**となる。UI 側では個別項目・イベント・バリデーション（`VR-NNN`）・エラーカタログ（`ERR-NNN`）を定義する。
- 下流（詳細設計）: UI レイアウト・配色・余白・タイポグラフィ・マイクロコピー最終表現・アニメーション・UI コンポーネント分割。本ドキュメントでは扱わない。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**体験設計レベル**の話であり、画面項目の詳細定義・API 契約・DB スキーマ・実装技術には踏み込まない。

- ユーザー像（ペルソナ `PER-NNN`）: 役割・目的・知識レベル・利用環境・心理的特性・制約（身体的・認知的・環境的）
- 利用シナリオ（`SCN-NNN`）: いつ・どこで・どんな前後関係で・どんな感情状態でシステムを利用するか
- 主タスク（Jobs-to-be-Done `JOB-NNN`）: 「何を達成したいのか」の粒度でのタスク定義、成功条件、優先順位
- タスクフロー（`FLW-NNN`）: 主タスクを達成するための操作の系列、分岐、迂回、中断・再開
- UX 観点の課題（`UXI-NNN`）: 認知負荷が高い箇所、ミスしやすい操作、分かりにくい表現・遷移、初見ユーザーが迷うポイント
- エラーしにくさ（予防）と回復（救済）の設計方針: 入力補助・確認ステップ・取消可能性・やり直しコスト
- フィードバック設計（`FB-NNN`）: 成功時・失敗時・待機時・進行中の利用者への状態通知方針（モダリティ・粒度・タイミング）
- アクセシビリティ（`A11Y-NNN`）: 視覚・聴覚・運動・認知の多様性への配慮方針（WCAG の考え方を参考に、論理レベルで何を担保するか）
- 操作効率（最小操作回数 / 主要経路の素早さ）と学習容易性（初見での到達可能性）のバランス方針
- 主タスク外の体験（オンボーディング・空状態・完了後の次アクション・離脱時の復帰）

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、体験設計が定まった後の工程で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**インタフェース設計で決める（本ドキュメントでは参照のみ）**
- 画面・対話の具体項目（`UI-NNN` の入力項目・出力項目・イベント一覧）
- バリデーション条件（`VR-NNN`）の具体（必須／形式／値域／業務制約）
- エラーカタログ（`ERR-NNN`）の具体コード・メッセージ分類
- API エンドポイント（`API-NNN`）・システム間連携（`SIF-NNN`）
- 画面遷移の完全網羅（本ドキュメントでは主タスクのフローのみ扱う）

**詳細設計（画面単位）で決める**
- UI レイアウト詳細（配色・余白・フォント・コンポーネント分割・アイコン）
- マイクロコピーの最終表現・トーン＆マナー・文言の文字数調整
- アニメーション・トランジションの曲線・秒数
- レスポンシブの具体ブレークポイント
- UI コンポーネントライブラリの選定とコンポーネント命名

**データ設計・コンポーネント設計・インフラ設計で決める**
- エンティティ・属性・PK / FK（データ設計）
- 実装クラス構造・DI 構成（コンポーネント設計・詳細設計）
- 物理ネットワーク・ランタイム選定（インフラ設計）

**要件定義で決まり済み（本ドキュメントでは再決定しない）**
- `UC-NNN` の追加・削除・主成功シナリオの再定義（必要なときは要件側に戻る）
- `BRU-NNN`（業務ルール）の変更
- 使用性以外の非機能要件（応答性能・可用性・セキュリティ等）

例外: 上記に属する項目でも、体験設計判断に直結する場合（例: 「要件側で高齢者利用を前提としていないが、実ユーザーの 3 割が高齢者であるため、アクセシビリティ方針を前提として明示する」「要件側では応答性能 2 秒以内と定めているが、ユーザーの期待値が 0.5 秒であり体感上のフィードバック設計が必要」）は、前提として最小限言及する。ただし要件そのものの改変は要件側に差し戻す。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。特に `functional.md` のユースケース概要・「5. アクターがCRUDする情報」、各 `usecase.md` の基本／代替／例外フロー、`non-functional.md` の使用性系（学習容易性・操作効率・エラー耐性・アクセシビリティ・満足度）。
- 追加で $ARGUMENTS にファイルパス・テキスト・既存 UX リサーチ結果・ユーザーインタビュー記録・競合サービスの観察メモが渡された場合はそれを併用する。
- 上流ドキュメントが存在しない場合は、入力で与えられた素材から暗黙的にペルソナ・シナリオを抽出したうえで、設計判断の根拠を明示する（抽出した暗黙前提は「6. 注意事項」の「前提の脆さ」として記載する）。
- 実ユーザー観察・ユーザビリティテスト結果が存在しない場合は「仮説ベース」であることを明記し、6.1 リスクで「検証必要」として扱う。

## 出力ファイル
- `docs/design/uiux/uiux-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: HCD / UI・UX 設計は「ペルソナ → シナリオ → タスク → フロー → 課題 → 改善方針」が 1 本の動線として辻褄を合わせることが最重要であるため。個別画面の詳細 UI 仕様は、インタフェース設計・詳細設計工程で画面単位の別ファイルに展開し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体方針 → 誰が → どんな状況で → 何を → どう操作し → どこで困り → どう解決するか → 横串品質」の順に理解できるよう意図しているため、固定する。

1. UX 設計方針
2. ペルソナ定義
3. 利用シナリオ
4. 主タスク（Jobs-to-be-Done）
5. タスクフロー
6. UX 課題と改善方針
7. フィードバック設計
8. アクセシビリティ方針
9. 注意事項

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/uiux-template.md`](templates/uiux-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. UX 設計方針
- 本 UX 設計全体を貫く方針を、箇条書きで 5〜8 点程度にまとめる。体験設計レベルの判断のみを扱い、具体の UI コンポーネント・配色・文言・フレームワークには踏み込まない。
- 典型的に書くべき方針:
  - **対象ユーザーの幅**: 初見ユーザー優先 / 習熟ユーザー優先 / 両立のいずれを取るか。両立する場合の「初見では安全側の既定値 → 習熟者はショートカットで短縮」等の階層化方針。紐付く `NFR-NNN`（学習容易性・操作効率）を明記。
  - **操作効率の基準**: 主要タスクの最小操作回数の目安、主要経路で画面遷移を何段までに抑えるかの目安。目安の根拠（競合比較・業務現場観察・要件ID）を添える。
  - **エラー耐性の方針**: 「ミスが起きない設計」（入力補助・制約 UI・確認ステップ）と「ミスしても被害が小さい設計」（取消・やり直し・履歴）のバランス。金銭・法務・安全に関わる操作は後者を必須とする。
  - **フィードバック原則**: 応答時間別のフィードバック設計（瞬時 / 短時間 / 長時間 / 非同期）、成功・失敗・進行中の伝達モダリティ（視覚 / 聴覚 / 触覚）の使い分け方針。
  - **アクセシビリティ水準**: WCAG 的な考え方で「何レベル相当を論理的に担保するか」（A 相当 / AA 相当 等の表現で）。画面詳細（コントラスト比の具体値等）はインタフェース設計・詳細設計に回す。
  - **マルチチャネルの扱い**: 画面・CLI・音声・チャット・帳票・通知のうち、本システムで同一タスクを複数チャネルで提供するか、どのチャネルを主としどれを補助とするか。紐付く `UC-NNN` を明記。
  - **体験の一貫性**: タスク間で操作語彙・遷移原則・フィードバック様式を揃える方針（例: 「取消は常に戻るボタンで左上」「破壊的操作は必ず確認を挟む」といった**原則レベル**の話）。
  - **認知負荷の上限**: 1 画面 / 1 ステップで扱う情報量・選択肢数の上限目安。超える場合の分割・段階化方針。
- 「流行っているから」「競合がやっているから」で済ませず、要件 ID または観察事実に紐付けて正当化する。紐付かない方針は記載しない。

### 2. ペルソナ定義
本章はタスク・フロー・UX 課題を検討する際の前提人物像を固定するためのものである。抽象的な「ユーザー」では議論が発散するので、具体像を固定する。

- 採用するペルソナを `PER-NNN` として表形式で列挙する。列:
  - `PER-NNN / 呼称 / 役割・属性 / 目的 / 業務・生活の文脈 / 利用頻度 / 前提知識・習熟度 / 利用環境（デバイス / 場所 / 時間帯 / ネットワーク）/ 身体的・認知的特性 / 心理的特性・動機 / 主な関連 UC / 主な関連 NFR`
- ペルソナは通常 2〜5 人程度。1 人だと多様性を見落とし、多すぎると焦点がぼける。
- **プライマリペルソナ**（主たる設計対象）と**セカンダリペルソナ**（主ターゲットではないが配慮する対象）を区別する。プライマリは 1〜2 人に絞る。
- **ネガティブペルソナ**（本システムの対象外と明示する層）がある場合は記録する。対象外としたことの根拠を `UC-NNN` / `NFR-NNN` に紐付ける。
- 各ペルソナは「なぜこの像を採用したか」を 1〜2 文で補足する（要件側のアクター定義と重なる場合は出典を示し、要件側にない像は観察・リサーチ・仮説の別を明記）。
- 架空の細部（氏名・顔写真・趣味）は最小限にし、設計判断に影響しない情報で紙面を埋めない。影響する情報のみを載せる。

### 3. 利用シナリオ
本章は「ペルソナがどんな状況でシステムと関わるか」の具体文脈を固定する章である。シナリオが曖昧だと、タスク・フローの議論が「よくあるパターン」に寄ってしまい、本当に辛い場面を見落とす。

- 採用するシナリオを `SCN-NNN` として表形式で列挙する。列:
  - `SCN-NNN / 名称 / 関連 PER-NNN / トリガ（何が起きて使い始めるか） / 前後の業務・生活 / 環境制約（手が離せない・時間がない・周囲に人がいる 等） / 感情状態（焦り・疲労・集中 等） / 関連 UC-NNN / 頻度 / 重要度`
- シナリオはハッピーパスだけでなく、「典型的に辛い状況」を必ず 1〜2 本含める（例: 「締切直前で焦っている」「現場で片手しか使えない」「高齢利用者が初見で使う」）。辛い状況を起点にタスク・フローを検証すると、UX 課題が先回りで見つかる。
- シナリオの「ナラティブ」（物語文）は、設計判断に影響する細部のみを含む短い段落とする。小説化しない。
- 各シナリオは 1 つ以上の `PER-NNN` と、1 つ以上の `UC-NNN` に紐付くことを確認する。紐付かないシナリオは、要件側の抜けかシナリオ自体の過剰かのいずれかなので、6.1 リスクに記録する。

### 4. 主タスク（Jobs-to-be-Done）
本章は「ペルソナがシステムを使って本質的に何を達成したいか」を、操作手順より上の粒度で固定する章である。ユースケース（`UC-NNN`）が「システム視点で何が起きるか」であるのに対し、JOB はユーザー視点で「何を成し遂げたいか」である。両者は重なるが視点が異なる。

- 採用する主タスクを `JOB-NNN` として表形式で列挙する。列:
  - `JOB-NNN / タスク名 / 関連 PER-NNN / 関連 SCN-NNN / 関連 UC-NNN / 目的（何を達成したいか） / 成功条件（達成した状態） / 失敗の顕在化（達成できないとき何が起きるか） / 頻度 / 優先度 / 時間制約（どの程度の時間で終えたいか）`
- タスクの粒度は「ユーザーが 1 回の利用セッションで達成したいまとまり」。細かすぎる操作単位（クリック・入力）はここで扱わない（フロー側で扱う）。
- 優先度は `NFR-NNN`（特に操作効率・学習容易性）の要求強度と、頻度・重要度を掛け合わせて決める。優先度の高い JOB は、後続のフロー設計・UX 課題検討で重点的に磨き込む対象になる。
- 1 つの JOB に対し、代替達成手段（別のチャネルやフロー）がある場合は、主経路と代替経路の位置付けを補足する（例: 「主経路は画面、代替は CSV インポート」「主経路は Web 画面、代替は電話で問い合わせ」）。
- JOB は `UC-NNN` と 1:1 とは限らない（1 JOB が複数 UC を横断する / 1 UC が複数 JOB を包含する）。対応関係を明示し、紐付かない JOB や UC は 6.1 リスクに記録する。

### 5. タスクフロー
本章は `JOB-NNN` ごとの操作系列を論理フローとして固定する章である。画面のピクセル配置・UI コンポーネント名・入力フィールド名は扱わない。あくまで「何を・どの順で・どう分岐して・どう終える」のレベル。

- 採用するフローを `FLW-NNN` として記述する。フローは JOB ごとに 1 つ以上。主フロー（ハッピーパス）と、重要な代替・例外フローを分けて書く。
- 各フローの記述要素:
  - `FLW-NNN`・名称・対応する `JOB-NNN`・関連 `UC-NNN`・起点（何がきっかけで始まるか）・終点（何をもって終わったとするか）・中断再開可能性（途中で離脱したあと続きから再開できるか、やり直しになるか）・想定操作回数・想定所要時間。
  - ステップは箇条書き or 表で列挙。各ステップに「ユーザーの意図」「システムが提供する情報／選択肢」「ユーザーの入力・選択」「システムの応答・フィードバック」を対にして書く。
- フローは **Mermaid `flowchart`** で 1 枚描く。分岐（条件）・ループ（繰り返し）・非同期待ち・離脱点を明示する。粒度はステップ単位で、UI コンポーネントまで降りない。
- 複雑な対話（例: 複数画面をまたぐウィザード、中断を挟むフロー）は **Mermaid `sequenceDiagram`** でユーザーとシステムのやり取りを時系列で描いてもよい。
- フローの**操作回数**と**想定所要時間**を必ず記録する。1 章の「操作効率の基準」と整合しない場合は、6.1 リスクに記録する（フローが目標効率を侵食する兆候）。
- 代替・例外フローとして必ず検討する観点:
  - **空状態**: データが存在しない・初回起動時の振る舞い。何を見せ、次に何を促すか。
  - **誤操作からの復帰**: 戻る・取消・やり直しの到達手順。やり直しコストの大きさ。
  - **中断と再開**: 通信切断・端末スリープ・業務割り込みからの復帰。入力内容の保全方針。
  - **長時間待機**: 応答時間が体感上長い処理での待機中の体験。途中キャンセル可否。
  - **失敗からの回復**: システム側の失敗・外部連携失敗・権限不足などに遭遇したときの次の手。誰に・何を相談すればよいか。

### 6. UX 課題と改善方針
本章は現行フローに内在するリスクと、改善方針を整理する章である。具体の UI 変更（配色・文言・ボタン配置）ではなく、「**何を解決したいか**」と「**どの方向で解決するか**」の論理レベルで書く。

- 採用する課題を `UXI-NNN` として表形式で列挙する。列:
  - `UXI-NNN / カテゴリ / 内容（現状どう困るか） / 関連 FLW-NNN / 関連 JOB-NNN / 関連 PER-NNN / 影響範囲 / 発生頻度 / 重要度 / 検出根拠（観察・仮説・競合比較） / 改善方針 / 期待効果 / インタフェース設計への申し送り`
- カテゴリ:
  - **認知負荷**: 情報量・選択肢数が多すぎる、用語が専門的すぎる、画面の意味が読み取れない
  - **操作ミス**: 誤タップ・誤入力を誘発する配置、類似選択肢の混同、破壊的操作の近接
  - **遷移の分かりにくさ**: どこに行けば良いか分からない、戻り方が不明、現在地が不明
  - **待ち時間の不安**: 進捗が見えない、終わったのか続行中なのか不明
  - **初見ユーザーの迷い**: 空状態での次の一手が分からない、専門用語で躓く、何ができるシステムかが伝わらない
  - **反復操作の非効率**: 慣れたユーザーがショートカットを持てない、同じ情報を何度も入力させる
  - **離脱・再訪時のコスト**: 中断後の続きから再開できない、再ログイン・再選択コストが高い
  - **アクセシビリティの欠落**: キーボード操作不可、代替テキスト不在、色のみで意味を伝える
- **改善方針は手段ではなく方向**で書く。「赤いボタンを緑にする」ではなく「破壊的操作と肯定操作を視覚的に区別する」。具体の色・文言はインタフェース設計・詳細設計で決める。
- 各課題には**発生頻度** × **影響範囲** × **重要度**で重要度を評価し、優先的に解決すべきものを明らかにする。重要度の高いものは 6.1 リスクでも追跡する。
- 課題の**検出根拠**を必ず明示する。実ユーザー観察・ユーザビリティテスト結果があればそれを、無ければ「仮説」「専門家による経験的推測」「競合サービス比較」の別を明記する。仮説ベースのものは 6.1 で「検証必要」扱いにする。

### 7. フィードバック設計
本章はシステムがユーザーに対して「いま何が起きているか」「結果はどうだったか」を伝える方針を固定する章である。具体の UI コンポーネント（トースト / モーダル / バナー）や文言はインタフェース設計・詳細設計で決めるため、ここでは**応答時間区分・モダリティ・粒度・タイミング**の方針までに留める。

- 採用するフィードバック方針を `FB-NNN` として表形式で列挙する。列:
  - `FB-NNN / 対象状況（成功 / 失敗 / 進行中 / 待機 / 未着手 / 破壊的操作前） / 応答時間区分（瞬時 < 0.1s / 短時間 < 1s / 長時間 > 1s / 非同期 / 超長時間） / モダリティ（視覚 / 聴覚 / 触覚 / 複合） / 粒度（軽微な通知 / 明示的な確認 / ブロッキング） / タイミング（即時 / 処理後 / 定期） / 関連 FLW-NNN / 関連 UXI-NNN / 方針`
- 応答時間区分ごとに最低限決めること:
  - **瞬時（0.1 秒未満）**: 無反応と区別できる最小のフィードバック（ボタン押下の視覚反応等）。省略すると「壊れている」と誤認される。
  - **短時間（0.1〜1 秒）**: 処理中であることの暗黙的な伝達。スピナー相当。
  - **長時間（1 秒超）**: 進捗の見える化、現時点での達成度、キャンセル可否。
  - **非同期（数分以上の処理）**: 完了通知の別経路（メール・通知センター等の**方針**）、途中状態の確認手段。
  - **超長時間（数時間〜日単位）**: ジョブキューの状態確認・再実行・取消の**方針**（具体経路はインタフェース設計で）。
- **成功フィードバック**: 静かに済ます（サイレント）か、明示的に祝うか。破壊的でない操作は前者、決済・申請・同意など取り消しコストが高い操作は後者が典型。
- **失敗フィードバック**: 何が起きたか・ユーザーが次に何をすべきか・問い合わせ先を含める方針。責任をユーザーに帰さない書き方の方針（「入力が間違っています」ではなく「〜の形式で入力してください」）。
- **破壊的操作前の確認**: 取消不可・金銭・個人情報・他者影響のある操作は、必ず確認ステップを挟む方針。確認の強度（軽確認 / 再入力 / 二要素 / 時間差）は操作の影響度で段階化。
- フィードバックは 1 章の「体験の一貫性」に従い、同じ種類の状況には同じ種類のフィードバックを与える。

### 8. アクセシビリティ方針
本章はアクセシビリティに関する**論理レベルの担保方針**を固定する章である。具体の色コントラスト比・フォーカスリング太さ・ARIA 属性の値はインタフェース設計・詳細設計で決めるため、ここでは「何を担保するか」「どの利用者層を想定するか」の方針に留める。

- 採用する方針を `A11Y-NNN` として表形式で列挙する。列:
  - `A11Y-NNN / 対象（視覚 / 聴覚 / 運動 / 認知 / 一時的・状況的制約） / 担保したい操作・理解 / 方針（どう担保するか） / 関連 FLW-NNN / 関連 UXI-NNN / 関連 NFR-NNN / 関連 WCAG 原則（参考）`
- 最低限整理する観点:
  - **視覚**: スクリーンリーダー対応、色のみで意味を伝えない、拡大表示耐性、コントラスト方針、動き・点滅の制御
  - **聴覚**: 音声情報に対する代替手段（字幕・テキスト）、通知音への依存排除
  - **運動**: キーボードのみでの操作到達、ポインタ精度に頼らないタップ領域、タイムアウトの延長・無効化
  - **認知**: 用語の平易さ、手順の段階化、取消・やり直し、一貫性、集中を妨げる動きの抑制
  - **一時的・状況的制約**: 片手操作、明るい屋外、騒音環境、低速回線、小画面、高齢による読み取り低下
- WCAG の考え方（知覚可能 / 操作可能 / 理解可能 / 堅牢）を参考にして整理するが、本ドキュメントは**論理設計**のレベルなので、具体数値（コントラスト比・フォントサイズ最小値）は詳細設計に申し送る。
- アクセシビリティ方針は主タスクの `JOB-NNN` と関連 `FLW-NNN` すべてに対して適用対象か否かを明示する。「この JOB は対象外」とする場合、その根拠を `UC-NNN` / `NFR-NNN` と紐付けて記録する（対象外を残す場合は 6.1 リスクに連動）。
- 要件側の非機能要件にアクセシビリティが未記載の場合、本ドキュメントの方針を要件側に逆流させる候補として 6.3 に記録する。

#### 9.2 代替案と採らない理由
- 主要な体験設計判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`。
- 最低でも以下の論点については検討の痕跡を残すことを推奨する。該当しなければ「検討不要と判断した理由」を 1 行で記す。
  - **対象ユーザーの幅**: 初見ユーザー優先 vs 習熟ユーザー優先 vs 両立
  - **主タスクの粒度**: 細かいタスクを多数 vs 大きなタスクを少数
  - **フロー分岐戦略**: 1 経路に統一 vs 状況別に複数経路を並列提供
  - **中断再開の扱い**: 途中状態を保全し再開可 vs 完了しなければ破棄
  - **破壊的操作の確認強度**: 軽確認のみ vs 多段確認（再入力・時間差・二要素）
  - **フィードバック様式**: サイレント優先 vs 明示的な成功表現を都度
  - **アクセシビリティ水準**: A 相当 vs AA 相当 vs AAA 相当
  - **マルチチャネル**: 同一タスクを複数チャネルで提供 vs 主チャネル 1 本に集約
- インタフェース設計寄りの判断（具体項目・バリデーション条件・エラーコード）は本章では取り上げず、インタフェース設計の代替案検討で扱う。詳細設計寄りの判断（配色・文言・コンポーネント）も本章では取り上げない。

## 図解の記法ルール
要件定義書・アーキテクチャ設計書・データ設計書・インタフェース設計書と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。

- タスクフロー図: `flowchart`
  - 各ステップをノードとし、分岐・ループ・離脱点を明示する。粒度はステップ単位で、UI コンポーネント・ボタン名まで降りない。
  - 主フローと代替・例外フローを色分けまたは `subgraph` で区別する。
- ユーザーとシステムの対話: `sequenceDiagram`
  - 複雑な対話（ウィザード・中断再開・非同期完了通知）を時系列で描くときに使う。
  - `participant` は「ユーザー」「システム」「外部通知」など役割単位で、内部モジュールまで降りない。
- ペルソナ・シナリオの関係整理: 必要なら `flowchart` や表形式で十分。無理に図にしない。
- カスタマージャーニーマップ相当（感情曲線込み）を描く場合: Mermaid `journey` を任意で利用可。ただし本ドキュメントでは必須ではなく、シナリオ章のナラティブで十分表現できるなら図を増やさない。

### 1. ペルソナとシナリオの具体性
- `PER-NNN` は具体的で、設計判断に影響する特性（知識レベル・利用環境・身体的特性・心理的動機）が書かれているか。架空の細部で埋めていないか。
- プライマリペルソナが 1〜2 人に絞れているか（多すぎると意思決定の軸がぼける）。
- `SCN-NNN` にハッピーパスだけでなく「辛い状況」が 1 本以上含まれているか。
- 各 `SCN-NNN` が `PER-NNN` と `UC-NNN` の両方に紐付いているか。

### 2. タスクとフローの網羅性
- すべての `JOB-NNN` が `PER-NNN` ・ `SCN-NNN` ・ `UC-NNN` に紐付いているか。
- 優先度の高い `JOB-NNN` について、主フローと代替・例外フロー（空状態・中断再開・失敗回復・長時間待機）の検討がなされているか。
- `FLW-NNN` の想定操作回数・所要時間が、1 章で宣言した「操作効率の基準」と整合しているか。
- すべての `UC-NNN` が、1 つ以上の `JOB-NNN` または `FLW-NNN` でカバーされているか。

### 3. UX 課題と改善方針の品質
- `UXI-NNN` の検出根拠が明示されているか（観察・テスト・仮説・競合比較の別）。
- 改善方針が「手段（具体 UI 変更）」ではなく「方向（解決したい体験の性質）」で書かれているか。
- 重要度の高い `UXI-NNN` が 9.1 リスクでも追跡されているか。
- 仮説ベースの `UXI-NNN` は 9.1 で「検証必要」扱いになっているか。

### 4. フィードバックとアクセシビリティ
- `FB-NNN` が応答時間区分ごとに網羅されているか（瞬時 / 短時間 / 長時間 / 非同期）。
- 破壊的操作（取消不可・金銭・個人情報・他者影響）について、確認ステップの方針が決まっているか。
- `A11Y-NNN` が視覚・聴覚・運動・認知・状況制約の各観点で整理されているか。
- 対象外とする JOB がある場合、その根拠が `UC-NNN` / `NFR-NNN` に紐付いて明示されているか。

### 5. 粒度の侵食が起きていないか
- **下向きの侵食（インタフェース設計）**: 画面の具体項目・`VR-NNN` の条件・`ERR-NNN` の具体コード・API エンドポイント定義が紛れていないか。紛れていたら「9.3 インタフェース設計への申し送り」に切り出す。
- **下向きの侵食（詳細設計）**: 配色・余白・フォント・コンポーネント名・マイクロコピーの最終文言・アニメーション具体値が紛れていないか。紛れていたら「9.3 詳細設計への申し送り」に切り出す。
- **横向きの侵食（データ設計）**: エンティティ属性・PK / FK が紛れていないか。
- **上向きの侵食（要件定義）**: `UC-NNN` の追加・`BRU-NNN` の変更・非機能要件の改変が黙って発生していないか。発生していたら「9.3 要件定義への逆流候補」に記録する。
- **空洞化**: UX 設計粒度で決めるべき話（ペルソナ・シナリオ・JOB・フロー・UX 課題・フィードバック方針・アクセシビリティ方針）が「インタフェース設計で決める」に丸投げされていないか。ここで決め切る。

### 6. 図と表の整合
- タスクフロー図に登場するステップが、対応する `FLW-NNN` の本文記述と一致しているか。
- `sequenceDiagram` がある場合、participant が `PER-NNN` またはシステム役割と整合しているか。
- 各章の表中の ID が、別章で参照している ID と一致しているか（採番ミスがないか）。
- 1 章で「採用する」と宣言した方針が、2〜8 章の個別記述と矛盾していないか。

### 7. 「誰のために」が通っているか
- 本ドキュメント全体を通して「誰が・どんな状況で・何を達成したいか」が一本の動線で読めるか。
- プライマリペルソナ視点で全章を通読したとき、矛盾や飛躍がないか。
- 最も重要な `JOB-NNN` について、対応する `PER-NNN` ・ `SCN-NNN` ・ `FLW-NNN` ・ `UXI-NNN` ・ `FB-NNN` ・ `A11Y-NNN` が全て揃っているか（1 つの重要 JOB を軸に縦串で追えること）。
