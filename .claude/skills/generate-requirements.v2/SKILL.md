# 要件定義書の作成（小規模開発向け / v2）

## このスキルの位置付け

`generate-requirements`（v1）の網羅性を維持したまま、**小規模開発（ユースケース 10 以下が目安）に必要な項目だけ**を残した軽量版である。v1 は ISO 25010 の 31 副特性をすべて検討させるため、小規模案件では成果物が肥大化しレビューが滞る傾向があった。本 v2 は以下を方針とする:

1. **不足情報は逐次対話で確認する。** 1 項目ずつ「これは必要か？必要なら内容は？」と尋ね、ユーザーは任意の項目を **スキップ** できる。スキップされた項目は成果物に一切記載しない（「該当なし」「TBD」も書かない。**項目自体を削る**）。
2. **項目を絞る。** 小規模で実務的に問われる項目だけを残し、それ以外は省略する。判断に迷ったら「書かない」を選ぶ。
3. **後続設計の要否を判定する。** 機能 / アーキテクチャ / クラス / コンポーネント / データ / HCD / インタフェース / インフラ の 8 設計について、本スキルの中で要否と簡潔な理由を `design-plan.md` に出力する。「とりあえず全部やる」は禁止。

なぜこの方針かというと、小規模案件では「ドキュメントを書く工数」と「ドキュメントを読む工数」の両方が直接的にプロジェクトコストを押し上げるためである。レビュー可能なサイズを保つほうが、抜け漏れの早期発見にも繋がる。

## 入力

$ARGUMENTS

## ワークフロー全体像

```
1. 入力の解釈
2. 必須項目の不足確認（逐次対話）
3. 任意項目の要否確認（逐次対話、スキップ可）
4. functional.md の生成
5. usecase/{UC-NNN}/usecase.md の生成（ユースケースごと）
6. non-functional.md の生成
7. 後続設計の要否判定 → design-plan.md の生成
8. 全体の整合性チェック
```

---

## ステップ 1. 入力の解釈

まず `$ARGUMENTS` を読み、以下を自分なりに抽出する。明示されていなくても文脈から推測できるものは仮置きしてよい（後で確認する）:

- **プロジェクト名 / 通称**
- **背景・目的**（なぜ作るのか）
- **スコープ**（何を含む / 含まない）
- **主要アクター**（誰が使うのか）
- **ざっくりやりたいこと**（暫定ユースケース候補）
- **既知の制約**（既存システム、技術指定、納期など）

このステップでユーザーに確認はしない。次のステップで一括的に確認する。

---

## ステップ 2. 必須項目の不足確認（逐次対話）

以下は **小規模でも省略できない最低限の項目** である。入力に不足がある場合、**1 項目ずつ** ユーザーに質問する。スキップは認めない（これらが揃わないと要件定義書として成立しないため）。

### 必須項目チェックリスト

| # | 項目 | 不足時の質問例 |
|---|---|---|
| 1 | プロジェクトの目的 | 「このプロジェクトで達成したいゴールを一文で教えてください」 |
| 2 | 主要アクター | 「このシステムを使う人 / 連携する外部システムを列挙してください」 |
| 3 | 最低 1 つのユースケース | 「ユーザーがこのシステムで実現したいことを 1 つ以上挙げてください」 |
| 4 | スコープ境界 | 「今回のスコープに含めるもの / 含めないものを教えてください」 |

質問は **AskUserQuestion ツールを使わず、自然文で 1 問ずつ** する。ユーザーが答えるのを待ち、次の質問に進む。理由は、ユーザーが過去の自分の回答を文脈として見ながら考えられるようにするため。

例:

> 「プロジェクトの目的を一文で教えてください。例: 『既存の Excel での顧客管理を Web アプリ化し、リモートでも複数人で同時編集できるようにする』のような粒度で OK です。」

ユーザーから回答が返ったら、次の必須項目の不足を埋めにいく。

---

## ステップ 3. 任意項目の要否確認（逐次対話、スキップ可）

ここから先は **小規模では省略してよい項目** である。**1 項目ずつ** ユーザーに「この項目を含めますか？」と尋ね、答えが得られたら次へ進む。ユーザーは以下のいずれかを返せる:

- **「スキップ」 / 「不要」 / 「なし」**: その項目は成果物から完全に削る
- **内容を直接記述**: その内容で記載する
- **「Claude に任せる」 / 「お任せ」**: 入力から推測した内容を仮置きする

スキップ判断はユーザーの裁量で OK。「迷ったらスキップ」を案内する。

### 任意項目チェックリスト（functional.md 側）

| # | 項目 | 質問例 | スキップ時の扱い |
|---|---|---|---|
| 1 | ステークホルダー定義（アクター以外の関係者） | 「発注者・承認者・運用者など、アクター以外で利害を持つ人を記載しますか？」 | セクションごと削除 |
| 2 | データ定義（ENT-NNN） | 「システムが扱う主要なデータの塊（顧客 / 注文 / 商品 など）を列挙しますか？ ユースケースから明らかなら自動抽出も可能です」 | セクションごと削除 |
| 3 | システム間インタフェース（SIF-NNN） | 「外部システムとの連携はありますか？」 | UI-NNN 以外の IF セクションを削除 |
| 4 | ハードウェアインタフェース（HIF-NNN） | 「プリンタ・スキャナ・IC カードリーダなどの物理機器との接続はありますか？」 | セクション削除 |
| 5 | 通信インタフェース（CIF-NNN） | 「ネットワーク越しの特別な通信要件（VPN、専用線、特定プロトコル等）はありますか？」 | セクション削除 |
| 6 | ビジネスルール（BRU-NNN） | 「『○○のときは△△する』のような業務ルールをまとめておきますか？ ユースケース本文に書ききれる量ならスキップで OK」 | セクション削除 |
| 7 | 用語集 | 「ドメイン固有用語の解説を含めますか？」 | セクション削除 |
| 8 | 参照ドキュメント | 「業務マニュアル・既存システム仕様書など、参照すべき外部資料はありますか？」 | セクション削除 |

### 任意項目チェックリスト（ユースケース詳細側）

ユースケースごとに以下を確認するが、毎回全部を聞くと冗長なので **最初の 1 ユースケース** で方針を決め、以降は同じ方針を適用する（途中でユーザーが「このユースケースは別」と言えば個別対応）。

| # | 項目 | 質問例 | スキップ時の扱い |
|---|---|---|---|
| 1 | 代替フロー | 「ユースケースに分岐（権限による違い、選択肢の違いなど）はありますか？」 | セクション削除 |
| 2 | 例外フロー | 「異常系（入力エラー、外部 API 失敗など）の振る舞いを書きますか？」 | セクション削除 |
| 3 | CRUD 情報表 | 「ユースケースが扱うデータの C/R/U/D を表で整理しますか？ シンプルなら不要」 | セクション削除 |
| 4 | 関連インタフェース | 「ユースケース内で使う画面・外部システム連携を ID で紐付けますか？」 | セクション削除 |
| 5 | 関連ビジネスルール | （BRU を採用した場合のみ）「このユースケースに関連する BRU を紐付けますか？」 | セクション削除 |
| 6 | sequenceDiagram | 「フロー図（Mermaid sequenceDiagram）を添えますか？」 | セクション削除 |
| 7 | stateDiagram | 「状態を持つ対象がある場合、状態遷移図を添えますか？」 | セクション削除 |

### 任意項目チェックリスト（non-functional.md 側）

**v1 の ISO 25010 × 31 副特性は採用しない。** 小規模で実務的に問われる以下のテーマだけを 1 項目ずつ確認する。

| # | テーマ | 質問例 | スキップ時の扱い |
|---|---|---|---|
| 1 | 性能（応答時間 / 同時利用 / データ量） | 「画面応答や同時利用数の目標値はありますか？ 体感で十分です」 | テーマごと削除 |
| 2 | 可用性 | 「稼働時間帯と、許容できる停止時間の目安はありますか？」 | テーマごと削除 |
| 3 | バックアップ・リカバリ | 「バックアップの頻度・保管期間、復旧目標（何時間以内に戻すか）はありますか？」 | テーマごと削除 |
| 4 | セキュリティ（認証 / 認可） | 「ログイン方式、権限の区分はありますか？」 | テーマごと削除 |
| 5 | セキュリティ（データ保護） | 「個人情報や機微データの取り扱い、暗号化要件はありますか？」 | テーマごと削除 |
| 6 | 操作ログ・監査ログ | 「誰が何をしたかの記録を残す必要はありますか？ 保管期間も含めて」 | テーマごと削除 |
| 7 | 対応環境（ブラウザ / OS / デバイス） | 「対応すべきブラウザ・OS・デバイスの指定はありますか？」 | テーマごと削除 |
| 8 | 法令・規格 | 「個人情報保護法、電子帳簿保存法、PCI DSS など、遵守すべき法令・規格はありますか？」 | テーマごと削除 |
| 9 | 移行 | 「既存システムや既存データからの移行はありますか？」 | テーマごと削除 |
| 10 | 運用環境・インフラ制約 | 「稼働環境（オンプレ / クラウド / 特定 OS など）の指定はありますか？」 | テーマごと削除 |

質問の進め方の例:

> 「では非機能要件について確認します。**性能** について、画面応答時間や同時利用数の目標値はありますか？（『3 秒以内』『同時 10 ユーザー』など、体感ベースで OK です。決まっていなければスキップで構いません）」

ユーザーが「スキップ」と答えたら、そのテーマは **non-functional.md に項目自体を書かない**。「該当なし」「TBD」も書かない。

## ステップ 4. functional.md の生成

`docs/requirements/functional.md` を作成する。**スキップされた項目は見出しごと削除する。**

採用された項目だけで構成する基本テンプレ:

```markdown
# 機能要件

## プロジェクト概要
（背景・目的・スコープ）

## ステークホルダー  ← 不採用ならセクションごと削除
（表形式: 役割 / 名前または部署 / 関心事項）

## ユースケース一覧
| UC-NNN | 名称 | 主アクター | 概要 | 詳細 |
|---|---|---|---|---|
| UC-001 | … | … | … | [usecase/UC-001/usecase.md](./usecase/UC-001/usecase.md) |

（必要に応じてアクターとユースケースの関連を flowchart で図示）

## データ定義  ← 不採用なら削除
| ENT-NNN | 名称 | 概要 | 主な保有情報 | 関連UC |

（必要なら erDiagram で関連を図示。多重度のみ。属性は書かない）

## インタフェース要件
### ユーザインタフェース（UI-NNN）  ← UI は基本必須
| UI-NNN | 画面・帳票名 | 種別 | 対象利用者 | 概要 | 関連UC |

共通 UI 要件: 対応デバイス / 対応ブラウザ / 言語 等（決まったものだけ）

### システム間インタフェース（SIF-NNN）  ← 不採用なら削除
（採用時のみ表で記載）

### ハードウェアインタフェース（HIF-NNN）  ← 不採用なら削除
### 通信インタフェース（CIF-NNN）  ← 不採用なら削除

## ビジネスルール  ← 不採用なら削除
## 用語集  ← 不採用なら削除
## 参照ドキュメント  ← 不採用なら削除
```

### 図解ルール

すべての図は Mermaid（````mermaid` コードブロック）で記述する。画像ファイルや drawio などの外部形式は使わない。理由は、テキストとして diff が取れ、レビュー時にコメントしやすいため。

## ステップ 5. ユースケース詳細の生成

ユースケースごとに `docs/requirements/usecase/UC-NNN/usecase.md` を作成する。**スキップされた項目は見出しごと削除する。**

採用された項目だけで構成する基本テンプレ:

```markdown
# UC-NNN: {名称}

## アクター
- 主アクター: …
- 副アクター: …  ← なければ行ごと削除

## 概要・目的

## 事前条件
## 事後条件（成功時 / 失敗時）

## 基本フロー
1. …
2. …

## 代替フロー  ← 不採用なら削除
## 例外フロー  ← 不採用なら削除

## CRUD 情報  ← 不採用なら削除
| ENT-NNN | エンティティ名 | 操作 | 概要 |

## 関連インタフェース  ← 不採用なら削除
- UI-NNN: …（このユースケース内での使い方）
- SIF-NNN: …

## 関連ビジネスルール  ← 不採用なら削除
## 関連非機能要件  ← 該当時のみ（NFR-NNN への参照）

## 補足  ← 任意
```

**設計工程への申し送り事項** は v1 では各 usecase.md に書いていたが、v2 では `design-plan.md` に集約する（ステップ 7 参照）。

---

## ステップ 6. non-functional.md の生成

`docs/requirements/non-functional.md` を作成する。**ステップ 3 でスキップされたテーマは項目自体を書かない。**

採用されたテーマだけを以下のフォーマットで列挙する:

```markdown
# 非機能要件

## NFR-001: 性能 - 画面応答時間
- 内容: 主要画面は通常負荷下で 3 秒以内に応答する
- 根拠: （ヒアリングで合意した内容、または "根拠未確定（要確認: 発注者）"）
- 検証方法: 受け入れ試験で計測
- 関連: UC-001, UC-002
```

### 記述ルール

- 1 要件 = 1 ブロック。ID は NFR-NNN で通し採番。
- 各要件には最低限 **内容 / 根拠 / 検証方法 / 関連** の 4 項目を含める。
- 数値で書けるものは数値で書く（「速い」「大量」のような定性表現は避ける）。決まっていないものは「TBD（決定者: ○○）」と明記する。
- v1 の「該当: A-5 / 可用性」のような ISO 25010 タグは付けない（小規模では追跡コストに見合わないため）。

## ステップ 7. 後続設計の要否判定 → design-plan.md の生成

`docs/requirements/design-plan.md` を作成する。本ファイルは **後工程の設計者（または Claude が `generate-*-design` スキルを呼ぶ判断）** に向けたガイドであり、「どの設計工程を実施し、どれを省略するか」を要件定義の段階で意思決定して残すためのものである。

### 判定の主軸

以下を **基本判定ロジック** とする（ユースケース数を主指標にする理由は、規模感が一目で分かり、ユーザーとの認識合わせがしやすいため）:

| 設計工程 | スキップ判定の目安 | 判定の補助指標 |
|---|---|---|
| 機能設計（generate-functional-design 相当） | ユースケースが極小（3 以下）かつロジック自明な CRUD のみ | ユースケース数 / ロジック複雑度 |
| アーキテクチャ設計（generate-architecture-design） | 単一プロセス・既存テンプレ流用で構成が自明 | コンポーネント数 / 外部連携の有無 |
| コンポーネント設計（generate-component-design） | コンポーネント分割の必要がない（モノリス・単一モジュール） | アーキテクチャ設計の結果に依存 |
| クラス設計（generate-class-design） | 業務ロジックが軽い（バリデーション + CRUD 主体） | ドメインロジックの重さ |
| データ設計（generate-data-design） | ENT が 3 以下かつ関連が単純 | エンティティ数 / 関連の複雑度 |
| HCD / UI/UX 設計（generate-hcd-uiux-design） | 単一ペルソナ・定型業務・社内利用 | アクター数 / ユーザー多様性 |
| インタフェース設計（generate-interface-design） | UI のみ・外部連携なし | SIF/HIF/CIF の有無 |
| インフラ設計（generate-infrastructure-design） | 既存環境流用・小規模・SLA 要件軽微 | 可用性要件 / 利用規模 |

**ユースケース数 10 以下** は小規模の目安であり、すべての設計工程を機械的に実施する必要はない。ただし機械的に判定するのではなく、上の補助指標を踏まえてユーザーと相談する。

### ユーザー確認

判定結果をユーザーに提示し、**設計工程ごとに 1 行コメントで合意を取る**。やり方は前ステップ同様、AskUserQuestion ではなく自然文の対話で十分。

例:

> 「後続設計の要否を以下のように判定しました。違うものがあれば指摘してください。
>
> - 機能設計: **実施推奨**（ユースケース 6 件、業務分岐あり）
> - アーキテクチャ設計: **簡略実施**（フロント + API + DB の 3 層が自明だが、外部連携 1 件があるため境界を明記）
> - コンポーネント設計: **スキップ**（モノリスで分割なし）
> - クラス設計: **スキップ**（CRUD 主体、ドメインロジック軽微）
> - データ設計: **実施推奨**（ENT 5 件、関連あり）
> - HCD/UIUX 設計: **簡略実施**（社内 2 ペルソナ、画面フローの確認のみ）
> - インタフェース設計: **実施推奨**（外部 API 連携 1 件、UI 8 件）
> - インフラ設計: **スキップ**（既存 AWS 環境流用、SLA 要件は社内基準のみ）」

### design-plan.md のフォーマット

```markdown
# 後続設計プラン

要件定義の結果に基づき、以降の設計工程の実施可否を以下のように判定する。各工程は必要最低限の粒度で実施する。

## 規模感サマリ
- ユースケース数: N
- エンティティ数: N（採用していない場合は「未定義」）
- 外部システム連携: あり / なし
- 想定アクター数: N
- 主要な非機能制約: （箇条書きで 1-3 件）

## 設計工程の要否
| 工程 | 判定 | 理由 | 想定の深さ |
|---|---|---|---|
| 機能設計 | 実施 / 簡略 / スキップ | … | フル / 部分 / - |
| アーキテクチャ設計 | … | … | … |
| コンポーネント設計 | … | … | … |
| クラス設計 | … | … | … |
| データ設計 | … | … | … |
| HCD / UI/UX 設計 | … | … | … |
| インタフェース設計 | … | … | … |
```

成果物を出力したら、最後に以下を自己点検する:

## 記述上の指針（v2 共通）

### 明確性
- 一文一意。「等」「など」「適切に」「必要に応じて」は使わない。
- 主語・動詞を省略しない。

### 簡潔性（v2 で強化）
- 小規模案件では「書かなくても伝わる」内容はあえて書かない。書くと読み手の認知負荷が増え、本当に重要な要件が埋もれる。
- 同じことを 2 箇所に書かない（DRY）。1 箇所に書き、他は ID で参照する。
- ステークホルダー、用語集、ビジネスルール、参照ドキュメントは「本当に他者に共有する価値があるか？」を一度自問してから書く。

### 検証可能性
- 各機能・非機能要件には「どうなったら満たされたか」を 1 行で書ける程度に具体化する。書けないなら定量化または分割し直す。

### 暗黙要件の扱い（v1 との差分）
v1 では「入力に明示されていなくても通常想定される要件は暗黙要件として追加」していたが、**v2 ではユーザーがスキップした項目を勝手に追加しない**。スキップは明示的な意思決定として尊重する。ただし、ステップ 3 のチェックリストに従って **一度は質問する** こと（聞きもせず黙って省略するのは禁止）。

## 出力ファイル一覧（採用項目によって変動）

確定で生成するもの:
- `docs/requirements/functional.md`
- `docs/requirements/usecase/UC-NNN/usecase.md`（ユースケース数ぶん）
- `docs/requirements/non-functional.md`（採用項目が 0 件ならこのファイル自体を作らない）
- `docs/requirements/design-plan.md`

不採用項目の扱い:
- 章ごとスキップ → 見出しごと削除
- ファイル全体が空になる場合 → そのファイルを作らない

新規ユースケース追加時は、既存ファイルを変更せず `usecase/UC-NNN/` を新規作成するだけで拡張できるようにする（v1 と同じ方針）。
