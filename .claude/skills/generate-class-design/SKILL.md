# クラス設計の作成
要件定義書・アーキテクチャ設計書・データ設計書・インタフェース設計書・コンポーネント設計書を入力として、詳細設計の起点となるクラス設計書を作成してください。

## Goal
コンポーネント設計で決定された `MOD-NNN` の内部構造を、**業務ロジックが宿る場所と、そこで守られる不変条件を一義に読み取れるクラス構造**として示す。

「業務ロジックが宿る場所と不変条件を一義に読み取れる」とは、各クラスが「何の責務を負い」「どんな状態（属性）を保ち」「どんな操作を提供し」「どの他クラスと協調し」「どの条件を常に満たすか」が、クラス名と責務記述から揃って読み取れ、業務ルール（`BRU-NNN`）や整合性ルール（`RULE-NNN`）の実装位置が特定できる状態を指す。逆に、言語固有構文・フレームワーク機構・DI コンテナ具体構成・ORM マッピング・命名規則といった実装工程で変わりうる詳細には踏み込まない。判断に迷ったら、要件 ID（`UC-NNN` / `NFR-NNN` / `BRU-NNN`）・構成要素 ID（`COMP-NNN` / `MOD-NNN` / `LYR-NNN`）・エンティティ ID（`ENT-NNN` / `RULE-NNN`）・インタフェース ID（`API-NNN` / `UI-NNN` / `SIF-NNN` / `ERR-NNN` / `VR-NNN`）のいずれかに紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて注意事項に記録する。

## 位置付け（要件定義・アーキテクチャ設計・データ設計・インタフェース設計・コンポーネント設計・詳細設計との関係）
本スキルは `/generate-requirements`、`/generate-architecture-design`、`/generate-data-design`、`/generate-interface-design`、`/generate-component-design` の成果物をすべて入力とし、詳細設計・実装の直前段階となる**論理クラス構造**を固める。コンポーネント設計で「どのモジュールが何を引き受けるか」を決めたのに続き、本スキルは「そのモジュールの内部で、責務と状態をどのクラスに配るか」「業務不変条件を誰が守るか」を決める。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 業務ルール（`BRU-NNN`）はクラスの操作・不変条件として実装される。ユースケース（`UC-NNN`）の基本／代替／例外フローは、代表シーケンス図の起点候補になる。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - `COMP-NNN` は所属モジュールの外殻として、`LNK-NNN` は「クラスから見たときに相手側がどの COMP にあるか」を追跡する根拠として使う。
- 上流（データ）: `docs/design/data/data-design.md`
  - `ENT-NNN` はエンティティクラス・値オブジェクト・集約の素材となる。属性・論理型・PK/UK はクラスの属性と識別子設計に引き継ぐ。`RULE-NNN` はクラス / 集約 / 横断の不変条件（`INV-NNN`）として再表現される。
- 上流（インタフェース）: `docs/design/interface/interface-design.md`
  - `API-NNN` のハンドラ責務はアプリケーションサービスクラス等の操作に落ちる。`VR-NNN` のうち業務正当性に関わるものはクラスの不変条件・事前条件として実装される。`ERR-NNN` はクラスが生成・変換・通過させる例外として対応付けられる。
- 上流（コンポーネント）: `docs/design/component/component-design.md`
  - `MOD-NNN` は各 `CLS-NNN` の所属先となる。`LYR-NNN` はクラスの配置層を決める。`DEP-NNN`（モジュール間依存）は、クラス間関連（`ASSOC-NNN`）に展開される根拠となる。**新しい `MOD-NNN` を本ドキュメントで追加しない**（必要ならコンポーネント設計側に戻って追加する）。
- 下流（詳細設計）: 言語固有型の具体化、フレームワーク機構（アノテーション・デコレータ・DI）の適用、ORM マッピング・リポジトリ実装の詳細、例外階層の具体、単体テストのモック戦略、ディレクトリ・パッケージ命名規則の具体。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**論理クラス構造レベル**の話であり、言語・フレームワーク・ライブラリ固有の機構には踏み込まない。

- クラスの洗い出し（`MOD-NNN` 内部をクラス粒度に分解する）
- 各クラスの**ステレオタイプ**（エンティティ / 値オブジェクト / 集約ルート / ドメインサービス / アプリケーションサービス / リポジトリ / ファクトリ / ポリシー（仕様） / アダプタ / DTO 等）
- 各クラスの責務（引き受けること / 引き受けないこと）
- 属性（名称・論理型・可視性・可変／不変・初期値制約）
- 操作（名称・引数の論理型・戻り値の論理型・可視性・事前条件・事後条件・生成／変換／通過させる例外）
- クラス間関連（`ASSOC-NNN`）: 方向・多重度・関連種別（関連／合成／継承／実現／依存）・ライフサイクル依存
- 集約（`AGG-NNN`）: 集約ルートの識別・集約に含まれるクラス・外部から直接参照可能な範囲・トランザクション境界の意味
- 不変条件（`INV-NNN`）: クラス内 / 集約内 / 集約横断のいずれの範囲で成り立つか・維持責任者・違反時の扱い
- 可変性原則（値オブジェクトは不変・エンティティは識別子で同一性保持）
- 生成・破棄（コンストラクタ引数・ファクトリ経由・DI による注入の「種別」）
- `ENT-NNN` とクラスのマッピング（1 ENT を 1 クラスにするか、エンティティ + 値オブジェクトに分けるか）
- `BRU-NNN` / `RULE-NNN` / `VR-NNN` のうち、どれをクラス側で実装するかの割り当て
- `ERR-NNN` の生成元クラス・変換を行うクラス・通過経路

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、クラス構造が定まった後の工程で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**詳細設計・実装で決める**
- 言語固有の型指定（`String` / `string` / `str`、`BigDecimal` / `decimal.Decimal` / `Number` 等）
- フレームワーク固有機構の適用（`@Service` / `@Entity` / `@Component` / デコレータ / ミドルウェアフック）
- DI コンテナの具体構成・スコープ・初期化順序
- ORM マッピング（カラム名対応・リレーション定義・フェッチ戦略）
- ディレクトリ・パッケージ命名規則の具体（`com.example.domain.order` 等）
- 例外階層の具体クラス名・継承関係
- ログメッセージ文面・バリデーションメッセージ文面の最終形
- 単体テスト分割・モック戦略・フィクスチャ設計
- 可視性修飾子の具体（`public` / `internal` / `package-private` / `protected` の言語別差分の扱い）
- Getter / Setter の具体（原則 Setter を持たない方針は決めるが、言語別の記法は決めない）

**UI 設計・インフラ設計で決める**
- UI レイアウト・具体の画面部品配置（`UI-NNN` のインタフェース設計で決定済み）
- コンテナ / プロセス集約・デプロイ単位（インフラ設計で決定）
- DB 物理実装（テーブル物理名・索引・パーティション・SQL・プロシージャ。詳細設計・インフラ設計）

**コンポーネント設計で決まり済み（本ドキュメントでは再決定しない）**
- `MOD-NNN` の追加・削除・責務の再定義（必要なときはコンポーネント設計側に戻る）
- `LYR-NNN` の定義・層の追加削除
- `DEP-NNN` の依存種別の再選定（`ASSOC-NNN` は `DEP-NNN` の内部展開として整合させる）

**データ設計・インタフェース設計・アーキテクチャ設計で決まり済み**
- `ENT-NNN` の属性・キー・削除方針・履歴方針
- `RULE-NNN` の制約内容
- `API-NNN` / `UI-NNN` / `SIF-NNN` の入出力項目・プロトコル
- `VR-NNN` のバリデーション条件・`ERR-NNN` のエラーカタログ
- `COMP-NNN` / `LNK-NNN` の責務分割・同期／非同期境界

例外: 上記に属する項目でも、クラス構造判断に直結する場合（例: 「`ENT-007 注文` を『注文』集約ルート + 『注文明細』エンティティに分解する必要があり、データ側の単一 `ENT` を複数クラスに写像する」）は、前提として最小限言及する。ただし物理 DB・具体フレームワーク機構には踏み込まない。

- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）を既定の入力とする。存在すれば必ず参照する。特に `COMP-NNN`・`LNK-NNN`。
- データ設計書（`docs/design/data/data-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `ENT-NNN`・属性・`RULE-NNN`・状態遷移。
- インタフェース設計書（`docs/design/interface/interface-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `API-NNN`・`VR-NNN`・`ERR-NNN`。
- コンポーネント設計書（`docs/design/component/component-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `MOD-NNN`・`LYR-NNN`・`DEP-NNN` と、各 MOD の責務・実行境界種別・`ENT` 保有責務の割り当て。
- 追加で $ARGUMENTS にファイルパス・テキストが渡された場合はそれを併用する。
- 上流ドキュメントが存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえでクラス分割判断の根拠を明示する（抽出した暗黙前提は「6. 注意事項」の「前提の脆さ」として記載する）。

## 出力ファイル
- `docs/design/class/class-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: クラス設計は「責務の配分」「集約境界」「不変条件の置き場」が互いに影響し合うため、読み手が 1 本の動線でそれらの辻褄を検証できる必要があるため。MOD 単位で分割すると、集約境界が MOD を跨ぐケース・横断的な不変条件の扱いが追いにくくなる。クラス単位の更に詳細な仕様（メソッドシグネチャの言語別形・フレームワーク適用・ORM マッピング）は詳細設計工程で機能単位の別ファイルに展開し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体方針 → クラス俯瞰 → 個別クラス → 構造の骨格（集約と関連） → 振る舞いの確認（代表シーケンス） → 未決事項」の流れで理解できるよう意図しているため、固定する。

1. クラス設計方針
2. クラス一覧
3. 各クラス詳細
4. 集約と関連
5. 代表シーケンス（任意）
6. 注意事項

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/class-template.md`](templates/class-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. クラス設計方針
- 本クラス設計全体を貫く方針を、箇条書きで 5〜9 点程度にまとめる。論理クラス構造レベルの判断のみを扱い、具体の言語・フレームワーク・アノテーションには踏み込まない。
- 典型的に書くべき方針:
  - **採用するステレオタイプの語彙**: エンティティ / 値オブジェクト / 集約ルート / ドメインサービス / アプリケーションサービス / リポジトリ / ファクトリ / ポリシー（仕様）/ アダプタ / DTO のうち、本プロジェクトで採用する語彙を定義する。層別の置き場（どの `LYR-NNN` にどのステレオタイプが置かれるか）も対応付ける。
  - **ドメインモデル貧血症の回避**: エンティティ・値オブジェクトは「データだけ」のクラスにせず、**自身に関わる業務判断・状態遷移・不変条件維持の操作を自身が持つ**ことを原則とする。ドメインサービスは「どのエンティティにも所属させにくい業務操作」に限定して置く。
  - **値オブジェクトの採用基準**: 原始型（整数・文字列）に業務的意味を与えて区別したい場合（例: `金額` を整数のままにせず `Money` として値オブジェクト化する）の基準。併せて不変性・等価性（値等価）を原則とする。
  - **可変性原則**: 値オブジェクトは不変（更新時は新しいインスタンス生成）、エンティティは識別子で同一性を保ちつつ内部状態は変わりうる。可変エンティティの意図せぬ共有による副作用を避ける方針。
  - **同一性の判定**: エンティティは識別子（ID）での等価判定、値オブジェクトは全属性の値等価。継承関係がある場合の等価判定ポリシー。
  - **集約境界とトランザクション境界**: 集約は**1 トランザクションで整合性を保つ最小単位**として定義する。集約ルート経由でのみ内部を更新し、外部から集約内部のクラスを直接参照・更新しない。集約をまたぐ整合性は結果整合性またはドメインサービスで扱う。
  - **属性の公開原則**: 属性は原則非公開（private 相当）。外部からのアクセスは操作経由に限定する。Setter の導入は原則避け、状態変化は業務的に意味のある操作（例: `注文.確定する()`）で行う。
  - **不変条件の維持責任**: 生成時（コンストラクタ・ファクトリ）と状態変化操作の両方で不変条件が守られるようにする。破れた状態で公開（呼び出し元に戻る）させない。
  - **永続化との分離**: ORM 都合・API 都合で属性を増やしたり責務を歪めたりしない。永続化専用の属性（例: 楽観ロック用バージョン）は詳細設計の責務とし、本ドキュメントでは言及しない。
  - **DTO・変換クラスの扱い**: 境界（プレゼンテーション層 / インフラ層）でのみ DTO を使い、ドメイン層に DTO を持ち込まない。変換の責務を担うクラス（アセンブラ / マッパー）の配置層。
  - **例外の扱い**: 業務例外（`ERR-NNN` のうち業務的に意味を持つもの）とシステム例外の区別。どの層でどちらを生成・変換するか。
  - **null の扱い**: 欠損を許容する属性は明示的に表現する（例: `Optional<顧客>` / `顧客?`）、必須属性は null を取らない不変条件として明記する方針。
  - **共通型・値オブジェクトの昇格基準**: 「2 箇所以上で使われるまでは各クラス内のプリミティブに留め、以後共通値オブジェクト化する」等の歯止め。過剰な汎化を避ける。
- 「流行っているから」「慣れているから」といった要件・上流設計に紐付かない方針は記載しない。

### 2. クラス一覧
- `MOD-NNN` 配下の論理クラスを表形式で列挙する。列:
  - `CLS-NNN / 名称 / ステレオタイプ / 所属 MOD（MOD-NNN）/ 所属 LYR（LYR-NNN）/ 対応 ENT（ENT-NNN。なければ「-」）/ 所属 AGG（AGG-NNN。なければ「-」）/ 主な責務 / 関連 UC / 可変性（不変 / 可変） / 再利用性`
- `CLS-NNN` は本ドキュメントで新規採番する。採番は `CLS-001` から始め、追加時は最大値の次を採る。廃止するものはステータス「廃止」で残すかプロジェクトのポリシーに従う。
- **1 つの CLS は 1 つの MOD に所属**する。複数 MOD にまたがる役割を持つように見えるものは、通常はクラス分割の兆候である（典型: エンティティとしての役割とサービスとしての役割が混在している）。
- **1 つの CLS は 1 つの LYR に所属**する。層をまたぐ CLS はほぼ必ず責務過多。層の境界で分割する。
- **ステレオタイプ**は 1 章で定義した語彙から選ぶ。複数ステレオタイプを持つクラス（例: 「エンティティ兼集約ルート」）は併記する（例: `エンティティ（集約ルート）`）。
- 「対応 ENT」列は、エンティティクラス・値オブジェクトがどの `ENT-NNN` を表現するかを示す。1 ENT が複数 CLS に分かれる場合（エンティティ + 値オブジェクト群）は、各 CLS に同じ `ENT-NNN` を記載してよい。サービス・ファクトリ・リポジトリなど ENT に紐付かないクラスは「-」。
- 「所属 AGG」列は、本クラスがどの集約に属するかを示す。集約ルート自身も自集約を記載する。集約に属さないクラス（ドメインサービス・ファクトリ・リポジトリ・アプリケーションサービス・DTO 等）は「-」。
- 「可変性」は「不変 / 可変」。値オブジェクトは不変が原則、エンティティは可変が原則だが、例外を採る場合は 6.2 代替案で理由を明記する。
- 「再利用性」は「プロジェクト固有 / 製品ライン共通 / 汎用ライブラリ化」の 3 区分。1 章の方針と整合させる。

### 3. 各クラス詳細
各クラスについて、以下のサブテンプレートで詳細を記述する。すべての CLS で同じテンプレートに沿って書く（該当なしの節は「該当なし」と明記し、省略しない）。

`#### CLS-NNN 名称`

- **概要**: 何を表すクラスか、1〜2 文。ステレオタイプ・所属 `MOD-NNN` / `LYR-NNN`・対応 `ENT-NNN`・所属 `AGG-NNN` を明記する。
- **責務**: 「〜する。一方、〜はここでは行わず、CLS-YYY（または外部）に委譲する」の形で、引き受けることと引き受けないことをセットで書く。責務の曖昧さは後工程での「どこに書くべきか分からないコード」の原因になるため、境界を明示する。
- **属性一覧**: 表形式で列挙する。列:
  - `属性名（論理）/ 論理型 / 可視性 / 可変 / 役割 / 制約（必須 / 値域 / 列挙等） / 概要`
  - **論理型**は言語非依存で書く（例: 文字列 / 整数 / 数値（小数）/ 真偽値 / 日付 / 日時 / 列挙 / 参照（`CLS-NNN`） / コレクション<`CLS-NNN`> / Optional<`CLS-NNN`> / `ENT-NNN` 参照）。具体型（`String` / `string` / `BigDecimal` 等）は書かない。
  - **可視性**は「公開 / 限定公開 / 非公開」の 3 区分で記述する。言語別の具体修飾子（`public` / `protected` / `private` / `internal`）は詳細設計。
  - **可変**は「不変 / 可変」。値オブジェクトの属性は全項目不変が原則。
  - **役割**は「識別子 / 値 / 参照 / 派生 / 監査」のいずれか。派生属性は「計算の元となる属性」を概要に書く。
  - **制約**は必須性・値域・列挙値・長さ制約など。これは詳細設計で DBMS 型に落ちる前の論理制約として書く。
- **操作一覧**: 表形式で列挙する。列:
  - `操作名 / 引数（名前: 論理型, ...） / 戻り値（論理型） / 可視性 / 事前条件 / 事後条件 / 生成・変換・通過する例外（ERR-NNN） / 実装する UC / BRU`
  - 操作名は業務的に意味のある動詞句にする（例: `確定する` / `キャンセルする` / `金額を合計する`）。`getX` / `setX` のような機械的な名称は原則避け、必要な場合も「なぜ必要か」を概要で補う。
  - **事前条件**は「呼び出し元に満たしていてほしい条件」（典型: `状態が下書きであること`・`対象期間が有効であること`）。事前条件を満たさない呼び出しの扱い（例外生成 / 戻り値で示す）は「例外」列に書く。
  - **事後条件**は「操作後に必ず成り立つ条件」（典型: `状態が確定に遷移している`・`合計金額が再計算されている`）。
  - **例外**は `ERR-NNN` を参照する。本クラスが**生成する**もの・下層のエラーを**変換する**もの・上位に**通過させる**ものを区別できるよう列に注記する。
  - **実装する UC / BRU** は、この操作が要件側のどのユースケース・業務ルールを実現するかを `UC-NNN` / `BRU-NNN` で参照する。実装が要件と紐付かない操作は、過剰実装の疑いがあるため 6.1 リスクに記録する。
- **クラス不変条件**: このクラスのインスタンスが「生成時」と「任意の操作が完了した時点」で常に満たす条件を箇条書きで示す。`INV-NNN` に昇格させるほどでないクラス固有の条件はここに書き、集約 / 集約横断にまたがるものは「4.3 不変条件」で `INV-NNN` として採番する。
- **参照する他クラス（協調・依存）**: 本クラスが協調する他 `CLS-NNN` を列挙する。協調の種類（集約内参照 / 集約越しの ID 参照 / ドメインサービス呼び出し / リポジトリ越しの取得 等）を一言添える。集約を跨ぐ直接参照を持つ場合は、6.1 リスクに記録するか、集約境界の見直し候補として検討する。
- **生成・破棄**: インスタンスの生成方法（コンストラクタ / ファクトリ / DI で注入 / リポジトリから復元）を種別レベルで記述する。コンストラクタ引数として何を受け取るかは論理型で示す。破棄のタイミング（リクエスト終了 / セッション終了 / GC 任せ）。DI コンテナ具体構成は詳細設計。
- **可変性**: 「不変」または「可変」。可変の場合、状態を変える操作（上の操作一覧のどれか）を列挙する。
- **等価性**: 「識別子等価（エンティティ）/ 値等価（値オブジェクト）/ 参照等価」のいずれか。識別子等価の場合、識別子となる属性を明示する。
- **対応エンティティ（ENT-NNN）との対応**: 対応する `ENT-NNN` の属性のうち、本クラスが担当する属性を明示する（エンティティを複数クラスに分解した場合、各クラスが担当する属性が分かるように）。データ設計に存在しない属性を本クラスが持つ場合は、その必要性（派生値 / 一時状態）を明記する。
- **対応するバリデーション（VR-NNN）**: IF 側で `VR-NNN` として定義されたバリデーションのうち、本クラスが実装する範囲を列挙する。「UI 側と API 側で二重検証」と決まっているものについては、API 側の業務正当性判定を本クラスのどの操作・不変条件で担うかを明示する。
- **対応するエラー（ERR-NNN）**: 本クラスが**生成する** / **変換する** / **通過させる** `ERR-NNN` を区別して列挙する（操作一覧の「例外」列の総覧と同等だが、クラスレベルで整理する）。
- **実装する業務ルール（BRU-NNN / RULE-NNN）**: 本クラスが実装責任を負う `BRU-NNN`（業務ルール）・`RULE-NNN`（データ整合性ルール）を列挙する。複数クラスに分散するものは、主たる実装担当を 1 つに定め、他は「協調」として書く。
- **備考**: 論理クラス構造レベルの補足のみ。メソッドシグネチャの言語別形・アノテーション・ORM マッピングは詳細設計に回す。

### 4. 集約と関連
本章は「クラス間の静的な構造」を固める章である。4.1 で集約境界（クラスの束ね方）、4.2 でクラス間の関連（細かな関係性）、4.3 で不変条件（構造上守るべき約束）を扱う。

#### 4.1 集約（AGG-NNN）
- システムが持つ集約を表形式で列挙する。列:
  - `AGG-NNN / 名称 / 集約ルート（CLS-NNN）/ 集約に含まれるクラス（CLS-NNN 列挙）/ 対応 ENT-NNN / トランザクション境界の意味 / 主な状態遷移の担い手 / 関連 UC`
- `AGG-NNN` は本ドキュメントで新規採番する（`AGG-001` から）。
- **集約ルート経由の原則**: 集約外部からは集約ルートを通じてのみ内部にアクセスする。内部クラスを外部から直接参照 / 更新しない（言語構文上の可視性だけでなく、設計方針として禁止する）。外部から参照する必要があるときは、集約ルートが **ID を返す**か、**必要な情報をコピーした値オブジェクト／DTO を返す**ことで応じる。
- **1 トランザクション = 1 集約の原則**: 1 つのトランザクション内で更新する集約は 1 つを基本とする。複数集約の整合はイベント駆動・結果整合性・補償トランザクション・ドメインサービスのいずれかで扱う方針を明記する。
- **集約の粒度**: 大きすぎる集約（1 トランザクションで更新する範囲が広すぎる）と小さすぎる集約（1 業務操作で複数集約の同時更新が必要になる）のどちらも問題。選んだ粒度の根拠を `NFR-NNN`（応答性能・スケーラビリティ）・`BRU-NNN`（業務ルール適用範囲）と紐付けて説明する。
- 集約に属さないクラス（ドメインサービス・ファクトリ・リポジトリ・アプリケーションサービス・DTO）はここでは扱わない。3 章の各クラス詳細で個別に扱う。
- 集約図は Mermaid `classDiagram` で描いてもよい（任意）。1 集約 1 枚、または全集約を 1 枚にまとめる。集約境界を `note` で示すか、集約ごとに図を分ける。

#### 4.2 クラス間関連（ASSOC-NNN）
- クラス間の静的関連を表形式で列挙する。列:
  - `ASSOC-NNN / 関連元 CLS / 関連先 CLS / 関連種別 / 方向 / 多重度 / ライフサイクル依存 / 対応する REL-NNN（データ側）/ 対応する DEP-NNN（コンポ側）/ 概要`
- `ASSOC-NNN` は本ドキュメントで新規採番する（`ASSOC-001` から）。
- **関連種別**は以下の種別レベルで記述する:
  - **関連（association）**: 使う / 知っている関係。相手のライフサイクルは独立。
  - **集約（aggregation）**: 全体と部分の関係だが、部分のライフサイクルは独立。UML 的な意味の「弱い所有」。本ドキュメントの `AGG-NNN`（DDD 的集約）とは別概念なので混同に注意。
  - **合成（composition）**: 全体が消えれば部分も消える強い所有関係。DDD の集約内部の関係は通常これ。
  - **継承（inheritance）**: is-a 関係のみに使う。コード再利用目的の継承は避ける方針（1 章で明記）。継承ツリーの深さは 2〜3 段に抑えるのを目安とする。
  - **実現（realization）**: インタフェース（抽象）の実装。依存性逆転の実装側。
  - **依存（dependency）**: 引数として受け取る・戻り値として返す等の一時的な関係。属性として保持しない。
- **方向**は「単方向 / 双方向」。双方向関連は原則避け、必要な場合はどちらの側が整合性維持責任を負うかを明示する。
- **多重度**は `1` / `0..1` / `0..*` / `1..*` / `N..M` 等で記述する。
- **ライフサイクル依存**は「独立 / 強（親が消えれば子も消える）/ 弱（親消滅時に子を別の親に移すか、独立存続か）」。合成関係は通常「強」、集約関係は通常「独立または弱」。
- **対応する REL-NNN / DEP-NNN**: データ設計の `REL-NNN`（エンティティ関連）に由来するものは参照を入れる。コンポーネント設計の `DEP-NNN`（モジュール間依存）の内部展開として発生しているものは `DEP-NNN` を参照する。対応が無い `ASSOC` は、データ / コンポーネント設計との整合確認が必要な兆候として 6.1 リスクに記録する。
- **循環依存は原則禁止**。見つかった場合は、共通部分の抽出・依存性逆転（インタフェース導入）・イベント化のいずれかで解消する。やむを得ず残す場合は理由と影響範囲を 6.1 リスクに記録し、6.2 代替案で不採用の案も示す。
- クラス図は Mermaid `classDiagram` で描く。層別に分けるか、集約別に分けるかは見やすさで選ぶ。粒度は `CLS-NNN` に留め、属性・操作まで図上に載せすぎない（図が読めなくなる）。

#### 4.3 不変条件（INV-NNN）
- クラス内 / 集約内 / 集約横断のいずれかで常に守るべき条件を表形式で列挙する。列:
  - `INV-NNN / 内容 / 成立範囲（CLS / AGG / 横断）/ 維持責任者（CLS-NNN または AGG-NNN）/ いつ検査するか（生成時 / 操作後 / 結果整合） / 違反時の扱い / 由来（BRU-NNN / RULE-NNN / VR-NNN）`
- `INV-NNN` は本ドキュメントで新規採番する（`INV-001` から）。
- **クラス内不変条件**: 原則として「3. 各クラス詳細」の「クラス不変条件」節にインラインで書く。重要度が高い・他クラスから参照される・横断性を持つ、いずれかに該当するものだけ `INV-NNN` として採番する。
- **集約内不変条件**: 集約ルートが維持責任を負う。集約ルートの操作が完了した時点で、集約内の全クラスを合わせた条件が成り立つ。例: 「注文集約では、注文明細の合計金額が注文の合計金額と一致する」。
- **集約横断不変条件**: 1 トランザクションでは守れず、結果整合性で扱う。維持手段（ドメインイベント / 定期ジョブ / 補償トランザクション）を明示する。例: 「顧客の累計注文金額は、注文集約の合計を集計した値と一致する（結果整合）」。
- **違反時の扱い**は「操作拒否（例外生成）/ 警告生成（処理は継続）/ 補正（自動調整）/ ログ記録のみ」等で記述する。方針は本章で決めるが、実装位置の最終確定（どの `ERR-NNN` として生成するか・どの層で検査するか）は既に 3 章の各クラス詳細で特定されていること。
- **由来**列には、`RULE-NNN`（データ整合性ルール）・`BRU-NNN`（業務ルール）・`VR-NNN`（バリデーション）のうち由来するものを参照する。どの `RULE-NNN` もクラス設計の `INV-NNN` のいずれかに受け止められること（受け止め先が特定できない `RULE-NNN` は、実装位置不明として 6.1 リスクに記録）。

### 5. 代表シーケンス（任意）
- 本章は任意。該当なしの場合は「該当なし」と明記して空節のまま残す。代表シーケンスを書かない場合でも、3 章の操作仕様と 4 章の集約・関連だけで業務フローが辿れる状態を目標とする。
- 書く場合は、主要な `UC-NNN` を 1〜3 本選び、Mermaid `sequenceDiagram` でクラス間の呼び出し順序を描く。全ユースケースを網羅しない（冗長になる）。選定基準の例:
  - **集約ルートが不変条件を守る典型例**（例: 「注文確定」で注文集約ルートが合計金額の再計算と状態遷移を同時に守る）
  - **複数集約をまたぐ整合性処理**（例: 「注文確定時に顧客の累計金額を更新する」結果整合のフロー）
  - **ドメインサービスが介在する業務判断**（例: 「与信枠を超える注文の判定」を Credit Policy に委ねる）
  - **例外フローで `ERR-NNN` がどう生成・変換されるか**
- 起点は典型的には「アプリケーションサービス」または「API ハンドラ MOD」。そこからリポジトリ越しに集約を復元し、集約ルートの操作を呼び、リポジトリで保存し、ドメインイベント発行 / 例外変換まで描く。
- 粒度は `CLS-NNN` 単位。引数・戻り値は論理型で書く。言語・フレームワーク固有の呼び出し記法には踏み込まない。
- 登場するクラスは、すべて 2 章のクラス一覧に存在すること。

### 6. 注意事項
注意事項は単一の表ではなく、以下 3 区分で整理する。混在させると読み手の対応先が曖昧になる。

#### 6.1 リスク・懸念点
- `RISK-NNN / 内容 / 影響範囲（CLS / AGG / ASSOC / INV / 業務） / 顕在化条件 / 暫定対応 / 詳細設計・テスト設計への申し送り`
- 典型カテゴリ:
  - **ドメインモデル貧血症**: エンティティ・値オブジェクトがデータ保持だけになり、業務判断がアプリケーションサービス・ユーティリティに漏れている
  - **神クラス**: 責務が肥大化し、変更時の影響範囲が広いクラス（操作数・属性数・関連数のいずれかが突出している）
  - **集約境界の曖昧さ**: 同じクラスが複数集約にまたがっているように見える / 集約ルートを経由しない内部参照が残っている
  - **不変条件の抜け**: `RULE-NNN`・`BRU-NNN` のいずれかを受け止める `INV-NNN` が特定できない
  - **不変条件の重複実装**: 同じ条件が複数クラスで独立に実装されていて、片方の変更が他方に波及しない
  - **継承の誤用**: コード再利用目的の継承、is-a でない継承、深すぎる継承ツリー
  - **値オブジェクトとエンティティの混同**: 同一性を識別子で保つべきものを値等価で扱っている、またはその逆
  - **可変オブジェクトの意図せぬ共有**: 同一インスタンスを複数の親が保持し、片側での変更が他側に波及する
  - **循環依存の潜在**: 現状は無くても、ある変更で発生する兆候
  - **永続化都合の混入**: ORM 都合・DB カラム都合でクラス属性が増えている / API レスポンス構造に合わせて属性が歪んでいる
  - **トランザクション境界が集約を越える**: 1 業務操作で複数集約の同時更新が必要になる（集約粒度の見直し候補）
  - **ドメインサービスへの過度な退避**: 本来エンティティ・値オブジェクトに持たせられる操作がサービスに流出している
  - **DTO のドメイン層侵入**: `API-NNN` のリクエスト型・`SIF-NNN` のファイル形式がドメイン層クラスに混入している
  - **要件未確定のまま進めた前提**

#### 6.2 代替案と採らない理由
- 主要なクラス構造判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`。
- 最低でも以下の論点については検討の痕跡を残すことを推奨する。該当しなければ「検討不要と判断した理由」を 1 行で記す。
  - **集約の粒度**: 大きめ（1 集約に多くを含める）vs 小さめ（細かく分ける）
  - **値オブジェクト化**: プリミティブのまま使う vs 値オブジェクトに昇格する（例: 金額・メールアドレス・住所）
  - **エンティティの分解**: 単一クラスに集約 vs エンティティ + 値オブジェクト群に分解
  - **操作の置き場**: エンティティ自身 vs ドメインサービス vs アプリケーションサービス
  - **継承 vs 委譲**: 型階層で表現する vs 委譲先のインタフェースで表現する
  - **不変 vs 可変**: 状態変化を伴うエンティティも不変に寄せる（スナップショット戻し）vs 可変のまま
  - **ファクトリの分離**: コンストラクタで生成 vs 専用ファクトリクラスで生成
  - **集約横断整合**: 結果整合（イベント）vs 同期（ドメインサービス + 複数集約更新）
  - **リポジトリの粒度**: 集約単位 vs 複数集約統合
- 詳細設計寄りの判断（具体型・アノテーション・DI 構成）は本章では取り上げず、詳細設計の代替案検討で扱う。

#### 6.3 後続工程への申し送り事項
- 本クラス設計では決め切らない論点を、**工程別**に分けて記録する。

**詳細設計・実装への申し送り**: 表形式で記載。列: `HO-D-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- 言語固有の型指定・コレクション型・Optional 表現
- フレームワーク固有機構の適用（アノテーション・デコレータ・ミドルウェア）
- DI コンテナ構成・スコープ・ライフサイクル管理
- ORM マッピング・リポジトリ実装・トランザクションマネージャ
- 例外階層の具体クラス名・継承関係
- Getter / Setter 生成方針（Lombok・record・data class 等の言語機能）
- ディレクトリ・パッケージ命名規則の具体
- ログメッセージ・バリデーションメッセージの文面

**テスト設計への申し送り**: 表形式で記載。列: `HO-T-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- 単体テスト粒度（クラス単位 / 集約単位）
- 値オブジェクトの等価性テスト
- 集約ルート経由の不変条件テスト
- モック戦略（リポジトリ・ドメインサービス）
- フィクスチャ・テストデータビルダの設計
- 状態遷移テストの網羅方針

## 図解の記法ルール
要件・アーキ・データ・IF・コンポーネント設計と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。

- **クラス図**: `classDiagram`
  - 関連（`ASSOC-NNN`）を矢印で示す。種別は UML 記法（`--|>` 継承 / `..|>` 実現 / `--*` 合成 / `--o` 集約（UML 的）/ `-->` 依存）で記述する。
  - 集約（DDD 的、`AGG-NNN`）の境界は `note for` もしくは図を分けて示す。UML の集約（`--o`）と混同しない記法を採る（例: 「このダイアグラムの破線枠内が 1 つの `AGG-NNN`」と `note` に明記する）。
  - 属性・操作は主要なものに絞る（識別子・業務的に意味のある操作のみ）。網羅は 3 章で担保する。
- **シーケンス図**: `sequenceDiagram`（任意）
  - 登場する participant は `CLS-NNN` 単位。アプリケーションサービス → 集約ルート → 集約内部クラス → リポジトリ の流れが典型。
  - 戻り値・例外伝播も矢印で描く。例外の場合は `alt` / `opt` で分岐を示す。
  - UC-NNN / API-NNN と紐付けた見出しを付ける。
- **状態遷移図**: `stateDiagram-v2`（必要に応じて）
  - データ設計側で `ENT-NNN` の状態遷移を既に描いている場合、本ドキュメントで重複して描かない。ただし、エンティティクラスが内部的に持つ状態遷移で業務的に意味を持つもの（例: 「集約ルート内部で持つライフサイクル状態」）が別途あればここで描く。

## ID 体系
本ドキュメント内で採番・参照する ID は以下。

- `CLS-NNN` クラス（**本ドキュメントで新規採番**。`CLS-001` から）
- `AGG-NNN` 集約（**本ドキュメントで新規採番**。`AGG-001` から）
- `ASSOC-NNN` クラス間関連（**本ドキュメントで新規採番**。`ASSOC-001` から）
- `INV-NNN` 不変条件（**本ドキュメントで新規採番**。`INV-001` から）
- `ALT-NNN` 代替案（本ドキュメント内の局所 ID）
- `RISK-NNN` リスク・懸念点（本ドキュメント内の局所 ID）
- `HO-D-NNN` / `HO-T-NNN` 後続工程（詳細設計・テスト設計）への申し送り事項

**参照のみ**（本ドキュメントで採番しない）:
- `UC-NNN` / `NFR-NNN` / `BRU-NNN` / `ENT-NNN`（要件側）
- `COMP-NNN` / `LNK-NNN`（アーキテクチャ側）
- `RULE-NNN` / `REL-NNN`（データ側）
- `API-NNN` / `UI-NNN` / `SIF-NNN` / `HIF-NNN` / `CIF-NNN` / `ERR-NNN` / `VR-NNN`（インタフェース側）
- `MOD-NNN` / `LYR-NNN` / `DEP-NNN`（コンポーネント側）

既存 ID は再採番しない。廃止するクラス・集約・関連・不変条件はステータス「廃止」で残すかプロジェクトのポリシーに従う。

## 上流設計書との紐付け
- すべての `CLS-NNN` は、1 つの `MOD-NNN` に所属する。所属先が無い CLS は、コンポーネント設計側に該当 MOD が未定義である兆候なので、コンポーネント設計側に戻って追加するか、本 CLS の必要性を再検討する。
- すべての `CLS-NNN` は、1 つの `LYR-NNN` に所属する。所属できない CLS は、層をまたぐ責務過多の兆候なので、層境界で分割を検討する。
- すべての `CLS-NNN` は、少なくとも 1 つの `UC-NNN`・`NFR-NNN`・`BRU-NNN`・`RULE-NNN` のいずれかに紐付けて「なぜ必要か」を説明できる状態にする。紐付かない CLS は過剰設計の疑いがあるため、6.2 代替案で不採用として整理するか、必要性の根拠（運用補助・共通インフラ等）を追記する。
- すべての `ENT-NNN` は、**それを表現する `CLS-NNN` が 1 つ以上**本ドキュメントに存在することを確認する。1 ENT を複数 CLS に分解する場合、どの属性がどの CLS に割り当たるかが「3. 各クラス詳細」の「対応エンティティとの対応」節で特定できること。
- すべての `RULE-NNN`（データ側整合性ルール）は、`INV-NNN` として本ドキュメントのいずれかで受け止められること。受け止め先が特定できない `RULE-NNN` は 6.1 リスクに記録する。
- すべての `BRU-NNN`（業務ルール）は、少なくとも 1 つの `CLS-NNN` の操作または `INV-NNN` で実装責任を負うこと。実装責任が特定できない `BRU-NNN` は 6.1 リスクに記録する。
- すべての `VR-NNN`（バリデーション）のうち、業務正当性に関わるもの（VR のカテゴリが「業務ルール」）は、対応する `CLS-NNN` の事前条件 / 不変条件として受け止められること。UI 側で完結する表示整形チェックは本ドキュメントの対象外。
- すべての `ERR-NNN`（エラー）について、生成するクラス・変換するクラス・通過するクラスが本ドキュメントで追跡できること。
- すべての `API-NNN` は、ハンドラ責務を担う `MOD-NNN` に所属する `CLS-NNN`（アプリケーションサービス等）の操作として受け止められること。
- すべての `DEP-NNN`（モジュール間依存）は、本ドキュメントの `ASSOC-NNN` または CLS 間の協調の記述で内部展開が説明できること。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を「6. 注意事項」に明記して残すほうがよい。

### 1. 責務が 1 クラスに寄りすぎていないか
- 操作数・属性数・関連数のいずれかが突出しているクラスがないか（目安: 操作が 2 桁後半を超える、属性が 15 を超える、直接関連するクラスが 10 を超える）。該当すれば責務分割候補として 6.1 リスクに記録する。
- 1 クラスが「業務 A の判定」「業務 B の判定」「データ整形」「外部通信」など複数の関心事を同時に担っていないか。
- 抽象化水準が揃っているか（同じクラスに「注文を確定する」のような業務操作と「JSON にシリアライズする」のような技術操作が混在していないか）。
- 「神クラス」を 6.1 に記録しているか、または現時点で該当なしと判定できているか。

### 2. データだけのクラスになっていないか（ドメインモデル貧血症）
- エンティティ・値オブジェクトが属性と Getter / Setter のみで、業務操作を持たない構造になっていないか。
- 業務判断（例: 「この注文は確定可能か」）がアプリケーションサービス・ユーティリティ側に漏れ出していないか。エンティティ自身に戻せないかを検討する。
- 値オブジェクト化できるプリミティブ（金額・期間・コード等）が、プリミティブのまま散らばっていないか。値オブジェクト化の基準は 1 章の方針と整合させる。
- 状態遷移を持つエンティティで、遷移操作が外側（呼び出し元）で素の状態属性を書き換える形になっていないか。遷移は必ずエンティティの操作経由にする。

### 3. 不変条件がどこで守られるか明確か
- すべての `RULE-NNN`（データ整合性ルール）について、受け止める `INV-NNN` または `CLS-NNN` 内不変条件が特定できているか。
- すべての `BRU-NNN`（業務ルール）について、実装責任を負う操作または不変条件が特定できているか。
- 集約内不変条件は集約ルートの操作完了時点で守られる設計になっているか。集約ルートを介さず内部クラスを更新される経路が残っていないか。
- 集約横断の不変条件について、同期（ドメインサービス）と結果整合（イベント・補償）のどちらで扱うかが明示されているか。
- 不変条件の検査タイミング（生成時 / 操作後）が各 `INV-NNN` で明示されているか。

### 4. API / DB 都合だけでクラスが歪んでいないか
- API レスポンスの形に合わせてドメインクラスが属性を増やしていないか。境界の DTO で受け止めるべきものがクラスに混入していないか。
- ORM 都合（具体カラム名、特定 ORM のルール、楽観ロック用バージョン等）でクラス属性や操作が歪んでいないか。本ドキュメントでは論理属性のみを扱い、永続化用属性は詳細設計に回す。
- 画面の都合（UI 側で扱いやすい整形済み文字列 / 表示用プロパティ）がエンティティに持ち込まれていないか。表示整形はプレゼンテーション層・DTO の責務。
- 外部 `SIF-NNN` のファイル項目構造がそのままクラス構造として採用されていないか。境界でマッパー・アダプタを介して受け止める。

### 5. 集約境界が適切か
- 1 集約は 1 トランザクションで整合性を保てる範囲に収まっているか。
- 集約ルートを経由しない内部クラスの外部参照・更新が残っていないか。残っていれば 6.1 リスクに記録する。
- 1 業務操作で複数集約の同時更新が必要な箇所について、結果整合 / ドメインサービス / 補償 のいずれで扱うかが明示されているか。
- 集約の粒度判断について、大きめ・小さめの代替案が 6.2 で検討されているか。

### 6. 関連（ASSOC）と継承の適切性
- 循環依存が残っていないか。残る場合は解消策（分割 / 依存性逆転 / イベント駆動）が 6.2 代替案で検討されているか。
- 継承は is-a 関係のみで使われているか。コード再利用目的の継承が紛れていないか。
- 深すぎる継承ツリー（3 段を大きく超える）が 6.1 リスクに記録されているか。
- 双方向関連が必要最小限に抑えられ、整合性維持責任がどちらか一方に明示されているか。
- 合成（`--*`）と関連（`-->`）・集約（`--o`）の区別が誤用されていないか（ライフサイクル依存の強さと矛盾がないか）。

### 7. 粒度の侵食が起きていないか
- **下向きの侵食**（本ドキュメントに詳細設計・実装が紛れている）: 言語固有型・アノテーション・DI 具体・ORM マッピング・ディレクトリ命名・例外階層具体クラス名・ログ文面が紛れていないか。紛れていたら「6.3 詳細設計への申し送り」に切り出す。
- **横向きの侵食（コンポーネント設計）**: `MOD-NNN` の追加・削除・責務再定義、`LYR-NNN` の変更、`DEP-NNN` 種別の再選定を本ドキュメントで行っていないか。必要ならコンポーネント設計側に戻る。
- **横向きの侵食（データ設計）**: `ENT-NNN` の属性定義・キー方針・`RULE-NNN` の制約内容を本ドキュメントで再定義していないか。
- **横向きの侵食（インタフェース設計）**: `API-NNN` / `VR-NNN` / `ERR-NNN` を本ドキュメントで再定義していないか。
- **上向きの侵食**: 新しい `BRU-NNN` や `UC-NNN` が、本ドキュメントで黙って発生していないか。発生していたら「6.1 リスク・懸念点」に記録し、要件側への波及候補とする。
- **空洞化**: 論理クラス構造粒度で決めるべき話（責務の配分・集約境界・不変条件の置き場・等価性方針・可変性方針）が「詳細設計で決める」に丸投げされていないか。ここで決め切る。

### 8. 図と表の整合
- クラス図（4.2）に登場する CLS が、すべて 2 章のクラス一覧に存在するか。
- 集約表（4.1）の「集約に含まれるクラス」に挙がっている CLS が、すべて 2 章のクラス一覧に存在するか。
- 関連表（4.2）の `ASSOC-NNN` が、すべてクラス図上の矢印として表現されているか。図と表で関連種別・多重度・方向が一致しているか。
- 不変条件表（4.3）の `INV-NNN` が、該当する `CLS-NNN` の詳細（3 章）または `AGG-NNN`（4.1）と紐付いているか。
- 代表シーケンス（5 章、書いた場合）に登場する CLS がすべて 2 章に存在し、呼び出されている操作が 3 章の操作一覧に存在するか。
- 2 章の「対応 ENT」「所属 AGG」列が、3 章・4.1 の記述と齟齬していないか。
- 1 章で「採用する」と宣言したステレオタイプ・可変性原則・集約境界方針が、2〜5 章の個別記述と矛盾していないか。
