# コンポーネント設計の作成
要件定義書・アーキテクチャ設計書・データ設計書・インタフェース設計書を入力として、基本設計の起点となるコンポーネント設計書を作成してください。

## Goal
アーキ側で決定された `COMP-NNN` の内部構造を、**変更容易性と責務の明確さを両立するモジュール分割**として示す。

「変更容易性と責務の明確さを両立する」とは、各モジュールが「何を引き受け」「何を引き受けないか（他モジュールへ委譲するか）」「どの方向に依存し」「どの方向には依存しないか」が一義に読み取れ、特定の要求変更が到達する範囲を事前に説明できる状態を指す。逆に、クラス・メソッドシグネチャ・DI 構成・ディレクトリ命名といった実装工程で変わりうる詳細は踏み込まない。判断に迷ったら、要件 ID（UC-NNN / NFR-NNN / BRU-NNN）・構成要素 ID（COMP-NNN / LNK-NNN）・エンティティ ID（ENT-NNN / RULE-NNN）・インタフェース ID（API-NNN / UI-NNN / SIF-NNN / ERR-NNN / VR-NNN）のいずれかに紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて注意事項に記録する。

## 位置付け（要件定義・アーキテクチャ設計・データ設計・インタフェース設計・詳細設計・インフラ設計との関係）
本スキルは `/generate-requirements`、`/generate-architecture-design`、`/generate-data-design`、`/generate-interface-design` の成果物をすべて入力とし、詳細設計・実装の出発点となる**論理モジュール構造**を固める。データ設計・インタフェース設計と並列で独立に動くのではなく、アーキ側の `COMP-NNN` を内側から肉付けしつつ、データ・IF の責務割り当てと突き合わせて内部モジュール構成を確定するという位置付けをとる。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 業務ルール（`BRU-NNN`）・ユースケース（`UC-NNN`）・非機能要件（`NFR-NNN`）が、どのモジュールの責務として実装されるかを決める根拠とする。特に変更容易性・保守性・拡張性の NFR は、本ドキュメントのモジュール分割と依存方向の正当性根拠となる。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - `COMP-NNN` を本ドキュメントの外殻として使う。**新しい `COMP-NNN` を本ドキュメントで追加しない**（必要ならアーキ側に戻って追加する）。
  - `LNK-NNN`（COMP 間リンク）は、発側 COMP 内の発信モジュールと受側 COMP 内の受信モジュールの対（`DEP-NNN`）に展開する根拠となる。同期／非同期の境界もここから引き継ぐ。
- 上流（データ）: `docs/design/data/data-design.md`
  - `ENT-NNN` の CRUD 責務・ライフサイクル・状態遷移が、どのモジュールで担われるかを決める。`RULE-NNN`（エンティティ横断整合性）の実装責務位置もここから導く。
- 上流（インタフェース）: `docs/design/interface/interface-design.md`
  - `API-NNN` のハンドラ責務、`UI-NNN` のイベント処理責務、`SIF-NNN` の送受信責務、`ERR-NNN` の生成／変換／提示責務、`VR-NNN` のバリデーション実装位置を、モジュール分割へ落とし込む。
- 下流（詳細設計）: 機能・画面単位の詳細設計、クラス図・メソッドシグネチャ・インタフェース定義、DI コンテナ構成、ディレクトリ・パッケージ命名規則、ORM マッピング、フレームワーク固有機構（アノテーション・デコレータ・フック）の具体適用。
- 下流（インフラ設計）: モジュールのデプロイ単位・プロセスコンテナ構成・ワーカースケール設定・共有ライブラリ配布方式・ランタイム選定の具体。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**論理モジュール構造レベル**の話であり、実装固有の構文・命名・フレームワーク機構には踏み込まない。

- 内部モジュールの洗い出し（`COMP-NNN` を内側から分解する）
- レイヤ配置（プレゼンテーション / アプリケーション / ドメイン / インフラ 等）と、各レイヤの責務
- 実行境界の割り当て（プロセス内ライブラリ / プロセス内サービス / 別プロセス / 非同期ワーカー / バッチ / クライアント常駐 / フレームワーク提供 等の**種別**）
- モジュール間の依存方向と循環の回避
- 業務ロジックの置き場（ドメイン層への集約方針）とインフラ依存の切り離し方針
- 横断関心事（ロギング / 認可 / トランザクション / 入力バリデーション / エラー変換 / 監査記録）の実装責務位置
- 状態を持つモジュールの境界（ステートフル / ステートレスの宣言と、状態の保管位置）
- 再利用性の評価（プロジェクト固有 / 製品ライン共通 / 汎用ライブラリ化）
- 変更影響範囲の局所化（特定の要求変更がどのモジュールに到達するかの想定）
- `ENT-NNN` の所有権 / `API-NNN` のハンドラ責務 / `ERR-NNN` の生成・変換経路 / `VR-NNN` の実装位置 の割り当て

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、モジュール構造が定まった後の工程で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**詳細設計で決める**
- クラス図・インタフェース定義・メソッドシグネチャ
- DI コンテナの具体構成・初期化順序・スコープ管理
- ディレクトリ・パッケージ命名規則（例: `src/domain/xxx` / `app/Services/Xxx` 等の具体名）
- フレームワーク固有機構の適用（アノテーション・デコレータ・ミドルウェアフック）の具体
- ORM マッピング定義・リポジトリ実装
- バリデーションメッセージ文面・ログフォーマット詳細
- モック・フィクスチャ戦略、単体テスト分割
- ビルド構成（モジュール分割したソースコードをどう成果物にまとめるか）

**インフラ設計で決める**
- デプロイ単位（どのモジュール群を 1 プロセス／コンテナにまとめるか）
- プロセスコンテナ・ワーカーのスケール設定・台数
- 共有ライブラリの配布方式（社内レジストリ / モノレポ / バイナリ配布）
- ランタイム・言語・具体フレームワークの選定

**アーキテクチャ設計で決まり済み（本ドキュメントでは再決定しない）**
- `COMP-NNN` の追加・削除・責務の再定義（必要なときはアーキ側に戻る）
- `LNK-NNN` の同期／非同期境界
- 認証認可の全体責務位置（IdP 委譲 / ゲートウェイ集約 / 自前）
- 外部 SaaS 利用の是非

**データ設計・インタフェース設計で決まり済み（本ドキュメントでは再決定しない）**
- `ENT-NNN` の属性定義・キー・削除方針・履歴方針
- `RULE-NNN` の制約内容
- `API-NNN` のリクエスト／レスポンス項目・主要ステータス・冪等性方針
- `UI-NNN` の入出力項目・画面イベント・対話フロー
- `VR-NNN` のバリデーション条件
- `ERR-NNN` のエラーカタログ

例外: 上記に属する項目でも、モジュール分割判断に直結する場合（例: 「SaaS 側から webhook 受信が必須であることが要件上確定しており、その受信口を独立モジュールに切り出す必要がある」）は、前提として最小限言及する。ただし具体の実装（言語・フレームワーク・具体ライブラリ名）には踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。特に `BRU-NNN`・`UC-NNN`・非機能要件（保守性 / 拡張性 / 応答性能 / セキュリティ）。
- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）を既定の入力とする。存在すれば必ず参照する。特に `COMP-NNN`・`LNK-NNN`（同期／非同期境界を含む）。
- データ設計書（`docs/design/data/data-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `ENT-NNN`・`RULE-NNN`・状態遷移定義。
- インタフェース設計書（`docs/design/interface/interface-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `API-NNN`・`UI-NNN`・`SIF-NNN`・`ERR-NNN`・`VR-NNN`。
- 追加で $ARGUMENTS にファイルパス・テキストが渡された場合はそれを併用する。
- 上流ドキュメントが存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえでモジュール分割判断の根拠を明示する（抽出した暗黙前提は「6. 注意事項」の「前提の脆さ」として記載する）。

## 出力ファイル
- `docs/design/component/component-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: コンポーネント設計は「責務の置き場」「依存方向」「配置の段階的詳細化」を読み手が 1 本の動線として検証できることが最重要であるため。モジュール単位の詳細（クラス分解・インタフェース定義・DI 構成）は、詳細設計工程で機能単位・画面単位の別ファイルに展開し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体方針 → レイヤ俯瞰 → モジュール俯瞰 → 個別モジュール → 依存関係 → 未決事項」の順に理解できるよう意図しているため、固定する。

1. コンポーネント設計方針
2. レイヤ構成
3. モジュール一覧
4. 各モジュール詳細
5. 依存関係
6. 注意事項

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/component-template.md`](templates/component-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. コンポーネント設計方針
- 本コンポーネント設計全体を貫く方針を、箇条書きで 5〜8 点程度にまとめる。論理モジュール構造レベルの判断のみを扱い、具体のフレームワーク・言語機能・ディレクトリ命名には踏み込まない。
- 典型的に書くべき方針:
  - **レイヤリング方式の選定**: 伝統的レイヤード / Clean Architecture / Hexagonal（ポート・アダプタ）/ オニオン等のうち、どの考え方を基本とするか。変形を採る場合はその逸脱点と理由。`NFR-NNN` の保守性・拡張性に紐付けて正当化する。
  - **依存方向の原則**: 典型は「外側（プレゼンテーション・インフラ）→ 内側（ドメイン）」の一方向依存。逆向きの依存を解決する手段（依存性逆転 / インタフェースによる境界 / イベント駆動）の採用方針。循環依存の扱い（原則禁止、やむを得ない場合の記録ポリシー）。
  - **配置方針の段階的詳細化**: 本ドキュメントは **(a) レイヤ配置 → (b) 実行境界** の順に配置を決める。(a) で「ドメイン層／アプリケーション層／プレゼンテーション層／インフラ層」等のレイヤを割り当てたうえで、(b) で各モジュールが「プロセス内ライブラリ / プロセス内サービス / 別プロセス / 非同期ワーカー / バッチ / クライアント常駐 / フレームワーク提供」等のどの実行境界に置かれるかを決める。ディレクトリ・パッケージ構成（(c)）は**詳細設計に回す**。
  - **モジュール分割の基準**: 業務関心単位（例: 注文 / 請求 / 在庫）/ 技術関心単位（例: 認証 / ログ / メッセージング）/ 機能単位（例: ユースケース別）のいずれを基本とするか。混在するときの判定基準。
  - **業務ロジックの置き場**: 業務ルール（`BRU-NNN`）の主たる置き場をドメイン層に集約する方針。アプリケーション層はユースケース調整・トランザクション境界設定に徹し、インフラ層は永続化と外部連携に徹するといった役割分担。
  - **横断関心事の実装戦略**: ロギング / 認可 / トランザクション境界 / 入力バリデーション / エラー変換 / 監査記録 / リトライ制御 / レート制限 等について、**どのレイヤ**で**どのような方式**（明示呼び出し / ミドルウェア的な挟み込み / フレームワーク機構利用）で実装するかの方針。具体のアノテーション名・フック名は詳細設計。
  - **状態の置き場**: ステートフルなモジュールを許容するか、原則ステートレスとして状態は外部ストアに逃がすか。許容する場合の適用範囲（例: セッション保持・短命キャッシュ・長期状態）。
  - **再利用性の扱い**: 「プロジェクト固有 / 製品ライン共通 / 汎用ライブラリ化」の 3 段階のうち、どれを既定とし、どの基準で昇格・降格を判断するか。過剰な汎化を避けるための歯止め（例: 「2 箇所以上で使われるまでは固有のまま」）。
- 「流行っているから」「慣れているから」といった要件・アーキ・データ・IF に紐付かない方針は記載しない。

### 2. レイヤ構成
本章はモジュールの配置先として使うレイヤの定義である。プロジェクト共通の層構造を宣言することで、3 章以降の個別モジュールの所属先が一義に特定できるようになる。

- 採用するレイヤを `LYR-NNN` として表形式で列挙する。列: `LYR-NNN / レイヤ名 / 主な責務 / 参照してよいレイヤ（LYR-NNN） / 参照してはいけないレイヤ / 典型的に置かれるモジュール種別`。
- 典型的なレイヤ構成の例（プロジェクトの実情に合わせて採否を決める）:
  - **プレゼンテーション層**: 外部入出力の入口・出口。画面コントローラ / API ハンドラ / CLI エントリ / 音声・ボット受付 / 外部 SIF 受信口 など。主たる責務は「外部の形式」と「内部のコマンド / クエリ」の相互変換。
  - **アプリケーション層**: ユースケースの調整・トランザクション境界の設定・ドメインの組み立て。業務ルールそのものは持たず、ドメイン層のオブジェクトを呼び出して流れを作る。
  - **ドメイン層**: 業務ルール（`BRU-NNN`）の実装・エンティティ（`ENT-NNN` に対応する概念）・ドメインサービス・状態遷移制御。外部技術（フレームワーク・DB・HTTP）に依存しない。
  - **インフラ層**: 永続化（DB アクセス）/ 外部 API クライアント / メッセージング送受信 / ファイル I/O / ログ出力実装 / 時計・乱数などの副作用源。ドメイン層が定義したインタフェースを実装する側に回る（依存性逆転）。
  - **共有・横断層（必要な場合のみ）**: ログ構造 / 認可ポリシー / エラー型 / 共通バリデータなど、複数レイヤから参照される不変の型・値オブジェクト。乱用すると全体がここに依存して「神レイヤ」化するため、含める対象を厳選する。
- レイヤ間の依存方向は、表の「参照してよいレイヤ」「参照してはいけないレイヤ」列で一義に特定できるようにする。典型的なルールは「プレゼンテーション → アプリケーション → ドメイン」「インフラ → ドメイン（ドメイン側インタフェースの実装として）」「ドメイン → 他層を参照しない」。
- レイヤ構成を Mermaid `flowchart` で 1 枚描く。レイヤを `subgraph` で囲み、許容される依存方向を矢印で示す。層内のモジュールはここでは描かない（3 章以降で扱う）。
- レイヤ数を増やしすぎない。最初は 3〜5 層に抑え、どうしても分離が必要な関心事だけを層として追加する。層が多いほど境界越えのコストが上がるため、`NFR-NNN`（保守性 / 拡張性 / 応答性能）との整合を 6.2 代替案で必ず検討する。

### 3. モジュール一覧
- システムを構成する論理モジュールを表形式で列挙する。列:
  - `MOD-NNN / 名称 / 所属 COMP（COMP-NNN） / 所属レイヤ（LYR-NNN） / 実行境界種別 / 主な責務 / 主に保有する ENT / 主に提供する API / 主に扱う UI・SIF / 関連 UC / 再利用性`
- `MOD-NNN` は本ドキュメントで新規採番する。採番は `MOD-001` から始め、追加時は最大値の次を採る。廃止するものはステータス「廃止」で残すかプロジェクトのポリシーに従う。
- **1 つの MOD は 1 つの COMP-NNN に所属**する。複数 COMP をまたぐ役割を持つように見えるものは、通常は「共有コード用の COMP」がアーキ側に必要な兆候である。アーキ側に該当 COMP がなければ、本ドキュメントで新規に MOD を置かず、6.1 リスクとして記録し、アーキ側の追加を促す。
- **1 つの MOD は 1 つの LYR-NNN に所属**する。責務が複数レイヤに跨るように見える MOD は、通常はレイヤ境界でさらに分割する候補である（例: 「注文サービス」を「アプリケーション層の注文ユースケース」と「ドメイン層の注文集約」に分ける）。
- **実行境界種別**は以下の種別レベルで記述する。具体のランタイム・コンテナ・プロセス管理は**インフラ設計に回す**。
  - **プロセス内ライブラリ**: 同一プロセス内で関数／メソッド呼び出しで使われる。状態を持たないのが基本。
  - **プロセス内サービス（インスタンス）**: 同一プロセス内でオブジェクトとして生存し、状態や接続を保持する。DI で注入される典型像。
  - **別プロセス・同ホスト**: 同一ホスト上で別プロセスとして動く。IPC 経由で呼ばれる。
  - **別プロセス・別ホスト**: 別ホストの別プロセスとして動く。ネットワーク経由で呼ばれる（`LNK-NNN` のプロトコルに乗る）。
  - **非同期ワーカー**: キュー・イベントを起点に起動される常駐プロセス。ユーザ応答時間に含まれない。
  - **スケジュールバッチ**: 時刻・頻度起点で起動される。ジョブ単位で完結する。
  - **クライアント常駐**: 利用者端末（ブラウザ / モバイル / デスクトップ）側で動く。通信は API 経由。
  - **フレームワーク・ランタイム提供**: 自前で実装せず、フレームワークやランタイムに委ねる（例: ルーティング・セッション・基本バリデーション機構）。責務の所在を明示するために一覧には残す。
  - **外部 SaaS・サードパーティ**: 自前実装しない外部依存。原則アーキ側で `COMP-NNN` として既に識別されているはずなので、一覧にはその COMP 配下の「受付 MOD」「呼出 MOD」などを本システム側に置いて扱う。
- 「主に保有する ENT」列と「主に提供する API」列は代表値で可。全量の割り当ては 4 章「各モジュール詳細」と 5 章「依存関係」で担保する。
- 「再利用性」は「プロジェクト固有 / 製品ライン共通 / 汎用ライブラリ化」の 3 区分で記載し、1 章の方針と整合させる。

### 4. 各モジュール詳細
各モジュールについて、以下のサブテンプレートで詳細を記述する。すべての MOD で同じテンプレートに沿って書く（該当なしの節は「該当なし」と明記し、省略しない）。

`#### MOD-NNN 名称`

- **概要**: 何をするモジュールか、1〜2 文。関連 `UC-NNN`・`COMP-NNN`・`LYR-NNN` を明記する。
- **責務**: 「〜する。一方、〜はここでは行わず、MOD-YYY に委譲する」の形で、引き受けることと引き受けないことをセットで書く。責務の曖昧さは後工程の最大の事故要因なので、境界を明示する。
- **入力契約**: このモジュールが外から受け取る呼び出し／イベントを列挙する。典型: 上位 MOD からの関数呼び出し / `API-NNN` のリクエストハンドラとしての受付 / `UI-NNN` の画面イベント処理 / キュー・トピックからのメッセージ受信 / スケジュール契機での起動 / 外部 `SIF-NNN` からのファイル・API 受信。呼出元が複数ある場合はすべて列挙する。
- **出力契約**: このモジュールが外に出すもの。典型: 下位 MOD への呼び出し / `API-NNN` のレスポンス生成 / 外部 `SIF-NNN` への送信 / イベント発行 / ログ・監査記録の出力 / `ERR-NNN` の伝播。
- **保有するデータ（ENT-NNN）**: このモジュールが CRUD 責務を持つ `ENT-NNN` を列挙する。状態遷移を駆動する責務を持つエンティティもここに含める。**1 つの ENT の主責務 MOD は原則 1 つ**とし、読み取りのみの他 MOD がいる場合は下の「参照するデータ」に分けて記述する。
- **参照するデータ（ENT-NNN）**: 読み取り専用で参照する `ENT-NNN` を列挙する。参照方法（共有ストレージ直読 / 所有 MOD への問い合わせ / キャッシュ経由）を一言添える。参照方法が「他 MOD の保有ストレージを直接読む」形になっている場合、境界侵食のリスクとして 6.1 に記録する。
- **関連するインタフェース（API / UI / SIF / HIF / CIF）**: このモジュールが提供側・消費側のどちらでどの I/F に関わるかを、`API-NNN` / `UI-NNN` / `SIF-NNN` / `HIF-NNN` / `CIF-NNN` の ID で列挙する。`API-NNN` を提供する側の場合は「ハンドラとして受け付ける」「ドメイン呼び出しに委譲する」といった責務の深さも書く。
- **対応する横断関心事**: ロギング / 認可 / トランザクション境界 / 入力バリデーション / エラー変換 / 監査記録 / リトライ制御 / レート制限のうち、このモジュール内で実装するものと、他レイヤ・他モジュールに委ねるものを区別して記述する。1 章の全体方針を必ず参照し、特例を置く場合は理由を明記する。
- **対応するエラー（ERR-NNN）**: このモジュールが**生成する** `ERR-NNN`、**変換・ラップする** `ERR-NNN`（下層のエラーを業務エラーに置き換える等）、**通過させる** `ERR-NNN`（上位に委ねる）を区別して列挙する。IF 側の `ERR-NNN` カタログと齟齬がないか確認する。
- **実装するバリデーション（VR-NNN）**: IF 側で `VR-NNN` として定義されたバリデーションのうち、このモジュールで実装する範囲を列挙する。1 章で決めた「UI 側 vs サーバ側」の責務分離と整合させる。
- **状態**: ステートレス / ステートフルのいずれか。ステートフルの場合は保持する状態の粒度（リクエストスコープ / セッションスコープ / 長期保持）と、保管位置（モジュール内メモリ / 外部ストア経由）を明示する。
- **実行境界の理由**: 3 章で割り当てた実行境界種別を選んだ理由を一文で書く。非機能要件（応答性能・可用性・拡張性）との紐付けを示す。
- **再利用性の想定**: プロジェクト固有 / 製品ライン共通 / 汎用ライブラリ化のうちどれか、そう判断した根拠（実利用箇所の数・期待される利用範囲）。
- **変更影響範囲の想定**: このモジュールの内部実装を変えたときに影響が波及する他 MOD の想定（典型: 直接依存している MOD のみ、または契約変更時のみ影響）。波及が広い場合は 6.1 リスクに記録する。
- **備考**: 論理モジュール構造レベルの補足のみ。クラス分解・メソッドシグネチャ・DI 具体構成は詳細設計に回す。

### 5. 依存関係
- モジュール間および「モジュール → 外部（COMP 境界越え）」の依存関係を表形式で列挙する。列:
  - `DEP-NNN / 依存元 MOD / 依存先（MOD-NNN または 外部 COMP-NNN / 外部 SIF-NNN） / 依存種別 / 依存の強さ（契約依存 / 実装依存） / 置換可能性 / 関連 LNK-NNN`
- `DEP-NNN` は本ドキュメントで新規採番する（`DEP-001` から）。
- **依存種別**は以下の種別レベルで記述する。具体のライブラリ機構・プロトコル実装は詳細設計・インフラ設計。
  - **同期呼出**: 関数呼び出し・同期 API 呼び出し。呼出先の完了を待つ。
  - **非同期呼出**: イベント発行・キュー送信・通知。呼出先の完了を待たない。
  - **イベント購読**: 他モジュールの発行したイベントを受ける。結合は疎だが時間的順序は保証されない。
  - **共有ストレージ経由**: DB・キャッシュ・共有ファイルを介する間接的な依存。所有権の境界を越える場合は 6.1 リスクに記録する。
  - **設定注入**: 起動時に上位から設定値を受け取る（初期化時の一方向依存）。
  - **型・契約参照のみ**: インタフェース定義・DTO 型の参照のみで、実装依存を持たない。
- **依存の強さ**は、「契約依存（公開インタフェースにのみ依存）」と「実装依存（内部実装や副作用に依存）」を区別する。実装依存は変更影響を広げるので、理由と許容範囲を明記する。
- **置換可能性**は、依存先を差し替えられるか（依存性逆転・ポート・アダプタ化の対象か）を「高 / 中 / 低」で評価する。低い場合は変更影響範囲が広がる兆候として 6.1 に連動させる。
- COMP 境界を越える依存（`DEP-NNN` の依存先が外部 `COMP-NNN`）は、アーキ側の `LNK-NNN` の発側／受側の展開として整合する必要がある。`LNK-NNN` に存在しない通信経路の `DEP-NNN` は、アーキ側に戻ってリンクを追加するか、本 DEP を見直す。
- **モジュール依存図**を Mermaid `flowchart` で 1〜2 枚描く。矢印の向きは依存方向（「A → B」は「A が B に依存する」）とする。レイヤ別に `subgraph` で分けると層間の越境が可視化しやすい。図の粒度は MOD-NNN 単位で、クラス・関数まで降りない。
- **循環依存は原則禁止**。見つかった場合は分割（責務の共通部分を抽出して 3 つ目の MOD に切り出す）・方向反転（依存性逆転）・イベント化（時間的疎結合）のいずれかで解消する。やむを得ず残す場合は、理由と影響範囲を 6.2 代替案で合理化し、6.1 リスクでも影響を記録する。

### 6. 注意事項
注意事項は単一の表ではなく、以下 3 区分で整理する。混在させると読み手の対応先が曖昧になる。

#### 6.1 リスク・懸念点
- `RISK-NNN / 内容 / 影響範囲（MOD / DEP / LYR / 業務） / 顕在化条件 / 暫定対応 / 詳細設計・インフラ設計への申し送り`
- 典型カテゴリ:
  - 業務ルールの散逸（同じ `BRU-NNN` が複数 MOD に実装されている）
  - ドメイン層へのインフラ依存混入（DBMS 固有機能・HTTP 型・フレームワーク型がドメインに持ち込まれている）
  - 「神モジュール」化（責務が肥大化し、変更時の影響範囲が広い MOD）
  - レイヤ境界の侵食（プレゼンテーションにドメインロジック、インフラにアプリケーション処理が混入）
  - 他 MOD 保有データの直読（共有ストレージ経由で他 MOD の ENT を直接読む）による所有権境界の曖昧化
  - 循環依存の潜在（現状は無くても、ある変更を受けると発生する兆候）
  - 横断関心事の実装位置不統一（ロギング／認可／トランザクションが MOD ごとに独自実装されている）
  - 状態を持つ MOD の境界が不明確（リクエストまたぎで意図せず状態が残る可能性）
  - 再利用期待と実態の乖離（「共通化する」と宣言したが 1 箇所でしか使われていない、またはその逆）
  - 変更影響範囲の見立てが楽観的（実際はもっと広い範囲に波及する）
  - 実行境界の選択が非機能要件と不整合（応答性能要件に対して同期呼出の連鎖が深い、等）
  - 要件未確定のまま進めた前提

#### 6.2 代替案と採らない理由
- 主要なモジュール構造判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`。
- 最低でも以下の論点については検討の痕跡を残すことを推奨する。該当しなければ「検討不要と判断した理由」を 1 行で記す。
  - **レイヤリング方式**: 伝統的レイヤード vs Clean Architecture vs Hexagonal vs オニオン
  - **モジュール分割の軸**: 業務関心単位 vs 技術関心単位 vs 機能（ユースケース）単位
  - **実行境界の選択**: 同期呼出 vs 非同期ワーカー vs バッチ vs フレームワーク提供
  - **横断関心の実装方式**: 明示呼び出し vs ミドルウェア的な挟み込み vs フレームワーク機構
  - **状態の置き場**: モジュール内保持 vs 外部ストア集約 vs セッション
  - **再利用粒度**: プロジェクト固有 vs 共通ライブラリ化（2 箇所以上で使われるまで昇格しない等の歯止め）
  - **循環依存の解消手段**: 分割による抽出 vs 依存性逆転 vs イベント駆動化
  - **保有 ENT の境界**: 1 ENT を 1 MOD 専有 vs 複数 MOD 協調保有（分散トランザクションを誘発しやすいので慎重判断）
- 詳細設計寄りの判断（クラス分解・DI 具体構成・命名規則）は本章では取り上げず、詳細設計の代替案検討で扱う。インフラ寄りの判断（プロセス集約・デプロイ単位）は本章では取り上げず、インフラ設計の代替案検討で扱う。

#### 6.3 後続工程への申し送り事項
- 本コンポーネント設計では決め切らない論点を、**工程別**に分けて記録する。

**詳細設計（機能・画面単位 / クラス分解 / フレームワーク適用）への申し送り**: 表形式で記載。列: `HO-D-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- クラス図・インタフェース定義・メソッドシグネチャ
- DI コンテナ構成・スコープ・初期化順序
- ディレクトリ・パッケージ命名規則（具体名）
- フレームワーク固有機構（アノテーション・デコレータ・フック）の具体適用
- ORM マッピング・リポジトリ実装・トランザクションマネージャの具体

**インフラ設計への申し送り**: 表形式で記載。列: `HO-I-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- デプロイ単位（どの MOD 群を 1 プロセス／コンテナにまとめるか）

## 図解の記法ルール
要件定義書・アーキテクチャ設計書・データ設計書・インタフェース設計書と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。

- レイヤ構成図: `flowchart` / `graph`
  - レイヤを `subgraph` で囲み、許容される依存方向を矢印で示す。層内の個別モジュールはここでは描かない（3 章以降で扱う）。
- モジュール依存図: `flowchart` / `graph`
  - 矢印は依存方向（A → B は「A が B に依存」）。レイヤ別に `subgraph` で分けると境界越えが可視化される。
  - 粒度は MOD-NNN 単位に留め、クラス・関数まで降りない。
  - COMP 境界を越える依存は、外部 COMP を `subgraph` で明示し、アーキ側の `LNK-NNN` との対応を添える。
- 代表的なユースケースの実行フロー: `sequenceDiagram`
  - 典型的な 1〜3 ユースケースについて、モジュール間の呼出順序を描く。アーキ側や IF 側の `sequenceDiagram` と齟齬がないか確認する（MOD 粒度に分解した結果、線の数が増えるのは自然）。
  - 起点は画面・API ハンドラ・外部 SIF 受信・スケジュール契機のいずれでもよい。
- 状態を持つモジュールの状態遷移: `stateDiagram-v2`
  - ステートフル MOD が業務的に意味を持つ状態を取る場合に使う。ENT の状態遷移（データ設計側）と責務を重複させないため、MOD の「内部オブジェクトの生存ライフサイクル」など、データ側では表現されない状態のみをここで扱う。
- 構造の俯瞰が必要な場合の C4 的な補助図は任意。ただし本ドキュメントは論理構造が主目的のため、物理配置（リージョン・AZ 等）は描かない（インフラ設計で表現する）。

## ID 体系
本ドキュメント内で採番・参照する ID は以下。

- `MOD-NNN` モジュール（**本ドキュメントで新規採番**。`MOD-001` から）

- `RULE-NNN`（データ側）
- `API-NNN` / `UI-NNN` / `SIF-NNN` / `HIF-NNN` / `CIF-NNN` / `ERR-NNN` / `VR-NNN`（インタフェース側）

## 要件定義書・アーキテクチャ設計書・データ設計書・インタフェース設計書との紐付け
- すべての `MOD-NNN` は、1 つの `COMP-NNN`（アーキ側）に所属する。所属先が無い MOD は、アーキ側に該当 COMP が未定義である兆候なので、アーキ側に戻って追加するか、本 MOD の必要性を再検討する。
- すべての `MOD-NNN` は、1 つの `LYR-NNN` に所属する。所属できない MOD は、2 章のレイヤ構成が不足しているか、MOD の責務が複数レイヤをまたいで肥大化している兆候なので、分割または層の追加を検討する。
- すべての `MOD-NNN` は、少なくとも 1 つの `UC-NNN` または `NFR-NNN` に紐付けて「なぜ必要か」を説明できる状態にする。紐付かない MOD は過剰設計の疑いがあるため、6.2 代替案で不採用として整理するか、必要性の根拠（典型: 運用補助・監視・共有基盤）を追記する。
- すべての `ENT-NNN`（データ側）は、**保有責務を担う MOD-NNN が 1 つ**本ドキュメントに存在することを確認する。複数 MOD で協調保有する場合は、協調の整合を 6.1 リスクに記録し、`RULE-NNN`（データ側整合性ルール）の実装責務位置を明示する。
- すべての `API-NNN`（IF 側）は、**ハンドラ責務を担う MOD-NNN が 1 つ**本ドキュメントに存在することを確認する。複数存在する場合は、責務分担（プレゼンテーション層で受けてアプリケーション層に委譲、等）をモジュール詳細で明示する。
- すべての `UI-NNN`（IF 側）について、そのイベント処理責務・出力整形責務を担う MOD が特定できることを確認する（クライアント常駐のモジュールになる場合もあり）。
- すべての `SIF-NNN`（IF 側）について、送信責務・受信責務を担う MOD がそれぞれ特定できることを確認する。
- すべての `VR-NNN`（IF 側）について、実装を担う MOD が特定できることを確認する。IF 側で「UI 側と API 側で二重検証」と決めた VR は、その両側にそれぞれ実装担当 MOD が割り当たる。
- すべての `ERR-NNN`（IF 側）について、生成元 MOD・変換経路の MOD・最終提示を担う MOD が追跡できることを確認する。
- すべての `LNK-NNN`（アーキ側）について、本ドキュメントの `DEP-NNN` のいずれかと対応することを確認する。対応しない LNK は、モジュール分割が COMP 内部に閉じすぎているか、アーキ側のリンクが不要になった兆候。
- すべての `RULE-NNN`（データ側）について、実装責務を担う MOD（多くはドメイン層）が特定できることを確認する。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を「6. 注意事項」に明記して残すほうがよい。

### 1. 責務の重複と空白がないか
- すべての `BRU-NNN` の実装責務を担う MOD が 1 つ以上存在し、複数 MOD に散らばっていないか（散らばる場合は意図的か偶発か判別）。
- すべての `UC-NNN` の調整（トランザクション境界・例外フロー制御）を担うアプリケーション層 MOD が特定できるか。
- 「誰もやらない」責務が残っていないか。特にエラー変換・監査ログ記録・横断バリデーションは、方針で決めた層に担当 MOD が必ず存在するか。
- 同じ業務動作（例: 「注文確定」）について、複数 MOD がそれぞれ独自に実装していないか。共通化済みならその集約先 MOD が一意に特定できるか。

### 2. 循環依存がないか
- 依存図（5 章）上で循環が生まれていないか。ツール支援で確認できない場合でも、「A → B → A」の形を目視で追う。
- 「現状は循環していないが、方針を一歩踏み外すと循環する」兆候（相互参照の誘惑がある箇所）を 6.1 リスクに記録しているか。
- やむを得ず循環を残している場合、6.2 代替案で分割／依存性逆転／イベント駆動化が検討されたうえで不採用の理由が明記されているか。

### 3. ドメインとインフラの分離が保たれているか
- ドメイン層の MOD に、DBMS 固有機能・HTTP 型・フレームワーク固有型・特定ライブラリ型が混入していないか。混入が発見されたら、依存性逆転（ドメイン側にインタフェースを置き、インフラ側で実装）で切り離せないかを検討する。
- アプリケーション層 MOD が、ドメイン層を飛ばしてインフラ層に直接業務判断を委ねていないか。
- ドメイン層以外に業務ルール（`BRU-NNN`）が埋め込まれていないか（典型: バリデーションと業務ルール判定が UI / コントローラに混在）。

### 4. 横断関心の実装位置が統一されているか
- ロギング / 認可 / トランザクション境界 / 入力バリデーション / エラー変換 / 監査記録 / リトライ制御 / レート制限のそれぞれについて、1 章の方針どおりの層・方式で実装されているか。
- 例外的に個別 MOD で独自実装しているものがあれば、その理由と影響範囲が明記されているか。
- トランザクション境界は **1 ユースケースにつき明確に 1 箇所**で設定されているか（典型: アプリケーション層のユースケース MOD で開始・確定）。

### 5. 変更影響範囲の局所化
- 典型的な変更シナリオ（例: 「画面に項目を 1 つ追加」「外部 SIF のレイアウト変更」「決済 SaaS の切り替え」）について、影響が及ぶ MOD の集合が小さく収まる構造になっているか。
- 影響範囲が不当に広い MOD があれば、責務分割候補として 6.1 リスクに記録しているか。
- 依存性逆転が必要なのに行われていない箇所（置換可能性が「低」の実装依存）について、`NFR-NNN`（保守性・拡張性）との緊張関係が明示されているか。

### 6. 粒度の侵食が起きていないか
- **下向きの侵食**（本ドキュメントに詳細設計が紛れている）: クラス名・メソッドシグネチャ・DI コンテナ具体構成・ディレクトリ命名・フレームワーク具体機構・ORM マッピング詳細・ログフォーマット具体・バリデーションメッセージ文面などが紛れていないか。紛れていたら「6.3 詳細設計への申し送り」に切り出す。
- **横向きの侵食（データ設計）**: `ENT-NNN` の属性定義や `RULE-NNN` の制約内容を本ドキュメントで再定義していないか。データ設計を参照するに留める。
- **横向きの侵食（インタフェース設計）**: `API-NNN` のリクエスト／レスポンス項目や `VR-NNN` のバリデーション条件、`ERR-NNN` のカタログを本ドキュメントで再定義していないか。IF 側を参照するに留める。
- **横向きの侵食（アーキテクチャ設計）**: `COMP-NNN` の追加・削除や `LNK-NNN` の同期／非同期境界の再定義を本ドキュメントで行っていないか。必要ならアーキ側に戻る。
- **インフラ設計の侵食**: デプロイ単位・プロセス集約・コンテナ構成・ランタイム具体・スケール設定が紛れていないか。紛れていたら「6.3 インフラ設計への申し送り」に切り出す。
- **上向きの侵食**: 要件側に未定義の業務ルールや新しい UC・NFR が、本ドキュメントで黙って発生していないか。発生していたら「6.1 リスク・懸念点」に記録し、要件側への波及候補とする。
- **空洞化**: 論理モジュール構造粒度で決めるべき話（レイヤ配置・実行境界・依存方向・横断関心の実装位置・ENT 保有責務・エラー変換経路）が「詳細設計で決める」に丸投げされていないか。ここで決め切る。

### 7. 図と表の整合
- レイヤ構成図に登場するレイヤが、すべて「2. レイヤ構成」の `LYR-NNN` 表に存在するか。
- モジュール一覧（3 章）に登場する MOD が、4 章「各モジュール詳細」にもれなく存在するか。
- 依存図（5 章）に登場する矢印が、すべて `DEP-NNN` 表に存在するか。
- `sequenceDiagram` に登場する MOD が、3 章の一覧に存在するか。
- 各 MOD 詳細で参照している `COMP-NNN` / `LYR-NNN` / `ENT-NNN` / `API-NNN` / `UI-NNN` / `SIF-NNN` / `ERR-NNN` / `VR-NNN` / `RULE-NNN` / `UC-NNN` / `NFR-NNN` / `BRU-NNN` が、それぞれの出典ドキュメントに実在するか（採番ミスがないか）。
- 1 章で「採用する」と宣言したレイヤリング方式・実行境界種別・横断関心の実装戦略が、2〜5 章の個別記述と矛盾していないか。
