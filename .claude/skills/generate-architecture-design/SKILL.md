# アーキテクチャ設計の作成
要件定義書および入力資料から、基本設計の起点となるアーキテクチャ設計書を作成してください。

## Goal
要件に対して過不足の少ないシステム構成案を示す。

「過不足が少ない」とは、要件を満たすために必要な構成要素は欠かさず、一方で現時点の要件では正当化できない構成要素（過剰な冗長化・未利用のミドルウェア層・想像上のスケール対応など）は含めない、という意味である。判断に迷ったら、対応する要件 ID（UC-NNN / NFR-NNN など）に紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて代替案セクションで記録する。

## 位置付け（要件定義・詳細設計・インフラ設計との関係）
本スキルは `/generate-requirements` の成果物を主な入力とし、詳細設計・実装の出発点となる**論理構成レベル**の合意を作る。

- 上流: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 特に各 `usecase.md` 末尾の「設計工程への申し送り事項」を拾い、論理構成レベルで答えられるものには本ドキュメントで回答する。構成粒度で答えられない（例: 個別 API の項目定義）ものは、本ドキュメントでは「詳細設計への申し送り」として保持する。
- 下流（機能 / 画面単位）: `docs/design/` 配下の機能単位・画面単位の詳細設計。
- 下流（インフラ）: 物理配置・ネットワーク構成・クラウド具体サービス・冗長化方式・CI/CD は**別工程（インフラ設計）で扱う**。本スキルでは触れない。本ドキュメントはインフラ設計の前提となる「どのコンポーネントをどの責務境界に置くか」までを示し、インフラ担当者はそれを実環境へ落とし込む。

## Focus（このスキルが扱う範囲）
このスキルは以下に集中する。いずれも**論理レベル**の話であり、実環境への落とし込みは対象外。
- 利用者 / クライアント / バックエンド / DB / 外部サービスの**論理的な配置**
- 責務分離（どの関心事をどのコンポーネントに置くか）
- 同期 / 非同期の境界（どこで疎結合化するか、どこまで応答時間に含めるか）
- セキュリティ・可用性・運用を踏まえた**論理構成判断**（認証認可の責務位置、ログ / 監視の収集点、外部サービス障害時のフォールバック責務）

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、アーキテクチャが定まった後の工程（詳細設計・インフラ設計）で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**詳細設計（機能 / 画面単位）で決める**
- 詳細なテーブル定義（カラム・型・制約・索引・正規化形）
- 個別 API の項目レベル仕様（エンドポイント別のリクエスト / レスポンス項目）
- 画面部品の細かい UI（レイアウト・配色・コンポーネント分割）
- 実装クラス詳細（クラス図・メソッドシグネチャ・DI 構成）

**インフラ設計で決める**
- 物理配置（リージョン / アベイラビリティゾーン / データセンタ）
- ネットワーク構成（VPC / サブネット / セキュリティグループ / ファイアウォール / LB / 踏み台 / VPN / 専用線）
- クラウドの具体サービス選定・インスタンスタイプ・スペック・台数・スケール設定
- 冗長化の実装方式（Active-Active / Active-Standby の具体構成、フェイルオーバー機構）
- CI/CD・IaC の具体構成
- バックアップ・監視の具体製品・エージェント構成

例外: 上記に属する項目でも、論理構成判断に直結する場合（例: 「SSO を使うため認証プロバイダ側で払い出される claim を利用する」「外部 SaaS の利用が規制上確定している」）は、アーキテクチャ上の前提として最小限言及する。ただしインフラ具体（リージョン名・サービス名・台数）には踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。
- 追加で $ARGUMENTS にファイルパス・テキストが渡された場合はそれを併用する。
- 要件定義書が存在しない場合は、入力で与えられた素材から暗黙的に要件を抽出したうえで、アーキテクチャ判断の根拠を明示する（抽出した暗黙要件は末尾の「リスク・懸念点」に「要件未確定として進めた前提」として記載する）。

## 出力ファイル
- `docs/design/architecture/architecture.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: アーキテクチャ設計は「全体の辻褄」を読み手が 1 本の流れで検証できることが最重要であるため。機能単位・画面単位の詳細設計は `docs/design/` 配下に機能・画面ごとのファイルとして別途配置し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「読み手が全体像 → 個別要素 → 関係性 → 採用理由 → 却下理由 → 懸念点」の順に理解できるよう意図しているため、順序は固定する。

1. 構成概要
2. 構成要素一覧
3. 主要な通信・連携
4. 採用理由
5. 代替案と採らない理由
6. リスク・懸念点

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/architecture-template.md`](templates/architecture-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. 構成概要
- システム全体を 1 段落（数文）で要約する。利用者 → クライアント → バックエンド → データストア → 外部サービスの典型的な流れを 1 本の動線として記述し、キーとなる設計方針（例: 「認証は IdP 集約」「注文確定は非同期キュー越し」）を 2〜3 点挙げる。
- 直後に Mermaid の **コンポーネント配置図**（`flowchart` または `graph`）を 1 枚置く。粒度はコンポーネント単位（責務単位）に留め、クラス・関数まで落とさない。外部アクター（利用者・他システム・運用者）はシステム境界の外に描く。システム境界は `subgraph` で表すが、**インフラ境界（リージョン / AZ / VPC / ネットワークゾーン）は描かない**。それはインフラ設計工程の成果物で表現する。
- 想定する前提・非前提（スコープ外）を箇条書きで明記する。

### 2. 構成要素一覧
- システムを構成するコンポーネントを表形式で列挙する。列: `COMP-NNN / 名称 / 区分（クライアント / API / ワーカー / DB / キャッシュ / メッセージング / 外部サービス 等）/ 主な責務 / 実行レイヤ / 関連 UC・NFR・SIF`。
- 各コンポーネントの「主な責務」は一文で、かつ「何をしないか」まで書き添える（例: 「注文確定処理を担う。在庫計算はここでは行わず、在庫サービスに委譲する」）。責務の曖昧さは後工程の最大の事故要因なので、境界を明示する。
- コンポーネント ID は `COMP-001` から採番する。以降の章ではこの ID で相互参照する。
- **実行レイヤ** 列は、そのコンポーネントが論理的にどの層で動くか（例: 利用者端末 / サーバサイド / データストア層 / メッセージング層 / 外部 SaaS / 自社運用システム）を記述する。**具体のクラウドサービス名・インスタンスタイプ・マネージドか自前運用かといったインフラ判断は書かない**（インフラ設計で決める）。ただし、SaaS 利用が要件上確定している場合（例: 「決済は外部 SaaS 利用」）は区分「外部サービス」として最小限記述する。

### 3. 主要な通信・連携
- コンポーネント間および外部サービスとの主要なやり取りを表形式で列挙する。列: `LNK-NNN / 発側 COMP / 受側 COMP or 外部サービス / 契機（ユーザ操作 / スケジュール / イベント 等）/ プロトコル（概要レベル：HTTPS / gRPC / メッセージング / ファイル 等）/ 同期 or 非同期 / 失敗時の扱い（リトライ / 補償 / DLQ / ユーザ通知 等）/ 関連 UC・SIF・CIF`。
- 代表的なユースケースについて、Mermaid の `sequenceDiagram` で主要フローを 1〜3 本程度図示する。要件定義書の `sequenceDiagram` と齟齬がないか確認する（構成要素で分解した結果、線の数が増えるのは自然）。
- 同期 / 非同期の境界を明示的に線引きする。特に「ユーザ応答時間に含まれる区間」はどこまでか（例: 決済確定まで同期 / 通知送信は非同期）を言語化する。

### 4. 採用理由
- 各主要コンポーネント・境界設計について、「なぜこの構成にしたか」を要件 ID と結びつけて記述する。形式: 箇条書きで「採用判断 → 紐付く要件 ID → 根拠（要件のどの条件を満たすため）」。
- 技術選択（特定のデータベース・ランタイム・SaaS 等）を伴う場合、以下を必ず明示する。
  - 決め手となった非機能要件（NFR-NNN）
  - 想定されるスケール・運用規模の前提（概算値で可、ただし出典または仮置きの根拠を明記）
  - 社内標準 / 既存資産 / 契約済みサービスなどの制約
- 「よく使われているから」「流行っているから」のような要件に紐付かない採用理由は記載しない。紐付けられない場合は、代わりに 5 章で代替案として整理する。

### 5. 代替案と採らない理由
- 主要な判断について、検討したが採らなかった案を表形式で記録する。列: `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件（どのような前提が変わったら再検討するか）`。
- 「再検討条件」は将来の保守性を左右する。例: 「利用者が想定の 10 倍になった場合」「外部 SaaS の SLA が現行より悪化した場合」「セキュリティ要件でデータの国外保管が禁止された場合」。
- 最低でも以下の論理設計上の判断については検討の痕跡を残すことを推奨する（該当しなければ「検討不要と判断した理由」を 1 行で）。
  - データストアの種別（関係モデル / ドキュメント / KVS 等）
  - 同期 / 非同期の境界
  - 認証認可方式（自前 / IdP 委譲 / ゲートウェイ集約）
  - 機能配置の切り分け（モノリス / サービス分割 / 外部 SaaS 利用）
- インフラ寄りの判断（クラウド / オンプレ、リージョン、具体サービス）は**インフラ設計工程の代替案検討で扱う**ため、本章では取り上げない。

### 6. リスク・懸念点
- 現時点で未解消のリスク・前提の脆さを列挙する。列: `RISK-NNN / 内容 / 影響範囲（COMP / LNK / 業務）/ 顕在化条件 / 暫定対応 / 詳細設計への申し送り`。
- リスクの典型カテゴリ: 外部サービス障害時のフォールバック、認証認可の責務境界、データ整合性（特に非同期境界をまたぐ場合）、運用・監視の死角、性能の見立て不確実性、移行時の新旧並行運用、法令・規制適合（データ所在地・保存期間）。
- 「要件未確定のまま進めた前提」もここに含める。確認先と、確認できなかった場合の最悪ケース影響を併記する。

## 図解の記法ルール
要件定義書と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。用途と推奨ダイアグラム:

- コンポーネント配置図 / 全体構成: `flowchart` または `graph`
  - 外部アクター（利用者 / 運用者 / 外部システム）をシステム境界の外に描き、境界を `subgraph` で明示する
  - 粒度は責務単位のコンポーネントに留め、クラス / 関数まで降りない
  - **インフラ境界は描かない**: リージョン / AZ / VPC / サブネット / ネットワークゾーン（公開網 / DMZ / プライベート）・LB / 踏み台・具体のクラウドサービスアイコンはアーキ設計書では描かない。これらはインフラ設計工程の成果物で表現する
- 主要フロー: `sequenceDiagram`
  - ユースケース単位で描く。要件定義書の同名 `sequenceDiagram` と齟齬がないか必ず照合する
- 状態を持つ主要コンポーネントが有限状態を取る場合: `stateDiagram-v2`

## ID 体系
本ドキュメント内で採番する ID は以下。要件定義書側の ID（UC / NFR / SIF など）はそのまま参照し、再採番しない。

- `COMP-NNN` 構成要素
- `LNK-NNN`  コンポーネント間 / 外部連携のリンク
- `ALT-NNN`  代替案
- `RISK-NNN` リスク・懸念点

一度採番した ID は変更しない。削除された要素は表から消さず、ステータスを「廃止」としてトレーサビリティを残す方針でもよい（プロジェクトのポリシーに従う）。

## 要件定義書との紐付け
- すべての `COMP-NNN` は、少なくとも 1 つの UC-NNN または NFR-NNN に紐付けて「なぜ必要か」を説明できる状態にする。紐付かないコンポーネントは過剰構成の疑いがあるため、5 章の代替案 / 不採用として扱うか、必要性の根拠を追記する。
- すべての `LNK-NNN` は、少なくとも 1 つの UC-NNN・SIF-NNN・CIF-NNN のいずれかに紐付ける。
- 要件定義書の SIF-NNN / HIF-NNN / CIF-NNN に対応する構成要素・リンクが本ドキュメントに存在することを確認する。存在しない場合は構成漏れ。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を明記して残すほうがよい。

### 1. クライアントとサーバ責務が曖昧でないか
- クライアント（ブラウザ / モバイル / デスクトップ）とサーバ（API / ワーカー / 外部サービス）のどちらが何を担うかを、構成要素一覧の「主な責務」列で一義に特定できるか。
- 特に以下が曖昧になりやすいので意識的にチェックする: 入力バリデーション（クライアント側の UX 用 vs サーバ側の正当性検証）、認可判定、機微情報の保持、日時生成（クライアント時刻 vs サーバ時刻）、集計・ソート。

### 2. 外部サービス障害時の影響範囲が見えるか
- 依存する外部サービス（SaaS / IdP / 決済 / メール / 通知 等）ごとに、その停止・遅延が「どのユースケースをどこまで劣化させるか」を RISK-NNN として記述しているか。
- 非同期境界（キュー・イベント）で分離されているものは「最悪ケースで X 分の反映遅延」のような具体的影響まで書けているか。
- フォールバック（縮退運転）の有無と、縮退時の利用者通知方針まで言及しているか。

### 3. 認証認可の責務位置が明確か
- 認証（真正性確認）をどのコンポーネントが担うか（自前 / IdP 委譲 / ゲートウェイ集約）が構成要素一覧で特定できるか。
- 認可判定（権限チェック）が複数箇所に分散していないか。分散するならその境界（例: エッジでは粗粒度 / サービス層で細粒度）が明示されているか。
- セッション / トークンの保管場所と有効期間の「考え方」が記載されているか（具体値は詳細設計でよいが、方式は構成要素に関わる）。
- 要件定義書のセキュリティ系 NFR-NNN（A-6 / 真正性 / 責任追跡性 等）と紐付いているか。

### 4. ロギング / 監視 / 運用観点が抜けていないか
- アプリケーションログ・アクセスログ・監査ログそれぞれが「どのコンポーネントで生成され、どの責務のコンポーネントに集約されるか」が論理構成として表現されているか（具体のログ基盤製品名・保管先ストレージはインフラ設計で決める）。
- 監視（リソース / アプリ / 業務 / 外形）について、**どこを観測すべきか・誰が受けるか**の責務位置が見えるか（監視基盤の製品選定はインフラ設計で決める）。
- デプロイ・バックアップ・ジョブ実行などの運用系処理が、運用者をアクターとしてコンポーネント配置図に登場するか、または別コンポーネントとして扱われているか。
- 非機能要件 (C) 運用・制約観点（NFR-NNN）の主要項目（SLA / 監視 / ログ / バックアップ / 運用時間帯）との紐付けに漏れがないか。目標値（稼働率・RTO / RPO 等）は要件側で定まっているが、それを**どのコンポーネントが担保するか**の責務割り当てをアーキ側で示す。実現方式（HA / DR の具体構成）はインフラ設計で決める。

### 5. 粒度の侵食が起きていないか
- **下向きの侵食**（アーキ設計書に詳細設計が紛れている）: テーブル設計・API の項目単位仕様・UI コンポーネント分解・クラス図のいずれかが紛れていないか。紛れていたら「詳細設計への申し送り」に切り出す。
- **横向きの侵食**（アーキ設計書にインフラ設計が紛れている）: リージョン / AZ / VPC / サブネット / セキュリティグループ / LB / 踏み台 / 具体のクラウドサービス名（例: ECS / RDS / S3 等）/ インスタンスタイプ / 台数 / スケール設定 / IaC 構成が紛れていないか。紛れていたら「インフラ設計への申し送り」に切り出す。
- **上向きの空洞化**: 論理構成粒度で決めるべき話が「詳細設計で決める」「インフラ設計で決める」に丸投げされていないか（特に同期 / 非同期境界、認証認可の責務位置、外部サービス障害時のフォールバック責務はここで決め切る）。

### 6. 図と表の整合
- system context 図に登場するコンポーネントが、すべて構成要素一覧（COMP-NNN）に存在するか。
- `sequenceDiagram` に登場する矢印が、主要な通信・連携表（LNK-NNN）に存在するか。
- 図にだけあり表にないもの、表にだけあり図にないものがないか。
