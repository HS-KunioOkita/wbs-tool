# インタフェース設計の作成
要件定義書・アーキテクチャ設計書・データ設計書を入力として、基本設計の起点となるインタフェース設計書を作成してください。

## Goal
画面・API・外部システム連携の**入出力契約**を、レビューとテスト設計に耐える粒度で示す。

「レビューとテスト設計に耐える粒度」とは、各インタフェースについて「誰から何を受け取り」「何を返し」「どういう値は受け付けないか」「失敗したときに何が起こるか」「誰の責務で処理されるか」までが、他ドキュメント（要件・アーキテクチャ・データ）と矛盾なく一義に読み取れる状態を指す。逆に、画面のピクセル配置や内部クラス構造、DBMS の物理型など、実装工程で変わりうる詳細は踏み込まない。判断に迷ったら、要件 ID（UC-NNN / UI-NNN / SIF-NNN / CIF-NNN / NFR-NNN）・構成要素 ID（COMP-NNN / LNK-NNN）・エンティティ ID（ENT-NNN / RULE-NNN）に紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて注意事項に記録する。

## 位置付け（要件定義・アーキテクチャ設計・データ設計・詳細設計・インフラ設計との関係）
本スキルは `/generate-requirements`、`/generate-architecture-design`、`/generate-data-design` の成果物を入力とし、詳細設計・実装の出発点となる**論理インタフェース契約**を固める。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - `functional.md` の「6. インタフェース要件」で粗粒度に列挙された `UI-NNN` / `SIF-NNN` / `HIF-NNN` / `CIF-NNN` を出発点とし、本スキルで入出力項目・バリデーション・エラー時の振る舞いまで肉付けする。
  - 各 `usecase.md` の「基本フロー・代替フロー・例外フロー」を、画面・API・外部連携の具体契約に写像する。フローに登場する入力項目・出力項目・分岐条件が、本ドキュメントのどこかで定義されていることを検証する。
  - 非機能要件（特に応答性能・可用性・セキュリティ・監視 NFR-NNN）を、タイムアウト・リトライ・認証認可・ログ出力の方針として具体化する。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - 構成要素 `COMP-NNN` と主要リンク `LNK-NNN` を参照し、各インタフェースが「どの COMP からどの COMP への通信か」「同期／非同期のどちらか」「失敗時の責務がどちら側にあるか」を決める根拠とする。
  - アーキ側で同期とされた境界上のインタフェースはユーザ応答時間に含まれる。非同期境界をまたぐものは、完了通知・再送・補償の責務配置を I/F 側で言語化する。
- 上流（データ）: `docs/design/data/data-design.md`
  - 画面・API で扱う論理項目は、データ設計のエンティティ `ENT-NNN` の属性または派生項目と対応が取れている必要がある。整合性ルール `RULE-NNN` は I/F 側バリデーションの根拠として参照する。
- 下流（詳細設計）: 機能単位・画面単位の UI レイアウト、API の項目レベル精密仕様（個別フィールドの命名規則 / JSON スキーマ例 / ページネーション具体値 / ORM マッピング）、個別バリデーションメッセージ文面、帳票の行列配置。
- 下流（インフラ設計）: 具体の API ゲートウェイ製品・WAF 設定・LB ヘルスチェック条件・TLS 証明書運用・VPN / 専用線・ネットワークタイムアウト値の実装。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**論理レベルの入出力契約**の話であり、UI の配色やクラス構造、物理ネットワーク構成には踏み込まない。

- 人間向けインタフェース（`UI-NNN`）: 画面・帳票・通知・CLI（コマンドライン）・音声（VUI / IVR）・チャット／メールボットなど、**人が発信者または受信者になる I/F** 全般。入力項目・出力項目・イベント（押下 / サブコマンド発行 / 発話意図 / メッセージ受信 等）と起動 API、画面間・対話間の遷移。
- API インタフェース: エンドポイント（メソッド＋論理パス）、目的、リクエスト項目、レスポンス項目、主要ステータス、冪等性・同時実行の扱い
- システム間インタフェース（`SIF-NNN`）: データ連携方式（ファイル／API／メッセージング）、レイアウト・項目、連携契機、失敗時の扱い、権威（正本）の所在
- ハードウェアインタフェース（`HIF-NNN`）: 機器（スキャナ / プリンタ / IC カードリーダ / センサ / カメラ 等）との接続方式、入出力データ形式、機器未接続・異常時の扱い。該当なしのプロジェクトでは「該当なし」を明記する
- バリデーション: 必須／形式／値域／業務制約、検証レイヤ（人間向け I/F 側／API／業務層）の責務割り当て
- エラー・例外: 発生源ごとのエラー種別、利用者向け表示・応答方針、ログ・監査・通知方針、回復動作
- 非機能の I/F 反映: タイムアウト値の**方針**（具体秒数は詳細設計でよいが、方針：同期かつ画面同期待ちは短め／バッチは長め、等）、リトライ可否・リトライ回数の方針、レート制限・同時実行制限の方針
- セキュリティ考慮: 認証・認可の責務位置、機微情報の扱い、入力の正規化・サニタイズ方針、出力のエスケープ方針、監査ログの取得点

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、I/F 契約が定まった後の工程で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**詳細設計（機能 / 画面・CLI・音声・ボット単位）で決める**
- 画面の UI レイアウト詳細（配色・余白・フォント・コンポーネント分割・アイコン）
- CLI のヘルプ文言・色付け・プログレス表示の具体仕様、サブコマンド階層の最終構造
- 音声 I/F の合成音声の声質・プロンプト文面・認識モデルのチューニング
- チャット／メールボットのメッセージ文面、リッチコンポーネント（カード・ボタン）の具体配置
- バリデーションメッセージの最終文言
- API の具体 JSON スキーマ・フィールド命名規則・シリアライズ形式（snake_case / camelCase 等）
- ページネーション・ソートの具体パラメータ名
- 内部クラス構造・DI 構成・メソッドシグネチャ
- 個別のキャッシュキー設計

**データ設計で決める（本ドキュメントでは参照のみ）**
- エンティティ・属性・論理型・PK / UK / FK の定義
- エンティティ横断の整合性制約（RULE-NNN）

**インフラ設計で決める**
- DBMS・API ゲートウェイ・WAF・LB の製品選定と具体設定
- TLS 設定値・暗号スイート・証明書運用
- ネットワーク経路・ファイアウォールルール・VPN / 専用線
- CDN 配信ルール・キャッシュ階層の物理配置

例外: 上記に属する項目でも、論理契約判断に直結する場合（例: 「外部 SaaS 側の既存 API 仕様が固定されておりリクエスト項目を変えられない」「監査要件でログ保存先が別系統に分離されることが確定している」）は、前提として最小限言及する。ただし具体設定値には踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。特に `functional.md` の「6. インタフェース要件」・各 `usecase.md` の基本／代替／例外フロー・「アクターがCRUDする情報」・非機能要件の応答性能／セキュリティ／監視項目。
- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）も既定の入力とする。存在すれば必ず参照する。特に `COMP-NNN` と `LNK-NNN`。
- データ設計書（`docs/design/data/data-design.md`）も既定の入力とする。存在すれば必ず参照する。特に `ENT-NNN` の属性定義と `RULE-NNN`。
- 追加で $ARGUMENTS にファイルパス・テキストが渡された場合はそれを併用する。
- 上流ドキュメントが存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえで、インタフェース判断の根拠を明示する（抽出した暗黙前提は「6. 注意事項」の「前提の脆さ」として記載する）。

## 出力ファイル
- `docs/design/interface/interface-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

1 ファイルに集約する理由: インタフェース設計は「画面 → API → データ → 外部連携」が 1 本の動線として辻褄を合わせることが最重要であるため。個別 API の精密スキーマや画面の詳細レイアウトは、詳細設計工程で機能単位・画面単位の別ファイルに展開し、本ファイルからリンクで繋ぐ。

## 出力順序（Output）
以下の見出し順で出力する。順序は「全体方針 → 俯瞰 → 個別契約 → 横串ルール → 未決事項」の順に理解できるよう意図しているため、固定する。

1. I/F 設計方針
2. インタフェース一覧
3. 各インタフェース仕様
4. エラー・例外方針
5. セキュリティ考慮
6. 注意事項

各章の具体的な記述ルールは次節「各章の書き方」を参照。必要ならテンプレート [`templates/interface-template.md`](templates/interface-template.md) をそのままコピーして埋めてよい。

## 各章の書き方

### 1. I/F 設計方針
- 本インタフェース設計全体を貫く方針を、箇条書きで 4〜8 点程度にまとめる。論理契約レベルの判断のみを扱い、具体の製品・コーデック・シリアライズ形式には踏み込まない。
- 典型的に書くべき方針:
  - **API 呼出様式**: REST / RPC / GraphQL / メッセージング のいずれを基本とするか。混在するときはその判定基準（例: 画面 → バックエンドは REST、ワーカー間はメッセージング）。
  - **人間向け I/F の種別適用方針**: 本システムで採用する人間向け I/F の種別（画面 / 帳票 / 通知 / CLI / 音声 / チャット・メール）を列挙し、それぞれの採用理由を要件 ID に紐付ける。採用しない種別は「採用しない」と明記する。CLI を採用する場合は「運用者向け / 利用者向け」のどちらか、音声・ボットを採用する場合は主チャネル（電話 / スマートスピーカー / メッセンジャ 等の種別）も示す。
  - **バリデーションの責務分離**: 人間向け I/F 側（UX 向上のためのクライアント検証）と API 側（業務正当性の最終判断）の役割分担。前者を通過してもサーバ側で再検証すること、逆に前者は「サーバで拒否される入力を未然に防ぐ UX」に徹すること、という位置付けを明示する。CLI・音声・ボットのように入力チャネルごとに表現力が異なる場合でも、サーバ側の検証が最終判断である原則は変えない。
  - **認証認可の位置**: アーキ側で決定された責務位置（IdP 委譲 / ゲートウェイ集約 / 自前）を再掲し、各 API に適用する方針を示す。公開 API（認証不要）と認証必須 API の区別が必要なら基準を明示する。
  - **エラー表現の統一**: エラー応答の構造方針（機械可読なコード＋人間可読なメッセージ＋詳細）を決め、すべての API で揃える旨を宣言する。コードの命名規則までは詳細設計で決めてよい。
  - **同期／非同期の境界適用**: アーキ側で決まった同期・非同期境界を、I/F 単位でどの側に含めるかを宣言する（例: 「注文確定 API は同期。通知送信は API 応答後に非同期発火」）。
  - **タイムアウト・リトライの基本方針**: 方針レベルに留める（例: 「画面同期 API は短め・リトライなし」「バッチ取り込みは長め・失敗時は取り込み単位で全体リトライ」）。具体秒数は詳細設計で確定するが、方針に沿った値が選ばれるよう上限／下限の考え方は示す。
  - **機微情報の取り扱い**: リクエスト・レスポンスに機微情報を含める場合のマスキング／ログ除外の原則。平文での授受可否を明示する。
  - **ファイル／帳票の文字コード・改行コードの原則**: `SIF-NNN` に関わる I/F で一貫させるための原則（例: UTF-8 BOM なし・LF）。既存システム都合で例外を置く場合は明示する。
- 「流行っているから」「慣れているから」といった要件・アーキ・データに紐付かない方針は記載しない。

### 2. インタフェース一覧
本章は俯瞰のためのカタログである。**I/F 種別ごとに別表**で列挙する。種別を混ぜると責任範囲・レビュー観点が変わるため。

#### 2.1 人間向けインタフェース一覧
- 要件定義書の `UI-NNN` をそのまま引き継ぎ、本ドキュメントではそのサブセットに入出力契約を肉付けする。`UI-NNN` は「人が発信者または受信者になる I/F」全般を包含するので、**画面・帳票・通知**に加え、**CLI（コマンドライン）・音声（VUI / IVR）・チャット／メールボット**などもここで扱う。表の列:
  - `UI-NNN / 名称 / 種別（画面 / 帳票 / 通知 / CLI / 音声 / チャット / メール / その他） / 対象利用者 / チャネル（ブラウザ / ダウンロード / メール / ターミナル / 電話 / スマートスピーカー / メッセンジャ 等） / 主な起動 API（API-NNN） / 関連 UC / 関連 ENT`
- **新規採番はしない**。要件側に未定義の人間向け I/F が必要になった場合は、要件定義書側に戻って `UI-NNN` を追加する（設計側で勝手に増やさない）。
- プロジェクトで採用しない種別があっても表から削らず、「該当なし」の注記を添えるか、1 章で採用しない旨を宣言して本節では省略する。採用方針の宣言と一覧の整合は、「Checklist」で確認する。

#### 2.2 API インタフェース一覧（API-NNN）
- 画面・バックエンド間、およびバックエンド間の API エンドポイントを表形式で列挙する。列:
  - `API-NNN / 名称 / HTTP メソッド / 論理パス / 目的 / 認証要否 / 同期・非同期 / 発側 COMP / 受側 COMP / 関連 UI・UC・SIF / 関連 LNK`
- `API-NNN` は本ドキュメントで新規採番する（要件側にはない概念）。採番は `API-001` から始め、追加時は最大値の次を採る。廃止するものはステータス「廃止」で残すかポリシーに従う。
- 論理パスはリソース指向で記述する（例: `POST /sales-plans` / `GET /sales-plans/{id}`）。バージョニング記法（`/v1/…`）を使うかは方針として 1 章で決めてよいが、URI の最終形は詳細設計で確定する前提でよい。
- 認証要否は「必須 / 不要 / 内部のみ（サービス間）」のいずれか。細かい権限判定は「5. セキュリティ考慮」で扱う。

#### 2.3 システム間インタフェース一覧
- 要件定義書の `SIF-NNN` をそのまま引き継ぎ、本ドキュメントで入出力レイアウト・契機・失敗時処理を肉付けする。表の列:
  - `SIF-NNN / 連携先システム / 連携方向 / 連携方式（ファイル / API / メッセージング） / 連携契機 / 想定頻度・概算データ量 / 同期・非同期 / 正本 / 関連 UC・UI・LNK`
- `SIF-NNN` は要件側と同一 ID 空間なので新規採番はしない。要件側で未定義のシステム間連携が発生したら要件定義書に戻って追加する。
- 「正本」列は「自システム / 外部システム / 双方で協調」のいずれかを記入する。マスタ変更時の権威を明示し、注意事項のリスクに連動させる。

#### 2.4 通信インタフェース一覧
- 要件定義書の `CIF-NNN` をそのまま引き継ぐ。`CIF-NNN` は通信経路（HTTPS / SDK 等）の粒度なので、本ドキュメントではそのまま再掲して紐付けを確認する表とする。列:
  - `CIF-NNN / 通信相手 / プロトコル / 暗号化・認証 / 本ドキュメントで紐付く API-NNN・SIF-NNN`
- `CIF-NNN` に紐付く I/F が本ドキュメントに存在しない場合、通信経路だけが浮いていることになるので、要件側またはアーキ側との整合を注意事項に記録する。

### 3. 各インタフェース仕様
各インタフェースについて、種別ごとのサブテンプレートで詳細を記述する。すべての I/F で同じテンプレートに沿って書く（該当なしの節は「該当なし」と明記し、省略しない）。

#### 3.1 人間向けインタフェース仕様（UI-NNN）

`UI-NNN` は「人が発信者または受信者になる I/F」全般を扱う。種別ごとに入出力モデルが違うため、以下のサブテンプレに沿って書く。本プロジェクトで採用しない種別は「該当なし（1 章で不採用と宣言）」と明記して省略する。

**共通の記法**:
- 論理型はデータ設計と同じ（文字列 / 整数 / 数値 / 真偽値 / 日付 / 日時 / 列挙 / 参照）を使う。DBMS 固有型は書かない。
- 対応 ENT・属性列は、データ設計書の `ENT-NNN.属性名` を記入する。紐付かない入力項目（表示・対話用の一時値）はその旨を明示する。
- 備考には論理契約レベルの補足のみ書く。見た目・文言・声質・ヘルプ文などの詳細は詳細設計に回す。

##### 3.1.1 画面仕様

`#### UI-NNN 名称（画面）`

- **概要**: 画面の目的・対象利用者・代表的なユースケース。関連 UC-NNN を明記する。
- **入力項目**: 表形式で列挙する。列: `項目名（論理） / 論理型 / 必須 / 既定値 / 値域・選択肢 / 対応 ENT・属性 / バリデーション ID（VR-NNN）`。
- **出力項目**: 表形式で列挙する。列: `項目名（論理） / 論理型 / 源泉（どの ENT / 派生ロジック / 他 API） / 空欄時の表示 / 概要`。画面上の列順・書式は詳細設計に回す。
- **画面イベントと起動 API**: 表形式で列挙する。列: `イベント（押下 / 変更 / 読込 / タイマ 等） / 起動 API（API-NNN） / 事前条件 / 事後の画面遷移 / 想定エラー（ERR-NNN）`。
- **画面間遷移**: どの画面から来るか・どの画面へ抜けるか。要件定義書の画面遷移図で示された流れとの整合を確認する。

##### 3.1.2 帳票仕様

`#### UI-NNN 名称（帳票）`

- **概要**: 帳票の目的・対象利用者・関連 UC-NNN。
- **抽出条件**: 対象期間・対象レコードの絞り込みパラメータ（画面起点なら対応する画面入力項目、バッチ起点ならスケジュールと既定パラメータ）。
- **出力項目**: 表形式で列挙する。列: `項目名（論理） / 論理型 / 源泉 / 空欄時の表現 / 概要`。並びの最終指定・列幅・書式は詳細設計に回す。
- **出力フォーマット**: CSV / Excel / PDF 等の**種別**と、必要ならそれぞれの使い分け条件。1 帳票で複数フォーマットを出す場合は、フォーマット別の差異（画像の有無・ページ区切りの意味）を記述する。
- **ファイル名規則の方針**: 可変部（対象年月・出力日時・利用者識別 等）と固定部の構成方針。最終命名規則は詳細設計で確定する。
- **文字コード・改行コード**: 1 章の原則に沿うか、逸脱する場合の理由。
- **大量件数時の扱い**: 件数上限・分割ダウンロードの方針。同期ダウンロードの上限と、超過時に非同期生成＋通知に切り替えるかの方針を示す。

##### 3.1.3 通知仕様

`#### UI-NNN 名称（通知）`

- **概要**: 通知の目的・送出契機・関連 UC-NNN。
- **チャネル**: メール / SMS / プッシュ通知 / 社内チャット 等の**種別**。具体の送信サービスはインフラ設計で決める。
- **宛先の決まり方**: 固定宛先 / ロール単位 / 利用者設定に従う / イベント主体に連動、のいずれか。宛先情報の源泉 ENT・属性を示す。
- **送出契機**: ユーザ操作後 / スケジュール / イベント駆動 / 閾値超過 のどれか。非同期境界をまたぐ場合の遅延許容を明示する。
- **本文の必須要素**: 差出人・件名の方針・本文に必ず含める情報項目（対象期間・操作リンク・相関 ID 等）を列挙する。最終文面は詳細設計。
- **再送・重複抑止**: 同一イベントに対する重複通知の抑止方針、失敗時の再送条件・回数の方針。
- **配信失敗時の扱い**: 宛先不達・外部サービス障害時の記録・再送・運用者通知の方針。

##### 3.1.4 CLI 仕様

`#### UI-NNN 名称（CLI）`

- **概要**: CLI の目的・対象利用者（エンドユーザ / 運用者 / 開発者）・代表的なユースケース。関連 UC-NNN を明記する。
- **呼出形式**: `command [subcommand] [options] [arguments]` の論理形を示す（具体のコマンド名は詳細設計で確定する方針でもよいが、サブコマンド階層の意味は本節で固める）。
- **サブコマンド一覧**（複数ある場合）: 表形式で列挙する。列: `サブコマンド / 目的 / 起動 API / 関連 UC`。
- **オプション（フラグ）一覧**: 表形式で列挙する。列: `論理名 / 論理型 / 必須 / 既定値 / 値域・列挙 / 対応 ENT・属性 / バリデーション ID / 概要`。短縮形・長形の命名規則は詳細設計で決めるが、意味は本節で固める。
- **位置引数一覧**: 表形式で列挙する。列と記法は上と同様。順序の意味を明示する。
- **標準入力（stdin）**: 利用するか、しない場合は明記。利用する場合は形式（行指向テキスト / JSON / CSV 等）と終端規約を示す。
- **出力**:
  - 標準出力（stdout）: 正常結果の出力形式の方針（人間可読 / 機械可読 / 両対応 `--json` 等）。
  - 標準エラー出力（stderr）: 進捗・警告・エラー情報の出力方針。人間可読と機械可読の切り替え条件。
  - ファイル出力がある場合はそのパスの決まり方。
- **終了コード**: 終了コード値の意味と `ERR-NNN` との対応を表形式で示す。少なくとも「正常終了 / 入力不正 / 認証失敗 / 業務エラー / 外部依存失敗 / 想定外の異常」の区別を持たせる。
- **対話挙動**: 対話プロンプト（確認 y/N / パスワード入力 等）の有無、TTY 以外では非対話に切り替える方針、`--yes` 等の非対話強制フラグの方針。
- **環境変数・設定ファイル**: 入力として解釈する環境変数の論理名・意味、設定ファイルの読み込み経路の方針（具体パスは詳細設計）。機微情報を環境変数で渡してよいか、ファイルに書いてよいかを明示する。
- **冪等性・副作用・dry-run**: 破壊的操作（削除・上書き・送信）を持つか、`--dry-run` 相当で副作用を抑止できるか、連続実行時の挙動。
- **認証・認可**: 利用者の同定方法（ログイン済みセッション参照 / トークンファイル / OS ユーザ連動 / サブコマンドで都度認証）と、権限判定の責務位置。
- **ログ・監査**: 機微情報を stdout / stderr / ログに含めない原則の再掲と、監査要件（NFR-NNN）で取得すべき操作の対応。

##### 3.1.5 音声インタフェース仕様（VUI / IVR）

`#### UI-NNN 名称（音声）`

- **概要**: 音声 I/F の目的・対象利用者・主チャネル（電話 / スマートスピーカー / 車載 等の種別）・関連 UC-NNN。
- **入力モデル**:
  - 起動ワード（ウェイクワード）の有無とその方針（採用する場合、固有語を要件 ID に紐付けて記述。具体の発話文字列は詳細設計で確定）。
  - 意図（intent）一覧: 表形式で列挙する。列: `意図名 / 目的 / 典型的な発話パターンの種別 / スロット項目 / 起動 API（API-NNN） / 関連 UC`。発話の具体文字列は詳細設計で確定。
  - スロット（パラメータ）: 各意図のスロット項目ごとに論理型・必須・値域・対応 ENT を示す。
- **出力モデル**:
  - 応答方式: 音声合成（TTS） / 事前収録 / 双方併用。切り替え条件。
  - 応答文の必須要素: 確認復唱（「〜を実行します、よろしいですか」）、確認番号、次の操作案内 等。最終文言は詳細設計。
  - マルチモーダル出力: 画面併用時の画面側との役割分担（音声が主か補助か）。
- **対話制御**:
  - 認識失敗・曖昧時: 再確認 / 選択肢提示 / 有人オペレータへの引継ぎ（IVR の場合）の方針と切替条件。
  - タイムアウト: 発話待ちタイムアウトの方針、タイムアウト時の再案内／切断の方針。
- **認証**: 声紋 / PIN / 外部認証（電話番号検証・SMS・アカウント紐付け）のどれを採るか。責任追跡性の確保方法。
- **プライバシー・録音**: 録音の保持方針・保持期間の方針・削除要求への対応方針。発話に機微情報（暗証番号・口座番号など）が乗る前提のログ・マスキング方針。
- **関連 API・ENT**: 意図の起動する API と扱う ENT を明示する。

##### 3.1.6 チャット・メール等のテキストボット仕様

`#### UI-NNN 名称（チャット / メール）`

- **概要**: ボットの目的・利用チャネル（社内チャット / LINE / Slack / メール 等の種別）・関連 UC-NNN。
- **入力モデル**:
  - 受信メッセージの形式: テキスト / 添付ファイル可否 / ユーザ発信のコマンド記法（`/command` 等）。
  - 意図抽出: 固定コマンド解釈 / 自然文の意図分類 のいずれを基本とするか。意図一覧と対応 API を表形式で示す。
  - 添付受信: 受け付けるファイル種別・サイズ上限の方針。
- **出力モデル**:
  - 返信メッセージの形式: プレーンテキスト / リッチコンポーネント（カード・ボタン・クイックリプライ 等）の方針。具体レイアウトは詳細設計。
  - プロアクティブ発信（ボット側から送る）場合の送出契機。
- **会話状態**: ステートレス / ステートフル。ステートフルの場合のセッション保持方針（保持する情報項目・有効期限）。
- **エスカレーション**: 自動応答から人間オペレータへの引継ぎ条件と、引継ぎ時に渡すコンテキストの範囲。
- **認証・発信者同定**: チャネル側のユーザ ID を信用する範囲と、アカウント紐付けの方法。なりすまし対策方針。
- **スレッド／引用**: 返信スレッドの保持方針・引用の有無。メールの場合は Re: プレフィックス・Message-ID / In-Reply-To ヘッダの扱いの方針。
- **関連 API・ENT**: 意図から起動する API と扱う ENT を明示する。

#### 3.2 API インタフェース仕様（API-NNN）

`#### API-NNN 名称`

- **概要**: 何をする API か、1〜2 文で。関連 UC・UI と、アーキ側の `LNK-NNN` を紐付ける。
- **エンドポイント**: `METHOD 論理パス`（例: `POST /invoices`）を太字で記載。パスパラメータがあれば意味を箇条書きで説明する。
- **リクエスト**: 表形式で列挙する。列: `項目名（論理） / 論理型 / 必須 / 値域・列挙 / 対応 ENT・属性 / バリデーション ID（VR-NNN） / 概要`。
- **レスポンス**: 表形式で列挙する。成功ケースのレスポンスボディ項目を列挙する。列: `項目名（論理） / 論理型 / 必須 / 源泉 / 概要`。リスト応答の場合はページネーションの有無・方針（カーソル型 / オフセット型）を明示する（具体パラメータ名は詳細設計）。
- **主要ステータス**: HTTP 系の場合は 200 / 201 / 204 / 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 系のうち**この API で発生しうるもの**を列挙する。各ステータスの発生条件を一文で書き、対応する `ERR-NNN` を紐付ける（RPC / メッセージングなら相当のコード体系で記述）。
- **冪等性・同時実行**: POST / PUT / DELETE で冪等か、複数回呼ばれたときの挙動が何か（二重登録拒否 / 最新で上書き / 差分適用 等）。楽観ロック・悲観ロックの必要性に言及する。必要な場合は更新トークン・バージョン属性の方針を示す（最終名は詳細設計）。
- **タイムアウト・リトライ方針**: 1 章の基本方針に沿って、この API が「短め／長め」のどちら側か、リトライ可／不可・条件を明示する。具体秒数は詳細設計で確定する旨を添える。
- **認証・認可**: 1 章で決めた全体方針に対し、この API 特有の要件があれば追記する（例: 「管理者ロールのみ」「テナント ID ヘッダ必須」）。認可判定の責務位置を示す。
- **備考**: 論理契約レベルの補足のみ。JSON スキーマ・フィールド命名規則は詳細設計に回す。

#### 3.3 システム間インタフェース仕様（SIF-NNN）

`#### SIF-NNN 名称`

- **概要**: 連携相手・目的・正本。要件側の `SIF-NNN` の記述と齟齬がないことを確認する。
- **連携方式の詳細**: ファイル連携なら「アップロード場所（共有フォルダ／画面アップロード／S3 バケット等の種別レベル）」「想定エンコーディング・改行コード」「ファイル名規則の方針」。API 連携なら「エンドポイント（相手側）」「認証方式（API キー / OAuth / 相互 TLS 等の種別）」。メッセージング連携なら「キュー or トピック」「順序保証の要否」。具体の製品・プロトコル設定はインフラ設計側で確定する旨を添える。
- **レイアウト（受信／送信項目）**: 表形式で列挙する。列: `項目名（論理） / 論理型 / 必須 / 値域・列挙 / 対応 ENT・属性 / 備考`。ファイル連携で既存システムのレイアウトがすでに決まっている場合は、その固定事実を前提として記載し、出典（現行システムの仕様書など）を示す。
- **連携契機と頻度**: 人手実行／スケジュール／イベント駆動のいずれか。頻度・件数の概算（要件側と同値でよい）。
- **失敗時の扱い**: ファイル内の個別行エラー（当該行スキップ or 全件ロールバック）とファイル全体エラー（形式不正等）で扱いを分けて記述する。取り込み履歴（`ENT-NNN`）への記録有無、リトライ可否、手動復旧手順の呼び出し口を示す。
- **権威と整合**: 自システムと相手システムのどちらが正本か。マスタの加筆・削除が双方で起きた場合の優先ルールを明示する（正本の逆側は参照のみ、など）。
- **備考**: 運用上の注意（取り込み実行時間帯の前提・相手システムのメンテナンス時間など）を論理レベルで。

#### 3.4 ハードウェアインタフェース仕様（HIF-NNN）

要件側で `HIF-NNN` が「該当なし」と宣言されているプロジェクトでは、本節も「該当なし」と明記して省略してよい。機器との直接連携がある場合は以下のサブテンプレに沿って書く。

`#### HIF-NNN 名称`

- **概要**: 機器種別（スキャナ / プリンタ / IC カードリーダ / バーコードリーダ / カメラ / センサ / POS レジ 等）・目的・関連 UC-NNN。
- **接続方式の種別**: USB / Bluetooth / シリアル / ネットワーク越し / ドライバ経由 / OS 標準印刷スプール経由 など、**種別レベル**で記述する。具体の製品・ドライバ・ポート番号はインフラ設計で確定する。
- **入出力データ形式**: 機器から受け取るデータの論理形式（カードの UID / バーコード文字列 / センサ値の単位と粒度 / 画像の解像度方針）または機器へ送るデータの論理形式（印刷ジョブの内容項目 / 制御コマンドの種別）を記述する。
- **トリガ・イベント**: 機器操作のどれがシステム側のどのイベントに対応するか。機器イベントを受ける `API-NNN` または画面イベントとの対応。
- **機器未接続・異常時の扱い**: 機器が応答しない・異常値を返す・権限エラーのときの画面・CLI 側の表示方針、リトライ可否、手動復旧の導線。
- **校正・初期化**: 機器の校正・初期化手順が必要な場合の操作主体（利用者 / 運用者）と頻度の方針。
- **機器固有の法規制**: 医療機器・計量機器・課金機器などの法規制（規格適合・検定）の有無と、本ドキュメントで扱う範囲の宣言。詳細はインフラ設計・調達工程で扱う。

#### 3.5 通信インタフェース仕様（CIF-NNN）
- `CIF-NNN` は通信経路（HTTPS / クラウド SDK 等）の粒度で要件定義書に記述済みのため、本ドキュメントでは**新たな詳細は追加しない**。代わりに、本ドキュメントの `API-NNN` / `SIF-NNN` / `HIF-NNN` が `CIF-NNN` のいずれに乗るかを一覧で紐付ける表を置く（2.4 節で代替）。
- 具体の TLS バージョン・暗号スイート・証明書運用はインフラ設計で確定する。

### 4. エラー・例外方針
- 個別のエラー条件を 3 章の各 I/F 仕様内で列挙しつつ、**横串のエラー分類と扱い**を本章で決める。I/F ごとに挙動がばらつくと利用者とフロントエンドの実装が破綻するため。
- **エラーカタログ（ERR-NNN）**: 表形式で列挙する。列: `ERR-NNN / 分類（入力不正 / 認証 / 認可 / 競合 / 存在しない / 業務ルール違反 / 外部依存失敗 / システム内部） / 代表的な原因 / 利用者向け挙動（チャネル別） / 再試行可否 / 監査・ログ方針 / 関連 API-NNN・UI-NNN・HIF-NNN`。
- `ERR-NNN` は本ドキュメントで新規採番する（`ERR-001` から）。
- 各 I/F 仕様では「この I/F で発生しうる `ERR-NNN`」を列挙する形でこの表を参照し、同じ事象に異なる名前が付くことを防ぐ。
- **利用者向け提示の I/F 別方針**: 同じ `ERR-NNN` でも、I/F 種別ごとに提示手段が違う。この対応関係を分類単位で宣言する。
  - 画面: モーダル / トースト / ページ遷移 / フォーム再表示
  - 帳票: エラーファイル出力 / エラー行をマーカ付きで出力 / エラー時は出力中止して通知
  - 通知: 失敗時の再送方針、通知自体のエラーは別ルートで運用者へ
  - CLI: stderr へのメッセージ出力＋終了コード（分類→終了コードの対応を統一）
  - 音声: 言い直し誘導 / 選択肢提示 / 有人オペレータへの切替
  - チャット・メール: 返信メッセージでの即時提示 / リトライ誘導 / エスカレーション
  - HIF: 画面・CLI 側での再接続案内 / 運用者通知
- **例外フローとユースケースの整合**: 各 `usecase.md` の例外フローに出てくる分岐を `ERR-NNN` と対応付け、上記チャネル別提示のどのパターンを採るかを分類ごとに決める（最終文面は詳細設計）。
- **外部依存失敗**（`SIF-NNN` / `CIF-NNN` / `HIF-NNN` 先の障害・遅延）時は、チャネル別の見せ方（即時エラー／再試行案内／縮退表示／機器切替）を方針として決める。アーキ側のフォールバック責務と整合させる。

### 3. 外部連携で責任境界が明確か

### 4. API 仕様とデータ設計が矛盾していないか
- API リクエスト／レスポンス項目のうち、ENT 属性と紐付くべきものが `ENT-NNN.属性名` で対応付けられているか。

- 状態遷移を持つエンティティの API では、許容される状態遷移（RULE-NNN）と、API が起こす遷移が整合しているか。

- **横向きの侵食（データ設計）**: ENT 属性や RULE を本ドキュメントで再定義していないか。データ設計を参照するに留める。
- **横向きの侵食（アーキテクチャ設計）**: COMP の責務や LNK の同期／非同期境界を本ドキュメントで再決定していないか。アーキ側の決定を受けて I/F 単位に落とし込むに留める。
- **インフラ設計の侵食**: TLS 設定値・WAF ルール・LB 振分け・具体ネットワークタイムアウト値・製品名が紛れていないか。紛れていたら「6.3 インフラ設計への申し送り」に切り出す。
- **上向きの侵食**: 要件側に未定義の業務ルールや新しい UC・UI・SIF・HIF・CIF が、本ドキュメントで黙って発生していないか。発生していたら、要件側への波及候補として「6.1 リスク・懸念点」に記録する。
- **空洞化**: 論理契約粒度で決めるべき話（バリデーション責務分離・エラー分類・冪等性方針・認証認可適用・タイムアウト方針）が「詳細設計で決める」に丸投げされていないか。ここで決め切る。

### 6. 図と表の整合
- 画面遷移図に登場するすべての画面が「2.1 人間向けインタフェース一覧」に存在するか。逆に、表にだけあって遷移に登場しない画面が意図的か偶発か判別できるか。
- CLI のサブコマンドツリー図（採用している場合）・音声の対話状態図・ボットの会話状態図に登場する要素が、それぞれの I/F 仕様と一致しているか。
- `sequenceDiagram` に登場するすべての矢印が、`API-NNN` / `SIF-NNN` / `HIF-NNN` として表に存在するか。
- 1 章で「採用する」と宣言した人間向け I/F 種別に対応する仕様が 3.1 のサブ節に存在するか。逆に、1 章で「採用しない」と宣言した種別の仕様が残っていないか。
- 各 I/F 仕様で参照している `ERR-NNN` / `VR-NNN` / `ENT-NNN` / `LNK-NNN` が、それぞれのカタログ／参照先に実在するか（採番ミスがないか）。
