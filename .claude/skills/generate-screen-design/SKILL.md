# 画面設計（スタイルガイド + 画面詳細）の作成
要件定義書・HCD/UI・UX 設計書・アーキテクチャ設計書・データ設計書・インタフェース設計書を入力として、詳細設計の一部である**スタイルガイド**と**画面ごとの詳細設計**を作成してください。

## Goal
本スキルは 2 種類の成果物を 1 スキルで扱う。

1. **スタイルガイド**: システム全体で一貫した視覚言語（デザイントークン）と共通コンポーネント仕様を与える、**横串の設計基盤**。
2. **画面詳細設計**: `UI-NNN`（種別「画面」）ごとに、レイアウト・状態・権限差分・動的挙動・レスポンシブ挙動を実装に落とせる粒度でまとめる。

「実装に落とせる粒度で一義に読み取れる」とは、各画面について「どんな領域割りで」「どの共通コンポーネントが置かれ」「どの状態（正常 / ローディング / 空 / エラー / 権限別）でどう見え」「入力項目の依存関係で何がどう変わり」「画面幅が変わったときに何が崩れないか」が、スタイルガイド（`DTK-NNN` / `CMP-NNN`）と上流ドキュメント（要件 / HCD・UI/UX / データ / インタフェース）に矛盾なく紐付いて読み取れる状態を指す。逆に、具体の CSS 変数名・Tailwind 設定・コンポーネントライブラリ固有構文・ピクセル完全配置の具象値までは踏み込まない。判断に迷ったら、要件 ID（`UC-NNN` / `NFR-NNN`）・HCD ID（`PER-NNN` / `SCN-NNN` / `JOB-NNN` / `FLW-NNN` / `UXI-NNN` / `FB-NNN` / `A11Y-NNN`）・インタフェース ID（`UI-NNN` / `VR-NNN` / `ERR-NNN` / `API-NNN`）・データ ID（`ENT-NNN` / `RULE-NNN`）のいずれかに紐付けられるかを基準にする。紐付けられないものは「今は採らない」側に置いて注意事項に記録する。

## 位置付け（要件定義・HCD/UI・UX 設計・アーキテクチャ設計・データ設計・インタフェース設計・実装との関係）
本スキルは `/generate-requirements`、`/generate-hcd-uiux-design`、`/generate-architecture-design`、`/generate-data-design`、`/generate-interface-design` の成果物を入力とし、実装工程の直前段階となる**画面単位の詳細仕様**と**全画面共通のスタイル基盤**を固める。コンポーネント設計・クラス設計と並列に走る「UI 側の詳細設計」という位置付けをとる。

HCD/UI・UX 設計で**論理方針**として決まった「どんなユーザーが、どんな状況で、どのタスクを、どのフローで達成し、どこで躓きやすく、どうフィードバックし、どうアクセシビリティを担保するか」を、本スキルでは**実装可能な具体値と視覚仕様**に落とす、という関係にある。HCD 側で決めた方針を本ドキュメントで覆さない（覆したくなったら HCD 側に戻る）。

- 上流（要件）: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 各 `usecase.md` の基本／代替／例外フローは、画面の状態一覧・状態遷移を決める根拠になる。
  - 非機能要件（特にユーザビリティ・アクセシビリティ・可読性・多言語・応答性能の「体感」項目）は、スタイルガイドの基準値（コントラスト比・フォントサイズ下限・タッチターゲット最小寸法・初期表示スケルトン方針）の根拠になる。
  - ブランド・トーン＆マナー要件は、スタイルガイドのカラー・タイポグラフィ・イラスト方針の根拠になる。
- 上流（HCD / UI・UX）: `docs/design/uiux/uiux-design.md`
  - `PER-NNN`（ペルソナ）・`SCN-NNN`（利用シナリオ）は、画面のレイアウト優先順位・コンポーネント密度・ブランドトーンの判断根拠になる。プライマリペルソナの利用環境（デバイス・通信状況・身体特性）は、スタイルガイドのブレークポイントやアクセシビリティ方針の前提になる。
  - `JOB-NNN`（主タスク）・`FLW-NNN`（タスクフロー）は、画面の「主 CTA の位置」「主要経路の短縮」「崩してはいけない要素」を決める根拠になる。複数画面をまたぐフローは、遷移の一貫性をスタイルガイド 1 章の方針として反映する。
  - `UXI-NNN`（UX 課題）と改善方針は、スタイルガイドの方針（破壊的操作と肯定操作の視覚的区別等）および画面詳細の動的挙動・フィードバック設計に具体化される。
  - `FB-NNN`（フィードバック設計）は、画面の状態一覧（ST-NN）の「応答時間区分ごとの見せ方（瞬時 / 短時間 / 長時間 / 非同期）」として実装値レベルに落とす。本スキルで新しいフィードバック方針を発生させない。
  - `A11Y-NNN`（アクセシビリティ方針）は、スタイルガイドのアクセシビリティ章で**具体値**（WCAG 準拠レベル・コントラスト比・フォーカスリング・タッチターゲット寸法）に落とす。HCD 側で A11Y の対象外とされた JOB がある場合、本ドキュメントでも対象外扱いを維持する。
- 上流（アーキテクチャ）: `docs/design/architecture/architecture.md`
  - 画面を提供する `COMP-NNN`（典型: フロントエンド COMP）の責務位置と、`LNK-NNN` の同期／非同期境界を参照する。画面でのローディング状態の必要性（非同期境界の下流を待つか）や、楽観的 UI 更新の可否を判断する根拠にする。
- 上流（データ）: `docs/design/data/data-design.md`
  - `ENT-NNN` の属性と `RULE-NNN`（状態遷移を含む）は、画面上の表示項目・権限別表示・フォーム動的挙動（「この状態のときはこの項目を編集不可」等）の根拠になる。
- 上流（インタフェース）: `docs/design/interface/interface-design.md`
  - `UI-NNN`（種別「画面」）は本ドキュメントの **1 ファイル = 1 画面** の単位そのもの。新しい画面を本ドキュメントで追加しない（必要ならインタフェース設計側に戻って `UI-NNN` を採番する）。
  - `UI-NNN` の「入力項目」「出力項目」「画面イベントと起動 API」「画面間遷移」は本ドキュメントの詳細化の起点とする。**本ドキュメントでは上書きしない**。不整合が見つかったら「6. 注意事項」にリスクとして記録し、必要なら I/F 側に戻る。
  - `VR-NNN` はフォーム動的挙動・入力補助（リアルタイム検証・サブミット前検証）の設計根拠。`ERR-NNN` は状態一覧の「エラー状態」「例外状態」の具体化根拠。`API-NNN` はローディング境界の根拠（呼ぶ API の同期／非同期と完了契機）。
- 下流（実装）: 具体の CSS 変数定義・Tailwind / MUI / Chakra 等フレームワーク固有の設定、実際のコンポーネントライブラリ採用とコンポーネント実装、画像・アイコンの実ファイル、各画面のコード化、i18n メッセージキーの実ファイル定義。

## Focus（このスキルが扱う範囲）
本スキルは以下に集中する。いずれも**画面単位の詳細仕様レベル**と**論理スタイル基盤レベル**の話であり、特定のコンポーネントライブラリやフレームワーク固有の記法には踏み込まない。

**スタイルガイド側（システム全体の横串）**
- カラー設計（ブランドカラー・意味カラー・中間階調・背景／表面・ダークモード方針）
- タイポグラフィ（フォントファミリ方針・見出し階層・本文サイズ・行間・letter-spacing）
- スペーシング・レイアウトグリッド（スケールと呼称、ブレークポイント）
- エレベーション・角丸・ボーダー（階層と意味）
- アイコン・画像・イラスト方針（線種・塗り方・トーン）
- モーション原則（duration と easing の論理名、過度な動きの抑制方針）
- 共通コンポーネント仕様（`CMP-NNN`: ボタン / フォーム要素 / カード / モーダル / テーブル / トースト / バッジ / タブ / ナビゲーション 等。状態別: default / hover / active / disabled / focus / loading / error）
- アクセシビリティ方針（WCAG 準拠レベル、コントラスト比下限、フォーカスリング、タッチターゲット最小寸法、キーボード操作原則）
- ブランド運用ルール（ロゴ使用ルール、余白規定、禁則、画像処理の原則）

**画面詳細側（`UI-NNN` ごと）**
- 画面全体のレイアウト（ヘッダ / サイドバー / メインコンテンツ / フッタ 等の領域分割）
- 領域内のコンポーネント配置（どの `CMP-NNN` をどこに、どんな順序で置くか）
- 入力項目・表示項目のグルーピング・視覚的優先順位
- 画面状態一覧（`ST-NN`: 初期 / 読込中 / 空 / 正常 / 部分エラー / 致命エラー / サブミット中 / サブミット後 等）と、状態間の遷移
- 権限別表示差分（ロール・所有関係・業務状態などに応じた表示／非表示・編集可否・操作可否の切替）
- フォーム動的挙動（項目間依存 / 条件付き必須 / 自動計算 / 片側選択による他項目の候補絞込 / リアルタイム検証の発火粒度）
- レスポンシブ挙動（ブレークポイント別のレイアウト変化、折返し方針、ナビゲーションの変形、テーブルの横スクロール or カード化の切替）
- `UI-NNN` のイベントに対応する UI 側挙動（押下時のローディング表示・確認モーダル・トースト表示・遷移先）
- 多言語・テキスト長変動への耐性方針（長文での折返し・省略・ツールチップ）

## Do not decide here（このスキルでは決めないこと）
以下は本スキルの対象外で、画面仕様・スタイル基盤が定まった後の工程で決める。粒度が崩れて議論が停滞するため、見つかっても本ドキュメントでは該当工程への申し送り事項に退避させ、ここでは決めない。

**実装で決める**
- 具体の CSS 変数名・Tailwind 設定ファイル・SCSS / CSS-in-JS の実ファイル
- コンポーネントライブラリの選定と具体利用方法（MUI / Chakra UI / Radix / shadcn-ui / Ant Design 等の採用判断）
- React / Vue / Svelte / HTMX 等フレームワーク固有の実装構文
- アイコン・画像の実ファイル（SVG / PNG）・圧縮設定・CDN 配置
- フォント配信方式（Google Fonts / セルフホスト / 可変フォント）
- i18n ライブラリの選定・メッセージキーの命名規則・メッセージファイル本体
- ユニットテスト・ビジュアルリグレッションテスト・E2E テストの具体
- ストーリーブック等のツール運用・カタログ整備
- ピクセル単位での微調整（具体 px 値を CSS で書く粒度）

**HCD / UI・UX 設計で決まり済み（本ドキュメントでは再決定しない）**
- ペルソナ（`PER-NNN`）・利用シナリオ（`SCN-NNN`）の定義。画面詳細で「誰が使う画面か」は HCD 側から引く。
- 主タスク（`JOB-NNN`）・タスクフロー（`FLW-NNN`）の設計。画面詳細で「この画面が属するフローは何か」「主 CTA は何か」は HCD 側から引く。
- UX 課題（`UXI-NNN`）の特定と改善方針の**方向性**。本ドキュメントは改善方針を**具体の視覚・動作**に落とすのみ。
- フィードバック方針（`FB-NNN`）の応答時間区分・モダリティ・粒度・タイミング。本ドキュメントはこれを ST-NN・CMP の具体状態表現に落とす。
- アクセシビリティ方針（`A11Y-NNN`）の対象範囲・担保すべき操作・理解・想定 WCAG 原則。本ドキュメントは具体値（コントラスト比・フォーカス表示・最小フォント・タップ寸法）に落とす。
- 対象ユーザーの幅（初見優先 / 習熟優先 / 両立）・操作効率の基準（目安操作回数・遷移段数）・エラー耐性の方針・体験の一貫性原則。

**インタフェース設計で決まり済み（本ドキュメントでは再決定しない）**
- `UI-NNN` の追加・削除・画面としての目的の再定義（必要ならインタフェース設計側に戻る）
- 画面の入力項目・出力項目の**項目一覧そのもの**（論理型・必須・対応 ENT）
- 画面イベントから起動される `API-NNN` の対応付け
- 画面間の遷移の**存在**（遷移先は I/F 側で宣言済み、本ドキュメントは遷移のトリガとアニメーションの方針を具体化するに留める）
- `VR-NNN` のバリデーション条件・`ERR-NNN` のエラーカタログ
- 認証認可の責務位置・権限モデル（ロール階層）

**データ設計・アーキテクチャ設計・要件で決まり済み**
- `ENT-NNN` の属性・`RULE-NNN` の内容
- `COMP-NNN` の責務・`LNK-NNN` の同期／非同期境界
- `BRU-NNN` の内容・ユースケースフロー

**インフラ設計で決める**
- CDN 配信ルール・画像最適化のサーバ側設定
- フォントファイルの配信・キャッシュポリシー

例外: 上記に属する項目でも、画面仕様判断に直結する場合（例: 「認証基盤側でフェデレーション時にメールアドレスが取得できない場合があると確定しており、画面側で補完入力を必須にする必要がある」）は、前提として最小限言及する。ただし具体の実装（ライブラリ名・CSS 具体値）には踏み込まない。

## 入力
- 要件定義書（`docs/requirements/` 配下一式）を既定の入力とする。存在すれば必ず参照する。特にユーザビリティ・アクセシビリティ・ブランドに関わる非機能要件と、各 `usecase.md` のフロー。
- HCD / UI・UX 設計書（`docs/design/uiux/uiux-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `PER-NNN`・`SCN-NNN`・`JOB-NNN`・`FLW-NNN`・`UXI-NNN` と改善方針・`FB-NNN`（フィードバック方針）・`A11Y-NNN`（アクセシビリティ方針）・1 章の UX 設計方針（対象ユーザーの幅・操作効率基準・エラー耐性方針・体験の一貫性原則）。HCD 側が未整備のままインタフェース設計が進んでいるプロジェクトは多いが、その場合でも本ドキュメントで HCD 側の決定を再発明しない。HCD 側を先に埋めるよう申し送り、本ドキュメントでは暫定前提として記載するに留める。
- アーキテクチャ設計書（`docs/design/architecture/architecture.md`）を既定の入力とする。存在すれば必ず参照する。特に `COMP-NNN`・`LNK-NNN` の同期／非同期境界。
- データ設計書（`docs/design/data/data-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `ENT-NNN`・`RULE-NNN` と状態遷移。
- インタフェース設計書（`docs/design/interface/interface-design.md`）を既定の入力とする。存在すれば必ず参照する。特に `UI-NNN`（種別「画面」）の入出力項目・イベント・画面遷移・`VR-NNN`・`ERR-NNN`・`API-NNN`。
- 既存のスタイルガイド（`docs/design/screen/style-guide.md`）がある場合は**必ず入力として読み込む**。画面詳細を書くときは既存トークン・既存コンポーネントを参照し、無断で新規トークン・コンポーネントを画面側で作らない。スタイルガイドが未作成なら、画面詳細を書く前に先にスタイルガイドを生成する。
- 既存の画面詳細（`docs/design/screen/UI-NNN-*/screen.md`）がある場合は差分更新とする。既存 ID（`ST-NN` / `LAY-NN` 等）は維持する。
- 追加で $ARGUMENTS にファイルパス・テキスト・対象画面（`UI-NNN` 指定）が渡された場合はそれを併用する。
- 上流ドキュメントが存在しない場合は、入力で与えられた素材から暗黙的に前提を抽出したうえで判断根拠を明示する（抽出した暗黙前提はスタイルガイドの「6. 注意事項」または画面詳細の「注意事項」に記載する）。

## 出力ファイル
本スキルは**出力を 2 系統に分ける**。スタイルガイドはシステム全体で 1 ファイル、画面詳細は画面ごとに 1 ファイル。

```
docs/design/screen/
├── style-guide.md                     # システム全体のスタイル基盤（1 ファイル）
└── UI-NNN-{slug}/
    └── screen.md                       # 画面ごとの詳細（UI-NNN 1 つにつき 1 ファイル）
```

- `{slug}` は `UI-NNN` の名称を kebab-case で短縮したもの（英小文字・数字・ハイフンのみ）。日本語画面名は英訳せず、要件側で付与された短縮名や対応する主要 UC のスラッグを使う。不明な場合は `ui-001-home` のような連番 + 役割の形でよい。
- 画面が 1 つしか存在しない小規模プロジェクトでも、同じ構造を採る（将来の画面追加に備える）。
- 既にファイルがある場合は、差分更新（章単位で追記・修正）し、既存の ID 体系は維持する。

**ファイルを分ける理由**: 画面詳細はレイアウト・状態・コンポーネント配置など情報量が多く、1 画面あたりでもそれなりの分量になる。全画面を 1 ファイルに集約すると、10 画面程度で可読性が崩れる。またビルド（実装）時の並行作業・PR レビューも画面単位に切り出しやすい。一方、スタイルガイドは全画面で参照される横串の基盤なので 1 ファイルに集約する。

**スタイルガイドと画面詳細の依存関係**: 画面詳細はスタイルガイドを**前提**として参照する。画面詳細で新しい視覚パターンが必要になった場合、**無断で画面側に書かず**、スタイルガイド側に新しい `DTK-NNN` / `CMP-NNN` を追加してから画面側から参照する。画面固有の一回限りの配置（ランディングページのヒーロー領域など）は例外として画面側で扱うが、その場合でも「スタイルガイドには昇格させない理由」を画面詳細の注意事項に書く。

1. スタイル設計方針
2. デザイントークン

## 各章の書き方（スタイルガイド）

### 1. スタイル設計方針
- 本スタイルガイド全体を貫く方針を、箇条書きで 5〜9 点程度にまとめる。論理スタイル基盤レベルの判断のみを扱い、具体のライブラリ・CSS 変数名・フレームワーク固有記法には踏み込まない。
- HCD / UI・UX 設計書の 1 章「UX 設計方針」（対象ユーザーの幅・操作効率の基準・エラー耐性の方針・フィードバック原則・アクセシビリティ水準・体験の一貫性・認知負荷の上限）と整合させる。HCD 側で決めた論理方針を、本章ではスタイル基盤としての実装方針に翻訳する（例: HCD 側の「初見ユーザー優先、情報密度は低め」 → 本章の「スペーシング密度: コンフォート、本文 16px、カード最大幅を狭く保つ」）。
- 典型的に書くべき方針:
  - **デザイン言語の出発点**: HCD 側のプライマリペルソナ（`PER-NNN`）・代表的シナリオ（`SCN-NNN`）の文脈、および要件側のブランド要件から導かれる視覚的トーン（例: 「信頼性重視・情報密度高め・装飾最小限」「親しみ・柔らかさ・余白広め」）を宣言する。PER-NNN の利用環境・身体特性（屋外での視認性・片手操作・高齢者前提 等）は、コントラスト・フォントサイズ・タッチターゲットの基準に直結するので明示的に紐付ける。
  - **カラーシステムの設計原則**: ブランドカラーと意味カラーの区別、中間階調の生成方針（明度スケール）、背景／表面の階層、ダークモード採用可否とその生成方針（反転 / 別系統定義）。
  - **タイポグラフィスケール**: 見出しと本文のサイズ階層、スケール比（例: モジュラースケール 1.250）、フォントファミリ選定の**種別**（セリフ / サンセリフ / 等幅）と用途割り当て方針。
  - **スペーシング原則**: 基底単位（4px / 8px 等）とスケール倍率、密度レベル（コンフォート / スタンダード / コンパクト）を複数持つかどうかの方針。
  - **コンポーネントの設計原則**: プリミティブ（Button / Input 等）とコンポジット（Form / Card 等）の区別、バリエーションの増やし方の歯止め（「同じ見た目のボタンに複数名称を与えない」等）。
  - **モーション原則**: 過度な動きの抑制、`prefers-reduced-motion` への対応方針、duration・easing の論理名（例: `motion.fast` / `motion.base` / `motion.slow`）と意味。
  - **アクセシビリティ最低基準**: WCAG の準拠レベル（AA / AAA）、コントラスト比の下限、フォーカスリング常時表示、キーボード操作原則。
  - **ダークモード方針**: 採用する／しない／将来採用余地、採用時のトークン命名方針。
  - **拡張ポリシー**: トークン・コンポーネントの追加手順（誰が提案し、どう合意し、スタイルガイドに昇格させるか）。画面側での場当たり定義を禁じる根拠として働く。
  - **非対応ブラウザ・環境**: サポート対象ブラウザ・画面幅の下限・高密度ディスプレイ対応の方針。これが画面側のレスポンシブ設計の前提になる。
- 「流行っているから」「慣れているから」といった要件・上流設計に紐付かない方針は記載しない。

### 2. デザイントークン（`DTK-NNN`）
トークンは表形式で列挙する。**論理名 + 代表値**までを本ドキュメントで決め、CSS 変数名・Tailwind 設定への反映は実装側で行う。

#### 2.1 カラートークン
- 列: `DTK-NNN / 論理名 / 役割（ブランド / 意味 / 中間階調 / 背景 / 表面 / テキスト / ボーダー / オーバーレイ） / ライトモード値（HEX or 論理値） / ダークモード値（採用時） / コントラスト確保対象 / 由来（要件 NFR-NNN / ブランド要件）`
- **ブランドカラー**: `primary` / `secondary` / `accent` 等。使う局面（主 CTA / 副 CTA / 強調）を「コントラスト確保対象」列に明示する（例: `text.onPrimary` との組で AA を満たすこと）。
- **意味カラー**: `success` / `warning` / `danger` / `info`。業務エラー（`ERR-NNN`）の分類別表示に使うため、I/F 側のエラー分類との対応を注記する。
- **中間階調（ニュートラル）**: `gray-050` 〜 `gray-900` のような段階定義。背景・境界・テキストに展開する。
- **背景／表面**: `background` / `surface` / `surface.raised` / `surface.sunken`（エレベーション階層と連動）。
- **テキスト**: `text.primary` / `text.secondary` / `text.disabled` / `text.inverse`。各ペアでコントラスト比を確認する。
- **ボーダー・オーバーレイ・シャドウ色**: 境界線やモーダルスクリムの色。
- **ダークモード採用時**の値を持つトークンには、ライト／ダークの両方の列に値を入れる。採用しない場合は列ごと省略してよい（1 章で宣言）。
- コントラスト比は WCAG 計算式に基づく値を参考として注記できる（具体値の厳密検証は実装・QA 工程）。

#### 2.2 タイポグラフィトークン
- 列: `DTK-NNN / 論理名 / 用途（見出し / 本文 / キャプション / 数値表示 等） / フォントファミリ種別 / サイズ（代表値 or 論理スケール） / 行間 / 文字間隔 / 太さ / 備考`
- **見出し階層**: `heading.h1` 〜 `heading.h6`（必要な範囲で）。各階層のサイズ・太さ・行間の組合せ。
- **本文**: `body.lg` / `body.md` / `body.sm`。既定は `body.md`。
- **キャプション・ラベル・数値表示**: 小さめ、または等幅の用途別。
- **フォントファミリ**: 具体フォント名を仮置きしてもよいが、最終採用は実装工程で確定する。論理的には「UI 全般のサンセリフ」「強調用のセリフ」「数値用の等幅」の**種別**まで決めておく。
- **多言語時の挙動**: CJK（日本語 / 中国語 / 韓国語）と英数字でフォールバック順がある場合、その方針。

#### 2.3 スペーシングトークン
- 列: `DTK-NNN / 論理名 / 値（代表 px や rem） / 主な用途`
- **スケール**: `space.0` = 0、`space.1` = 4px、`space.2` = 8px … のような連続スケール。または `xs / sm / md / lg / xl / 2xl` の命名。
- **主な用途**: インライン間隔（テキスト間）/ スタック間隔（要素間）/ セクション間隔（領域間）など、適用箇所の想定を書く。
- **グリッド**: コンテナ最大幅・カラム数・ガター幅の原則を記す（コンテナ幅は後述のブレークポイントと連動）。

#### 2.4 エレベーション・角丸・ボーダー
- 列: `DTK-NNN / 論理名 / 値（代表的な数値 or 影の表現） / 主な用途`
- **エレベーション**（シャドウ階層）: `elevation.0` / `elevation.1`（カード）/ `elevation.2`（ポップオーバー）/ `elevation.3`（モーダル）/ `elevation.4`（トースト）等。ダークモード時の扱いを宣言。
- **角丸**: `radius.none` / `radius.sm` / `radius.md` / `radius.lg` / `radius.full`（円形）。コンポーネント種別と意味を対応させる。
- **ボーダー太さ**: `border.thin` / `border.base` / `border.thick`。色トークン（2.1）との掛け合わせで実際の境界を決める。

#### 2.5 モーショントークン
- 列: `DTK-NNN / 論理名 / 値（duration or easing） / 主な用途`
- **Duration**: `motion.fast`（例: 100ms）/ `motion.base`（例: 200ms）/ `motion.slow`（例: 400ms）。
- **Easing**: `ease.standard`（標準）/ `ease.emphasize`（強調の進入）/ `ease.decelerate`（離脱）/ `ease.accelerate`。
- **適用方針**: マイクロインタラクション（hover / focus 反応）は `fast`、状態遷移は `base`、ページレベル遷移は `slow` 寄り、のような対応を記す。
- `prefers-reduced-motion` を尊重し、アニメーションを一律短縮・無効化する条件を宣言する。

#### 2.6 ブレークポイント
- 列: `DTK-NNN / 論理名 / 下限幅 / 主な対象端末種別 / コンテナ幅方針 / カラム数方針`
- 代表例: `sm`（〜640px: スマートフォン縦）/ `md`（〜768px: スマートフォン横・小型タブレット）/ `lg`（〜1024px: タブレット）/ `xl`（〜1280px: デスクトップ）/ `2xl`（〜1536px: 広幅デスクトップ）。
- モバイルファースト／デスクトップファーストのどちらで記述するか、1 章の方針と整合させる。
- 画面詳細の「レスポンシブ挙動」章でこのブレークポイントを参照する。

### 3. コンポーネントカタログ（`CMP-NNN`）
共通コンポーネントを表形式と個別仕様で列挙する。**論理的な振る舞いと視覚仕様**を決め、具体の実装構文（React / Vue の props 名・ライブラリ固有構文）は実装工程に回す。

#### 3.1 コンポーネント一覧
- 列: `CMP-NNN / 名称 / 分類（プリミティブ / コンポジット / レイアウト / フィードバック / ナビゲーション） / 主な用途 / バリエーション数 / 依存する CMP-NNN / 依存する DTK-NNN / 備考`
- `CMP-NNN` は本ドキュメントで新規採番する（`CMP-001` から）。
- **分類**:
  - **プリミティブ**: Button / Input（TextField）/ Select / Checkbox / Radio / Switch / Textarea / Label
  - **コンポジット**: FormField（Label + Input + エラーメッセージ）/ Card / Table / DataGrid / Modal / Drawer / Tabs
  - **レイアウト**: Stack / Inline / Grid / Container / Divider / Spacer
  - **フィードバック**: Toast / Alert / Banner / ProgressBar / Spinner / Skeleton
  - **ナビゲーション**: Header / Sidebar / Breadcrumb / Pagination / Menu
- **バリエーション**: 見た目や役割のバリアント数（例: Button なら primary / secondary / ghost / danger / link の 5 種）。
- **依存する CMP-NNN**: コンポジットはプリミティブに依存する。依存関係は循環しないことを「6. 注意事項」で確認する。

#### 3.2 各コンポーネント仕様
各 `CMP-NNN` について、以下のサブテンプレートで詳細を記述する。

`#### CMP-NNN 名称`

- **概要**: 何のコンポーネントか、1〜2 文。分類・主な用途・関連 UC-NNN（必要なら）。
- **用途・原則**: どういう場面で使うか、使わない場面。類似コンポーネントとの使い分け（例: Button と Link の使い分け: 同じ見た目でも「遷移」は Link、「動作」は Button とする）。
- **バリアント**: 表形式で列挙する。列: `バリアント名 / 役割・意味 / 使用する DTK-NNN / 用法制約（例: primary は 1 画面 1 つまで）`。
- **サイズ**: 表形式で列挙する。列: `サイズ名 / 適用する DTK-NNN（パディング・フォントサイズ）/ 主な用途`。sm / md / lg の 3 種が典型。
- **状態**: 表形式で列挙する。列: `状態 / 視覚変化（使用する DTK-NNN） / 備考`。状態は `default / hover / focus / active / disabled / loading / error` を基本とする。fieldset 系には `readonly` を追加、トグル系には `checked / unchecked`、入力系には `invalid / valid` を追加。
- **要素構成**: コンポーネントを構成する論理パーツ（例: Button なら `icon-leading / label / icon-trailing`）と、それぞれのオン／オフ可否。
- **入出力契約**: ユーザー操作に対するコールバックの**種別**（onClick / onChange / onBlur / onFocus / onKeyDown 等のうち実装側で使うもの）。具体の prop 名は実装工程で決める。
- **アクセシビリティ**: ARIA ロール・ラベル付け原則・キーボード操作（フォーカス遷移・Enter / Space の動作・Escape の扱い）・スクリーンリーダー上での読み上げ順序の方針。WCAG の該当基準を注記する。
- **レスポンシブ挙動**: 画面幅が変わったときの挙動（縮む / 全幅になる / 縦積みに変わる）。ブレークポイント（`DTK-NNN`）を参照する。
- **使用可否の制約**: このコンポーネントを使ってはいけない場面、または他コンポーネントへ寄せるべき場面。
- **関連コンポーネント**: 似ている他 `CMP-NNN` との関係（継承的・代替的・補完的）。

### 4. アクセシビリティ方針（具体値への落とし込み）
- 本章は HCD / UI・UX 設計の `A11Y-NNN`（論理方針）を**具体値と視覚仕様**に落とす章である。HCD 側で決まった「対象・担保したい操作・方針・対応する WCAG 原則」を、本章で「具体の閾値・最小寸法・実装可能な挙動」に翻訳する。HCD 側にない論点（例: 実ユーザー観察で出てきた特殊配慮）をここで新規に発生させない。発生したら HCD 側への逆流候補として 6 章に記録する。
- 各 `A11Y-NNN` に対して、本章で何を決めるかを表形式で対応付ける。列: `A11Y-NNN / HCD 側方針（要約） / 本章での具体化内容 / 関連 DTK-NNN・CMP-NNN`。
- **準拠レベル**: WCAG の目標準拠レベル（A / AA / AAA）の**具体値宣言**。HCD 側で「AA 相当」と決まっていれば、本章で「WCAG 2.1 AA に準拠」と明示する。項目単位で AAA を目指す箇所（例: 色のコントラストだけは AAA）がある場合はここで宣言する。
- **コントラスト比**: 2.1 カラートークンの背景 × テキスト組合せで満たすべき比（通常: 4.5:1、大型テキスト: 3:1）を原則として宣言する。HCD 側 A11Y-NNN の「視覚」観点の具体化。違反が出た場合の解消方針（代替トークンの生成 or 使用禁止組合せの宣言）を示す。
- **キーボード操作**: Tab 順序の方針、フォーカスリングの常時表示、モーダル内のフォーカストラップ、Escape でのキャンセル原則、ショートカットキーを導入する場合の衝突回避方針。HCD 側 A11Y-NNN の「運動」観点の具体化。
- **スクリーンリーダー対応**: ARIA ロール／ラベル／ライブリージョンの使用方針、画像の alt テキスト方針（装飾目的は空 alt、情報目的は説明 alt、複雑図は詳細説明へのリンク）、状態変化の通知方針（トーストを視覚以外でどう伝えるか）。HCD 側 A11Y-NNN の「視覚」観点の具体化。
- **可読性**: 最小フォントサイズ下限（通常 14px・本文 16px 程度）、行間下限、段落幅上限（日本語 40〜50 文字、英語 60〜80 文字）の方針。HCD 側 A11Y-NNN の「視覚 / 認知」観点の具体化。
- **タッチターゲット**: 最小寸法（44×44px 目安）、ターゲット間の最小余白。HCD 側 A11Y-NNN の「運動」観点の具体化。
- **動きへの配慮**: `prefers-reduced-motion` 尊重、自動再生の禁止、点滅の禁止（発作誘発の原則）。HCD 側 A11Y-NNN の「認知 / 状況的制約」観点の具体化。
- **音の扱い**: 自動音声再生の禁止、音のみで情報を伝えない原則。HCD 側 A11Y-NNN の「聴覚」観点の具体化。
- **言語切替と読み上げ**: 言語タグ（`lang` 属性相当）の適用方針、複数言語が混在する場面での部分ラベル付けの方針。
- **対象外とする場面**: HCD 側で「対象外」とされた `JOB-NNN` がある場合、本章でもその旨を維持し、対応する画面での具体的な「AA を満たさない代わりに何を代替として用意するか」があれば書く。本スキル側で独自に対象外を増やさない。

### 5. ブランド運用ルール
- **ロゴ**: 最小表示サイズ、周囲に確保するクリアスペース、使用可能な背景色（2.1 カラートークンとの対応）、禁則（変形・色変更・縁取り）。
- **画像・イラスト方針**: 写真の方針（彩度・トーン・人物の写り方）、イラストの方針（線の太さ・塗り・色彩使用）、アイコンの方針（線 vs 塗り、太さ、コーナー処理）。一貫性の出し方を論理的に宣言する。
- **文言トーン**: ですます／だ・である、カジュアル／フォーマルの方針、業務用語の統一、禁止用語（差別的表現・誤解を招く表現）。
- **禁止事項**: ブランドを毀損する用法を列挙する（例: 競合ロゴと並置、色の勝手な反転、トリミングで文字が欠ける配置）。
- 詳細な運用（承認フロー、制作ツール、素材配布経路）は運用工程に回す。

### 6. 注意事項
スタイルガイドの注意事項も、以下 3 区分で整理する。

#### 6.1 リスク・懸念点
- `RISK-NNN / 内容 / 影響範囲（DTK / CMP / A11y / ブランド / 画面全般） / 顕在化条件 / 暫定対応 / 実装・運用への申し送り`
- 典型カテゴリ:
  - ダークモードを後から導入する場合のトークン名設計の歪み
  - 多言語化時のテキスト膨張（英語→日本語で 1.3 倍、ドイツ語はさらに膨張）へのレイアウト耐性不足
  - 大規模データテーブルでのレスポンシブ対応（横スクロール / カード化 / 列の折りたたみの選択）
  - アクセシビリティ基準とブランドカラーのコントラスト不足
  - コンポーネントのバリアント数膨張（「特殊なボタン」が増え続ける兆候）
  - アイコン・画像の肥大化（アセット管理が追いつかない）
  - 高密度ディスプレイでのスケーリング崩れ
  - 古いブラウザ（例: iOS Safari n-2 バージョン）での機能差分

#### 6.2 代替案と採らない理由
- `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`
- 最低でも以下については検討の痕跡を残す:
  - **カラースケールの生成方法**: 手動調整 vs アルゴリズム生成（HSL / OKLCH 等）
  - **ダークモード**: 採用 vs 非採用 vs 段階導入
  - **スペーシングのスケール**: 4 ベース vs 8 ベース vs 非線形スケール
  - **タイポグラフィのスケール**: 線形 vs モジュラースケール
  - **ブレークポイントの数**: 3 段階 vs 5 段階 vs 6 段階
  - **アイコン**: 線画 vs 塗り vs 両対応
  - **密度レベル**: 単一 vs 複数（コンフォート / スタンダード / コンパクト）

#### 6.3 後続工程への申し送り事項
**実装への申し送り**: 表形式。列: `HO-I-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- CSS 変数名・Tailwind 設定・SCSS 変数のマッピング
- コンポーネントライブラリ採用の是非（shadcn-ui / MUI / Chakra 等）
- アイコンライブラリの選定（Lucide / Heroicons / Tabler 等）
- フォント配信方式（Google Fonts / セルフホスト / 可変フォント）
- ダークモード実装（CSS 変数切替 / data 属性 / class 切替）
- i18n ライブラリ選定・メッセージキー命名規則

**QA・テスト設計への申し送り**: 表形式。列: `HO-T-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- ビジュアルリグレッションテスト対象の範囲
- アクセシビリティ自動テスト（axe 等）の CI 組込
- 手動スクリーンリーダー検証の対象画面・頻度
- コントラスト比の自動検査

**HCD / UI・UX 設計への逆流候補**: 表形式。列: `HO-U-NNN / 内容 / 逆流理由 / 相談先`。典型:
- スタイルガイド作成中に発見した、HCD 側に反映すべき新しい A11Y 観点
- HCD 側にないフィードバック方針（`FB-NNN`）が必要になった局面
- ペルソナ（`PER-NNN`）の利用環境前提と実装可能な視覚仕様のギャップ（例: 「現場利用で想定されるデバイスでは、HCD 側の視覚方針が成立しない」）

## 各章の書き方（画面詳細）

### 1. 画面概要
- **UI-NNN**: 本ドキュメントが対象とする `UI-NNN` を明記する。名称・種別（「画面」）・対象利用者は I/F 側から引き継ぐ。
- **画面の目的**: 利用者が何をする画面か、1〜2 文で述べる。I/F 側の「概要」に矛盾しないこと。
- **関連 UC-NNN**: 本画面で実現する `UC-NNN` を列挙する。
- **関連 PER-NNN / SCN-NNN**: 本画面を主に利用するペルソナと、代表的な利用シナリオを HCD 側から引いて記載する。ペルソナの利用環境・身体特性（片手操作・屋外・低速回線 等）がレイアウトやレスポンシブ判断に直結するので、関連する特性を短く補足する。
- **関連 JOB-NNN / FLW-NNN**: 本画面が属する主タスクとタスクフローを HCD 側から引く。本画面がフローのどのステップか（起点 / 中間 / 終点）、主経路上にあるか代替経路か、中断再開が想定されるかを明示する。
- **本画面の主 CTA**: フロー（FLW-NNN）の目的を達成する主操作を 1 つ（多くても 2 つ）特定する。レイアウト・状態設計・レスポンシブ判断で「崩してはいけない要素」の根拠になる。
- **関連 UXI-NNN**: HCD 側で本画面の主タスクに関連して挙がっている UX 課題があれば参照する。本画面詳細（2〜9 章）でどこにそれを解消する設計を入れたかを、対応表として補足する。
- **主なアクター・権限**: どのロール・どの業務状態で本画面を開くか。権限による表示差分の概観（詳細は 5 章）。
- **入力・出力項目の参照**: I/F 側で定義済みの入力項目・出力項目一覧へのリンクを示す（**本ドキュメントで再掲しない**。差分があれば I/F 側を修正）。
- **起動 API の参照**: I/F 側で定義済みの `API-NNN` と対応イベントへのリンクを示す（同上、再掲しない）。
- **画面間遷移の参照**: I/F 側の画面遷移図での位置を示す（入り口: どの画面から来るか、出口: どこに抜けるか）。

### 2. レイアウト
- 画面全体の領域分割を **Mermaid の `flowchart`** または **ASCII アート風の table** のいずれかで示す。`LAY-NN`（画面内 ID）で各領域に ID を付ける。
- Mermaid 例（ワイヤフレーム相当）:
  ```
  flowchart TB
    H[LAY-01 ヘッダ]
    S[LAY-02 サイドナビ]
    M[LAY-03 メインコンテンツ]
    F[LAY-04 フッタ]
    H --- S & M
    S --- M
    M --- F
  ```
- 各領域について表形式で列挙する。列: `LAY-NN / 役割 / 主な CMP-NNN（このエリアに置く共通コンポーネント） / 固定 or スクロール / ブレークポイント変化の概要（詳細は 7 章）`。
- 画面固有のカスタム配置（スタイルガイドの `CMP-NNN` に該当しないもの）は、`LAY-NN` 直下に**ローカルな記述**として追加してよい。ただし複数画面で再利用する兆候があれば、スタイルガイド側に `CMP-NNN` として昇格させることを 10 章（注意事項）に記録する。
- 粒度は「どこに何が来るか」までで、ピクセル完全寸法には踏み込まない。数値を書くときはスタイルガイドのトークン（`DTK-NNN`）で参照する。

### 3. コンポーネント配置
- 領域（`LAY-NN`）ごとに、置くコンポーネントの配置と視覚的優先順位を記述する。表形式で列挙する。列: `配置順 / 領域 LAY-NN / CMP-NNN / バリアント・サイズ / 表示条件（常時 or 権限 or 状態依存） / 紐付く入力項目・出力項目（I/F 側） / 紐付く API-NNN（イベント起点） / 備考`。
- **配置順**は「上から下・左から右」の読み順をそのまま番号化する。
- **バリアント・サイズ**は `CMP-NNN` が定義するバリアント・サイズの中から選ぶ。ここで新しいバリアントを発明しない（発明が必要なら 10 章に昇格候補として記録）。
- **表示条件**が「常時」以外の場合、5 章（権限別）・4 章（状態別）・6 章（フォーム動的挙動）のどこで詳細化するかを注記する。
- **紐付く入力項目・出力項目**: I/F 側の項目名を参照する（再掲ではなく参照）。
- フォーム全体の構成は `FormField` の連なりとして表現する。入力項目のグルーピング（関連する項目をまとめるカードやフィールドセット）は本章で配置を決める。

### 4. 画面状態一覧（`ST-NN`）
画面が取りうる全状態を列挙し、各状態での見え方を定義する。`ST-NN` は画面内で閉じた ID（他画面の `ST-NN` と番号が重複してよい）。

本章は HCD / UI・UX 設計の `FB-NNN`（フィードバック方針）を画面上の具体表現に落とす中心となる。各 `ST-NN` の「見え方」列で `FB-NNN` との対応を明示する（例: 「ST-05 サブミット中: FB-003 に従い、短時間区分のスピナー + 送信ボタン disable」）。

- **基本状態**（多くの画面で共通）:
  - `ST-01 初期` / `ST-02 読込中（初回）` / `ST-03 空（データなし）` / `ST-04 正常表示` / `ST-05 サブミット中` / `ST-06 サブミット成功` / `ST-07 部分エラー` / `ST-08 致命エラー` / `ST-09 無権限`
  - これらは画面の性質により取捨選択する。例: 一覧画面は `ST-03 空`・`ST-07 部分エラー` を持つが、単票閲覧画面は `ST-07` の代わりに `ST-08` だけを持つ、等。
- 各状態について表形式で列挙する。列: `ST-NN / 状態名 / 発生契機（初期描画 / API-NNN の応答 / 入力変更 / 権限判定 / エラー ERR-NNN） / 対応 FB-NNN / 応答時間区分（瞬時 / 短時間 / 長時間 / 非同期 / 超長時間） / 見え方（スタイルガイドの CMP-NNN・DTK-NNN の参照で記述） / 主要メッセージの種別（成功 / 警告 / エラー / 情報） / ユーザーが取れる次の操作`
- **ローディング状態**は必ず「スケルトン / スピナー / 楽観的更新」のいずれを採るかを明示する。HCD 側 `FB-NNN` の応答時間区分（短時間 / 長時間）に従って選ぶ（短時間ならスピナー・長時間なら進捗表示＋キャンセル可否、のように）。スケルトンを採る場合、主要領域（`LAY-NN`）でのスケルトンの粒度（行数・カラム数・高さ）を概要レベルで示す。
- **空状態**は「単に空」で済ませず、「なぜ空か（データなし / フィルタにより 0 件 / 権限で閲覧不可）」を区別する。各区別に対する CTA（例: 「新規作成する」「フィルタを外す」「管理者に依頼する」）を明示する。HCD 側で「初見ユーザーの迷い」として `UXI-NNN` が挙がっている場合、本節がその解消点の 1 つになる。
- **エラー状態**は I/F 側の `ERR-NNN` と対応付ける。`ERR-NNN` の分類（入力不正 / 認証 / 認可 / 競合 / 存在しない / 業務ルール違反 / 外部依存失敗 / システム内部）ごとに、モーダル / トースト / インライン / ページ置換 のどの見せ方を採るかを、I/F 側 4 章の方針と HCD 側 `FB-NNN` の失敗フィードバック方針（責任をユーザーに帰さない書き方・次の一手の提示）に沿って具体化する。
- **破壊的操作前の確認状態**: HCD 側 `FB-NNN` の「破壊的操作前の確認」方針に沿って、確認の強度（軽確認 / 再入力 / 二要素 / 時間差）を状態として表現する必要があればここに `ST-NN` を追加する。
- **状態遷移図**: 必要に応じて Mermaid `stateDiagram-v2` で状態間の遷移を描く。遷移のトリガ（ユーザー操作・API 応答・タイマ）を矢印ラベルに付ける。状態数が 4 個以下で自明な場合は図を省いて表だけでもよい。

### 5. 権限別表示差分
- 本画面を開ける**全ての権限・状態**について、表示差分を表形式で列挙する。列: `権限条件（ロール / 所有関係 / 業務状態の組合せ） / 表示される LAY-NN / 非表示になる LAY-NN / 操作不可になる項目 or CMP-NNN / 代替表示（差分時のメッセージやガード画面） / 由来（UC-NNN の事前条件 / BRU-NNN / RULE-NNN）`
- **ロール階層**: I/F 側 5 章で宣言された権限モデルを前提とし、本章では**画面レベルの表示切替**に集中する。権限モデル自体の定義は行わない。
- **差分パターンの典型**:
  - 読取専用ロール: 編集操作（ボタン・入力項目）が disabled、もしくは編集用 CMP をまるごと非表示にし、閲覧用の静的表示に置き換える。
  - 所有者のみの操作（削除・公開）: 当該ボタンを所有者以外では非表示。
  - 業務状態による遷移制限: 例えば「確定済み」状態のレコードは編集不可、「下書き」なら編集可。
  - 組織境界・テナント境界: 他テナントのレコードは URL 直アクセスでも一覧に出さない、または「見つかりません」を返す（情報漏洩抑止のため「無権限」と区別）。
- **「無権限」と「存在しない」の表示切替方針**: セキュリティ上、無権限を知らせるべきでない場面（レコードの存在自体を秘匿したい場合）は「存在しない」として扱う方針を画面ごとに宣言する。
- **動的な権限変化**: セッション中に権限が変わりうる（別タブでの操作・管理者による権限剥奪）場合、API 呼出し時の 401/403 応答に対するフォールバック（再ログイン誘導・画面ロック）を宣言する。

### 6. フォーム動的挙動
- 入力フォームの**項目間の動的な相互作用**を列挙する。表形式で列挙する。列: `挙動 ID（DYN-NN） / トリガ項目 / 対象項目 / 挙動（値変更 / 表示・非表示 / 活性・非活性 / 選択肢絞込 / 自動補完 / リアルタイム検証） / 発火タイミング（onChange / onBlur / onSubmit / debounced） / 依存する業務条件（BRU-NNN / RULE-NNN）`
- `DYN-NN` は画面内で閉じた ID。
- **条件付き必須**: 「A が X のとき B は必須」のような条件付き必須は、I/F 側の `VR-NNN` の一部として定義されていることが前提。本章では**発火タイミングと UI 上の反映**を決める（例: サブミット時のみ判定、onBlur で即時表示）。
- **自動計算**: 合計金額・税込金額・期間日数など、入力から派生する値の計算方針。サーバ側再計算との関係（表示はクライアントで計算しても、確定はサーバ再計算優先、等）を宣言する。
- **選択肢の絞込**: 「A の選択に応じて B の候補が変わる」の場合、候補取得元（クライアント側定数 / API 呼出 / キャッシュ）と再取得のキャッシュ方針を記す。
- **リアルタイム検証の粒度**: 全項目を onChange で検証すると過剰。どの項目をどの粒度（onBlur / onChange / debounced 300ms）で検証するかを決める。エラーメッセージの表示位置はスタイルガイド側 `FormField` の仕様を参照する。
- **サブミット時の挙動**: 送信ボタンの disable 条件、二重送信防止、サーバ応答待ち中の画面状態（`ST-05 サブミット中`）との連携。

### 7. レスポンシブ挙動
- ブレークポイント（スタイルガイドの `DTK-NNN`）ごとのレイアウト変化を表形式で列挙する。列: `ブレークポイント（DTK-NNN） / 想定端末種別 / 各 LAY-NN の挙動（幅・折返し・積み替え・非表示） / ナビゲーションの変形（例: サイドバー → ハンバーガー） / テーブルの変形（横スクロール or カード化）`
- **モバイル（sm）**: 画面幅が狭い端末での優先順位を明示する（例: サイドナビはハンバーガー化、二次操作はオーバーフローメニューに退避、テーブルはカード形式に切替）。
- **タブレット（md / lg）**: サイドナビとメインコンテンツの同居の可否、2 カラムレイアウトの可否。
- **デスクトップ（xl 以上）**: コンテンツ最大幅の上限、余白の広げ方、3 カラム以上の採用可否。
- **崩してはいけないもの**: ブレークポイント間で一貫して保つべき要素（例: 画面タイトル・主 CTA は必ず視界に入るべき、等）を明示する。
- **特殊な幅**（超幅広・超狭）での挙動や、縦横比（縦長モバイル・横向きタブレット）への対応方針。
- 画面内でテーブルやデータグリッドを使う場合、幅が足りない時の挙動（横スクロール / 列の非表示 / カード化）を明示する。

### 8. イベントと画面遷移
- 本画面で発生するユーザー操作イベントと、それに対する画面・API の応答を表形式で列挙する。列: `イベント（CMP-NNN 上の操作） / トリガ条件（ST や権限の前提）/ 起動 API-NNN（I/F 側から引く） / API 呼出中の画面挙動（ST-05 等） / 成功時の挙動（遷移 / 状態変化 / メッセージ） / 失敗時の挙動（ERR-NNN に応じた表示） / 確認モーダルの要否`
- **破壊的操作**（削除・取消・公開停止）は必ず確認モーダルを経由する方針を宣言する。確認モーダルの構成（メッセージ・プライマリボタン色）はスタイルガイドの `CMP-Modal` を参照する。
- **非同期完了通知**: I/F 側で非同期境界がある操作（取り込み・エクスポート等）の場合、完了通知の見せ方（トースト / バッジ / 別画面での表示）を宣言する。
- **遷移元・遷移先**: I/F 側の画面遷移図と整合するよう、入口となる画面一覧と、出口（完了時・キャンセル時・エラー時）の遷移先を明示する。戻るボタン（ブラウザ履歴 / アプリ内ナビ）での挙動も宣言する。
- **画面内モーダル・ドロワー**: モーダル / ドロワーを開く操作は画面遷移ではないが、本表に含めて管理する（`CMP-Modal` / `CMP-Drawer` の開閉として）。

### 9. 多言語・テキスト長変動方針
- 本システムが多言語対応する場合の方針を本画面に適用する形で宣言する。
- **想定言語**: 対応言語と、それぞれのテキスト長変動の想定倍率（英語基準で日本語 ×1.3、ドイツ語 ×1.4、中国語 ×0.8 等、プロジェクトで採る方針）。
- **長文時の挙動**: ボタン幅固定で折返し / ボタン幅可変 / 省略（`...`）+ ツールチップ、の選択を操作別に決める。
- **テキスト方向**: RTL（アラビア語・ヘブライ語）対応の有無。対応する場合の左右反転方針（アイコンの向きも含む）。
- **数値・通貨・日付の書式**: ロケールに応じた区切り文字・通貨記号位置・日付順序の原則を宣言する。具体のフォーマット関数・ライブラリは実装工程。
- 本システムが多言語対応しない場合は「対応しない」と明記する（将来対応時の影響範囲を把握するため空欄にしない）。

### 10. 注意事項
画面詳細の注意事項も、スタイルガイドと同じく 3 区分で整理する。

#### 10.1 リスク・懸念点
- `RISK-NNN / 内容 / 影響範囲（LAY / CMP / ST / 権限 / 動的挙動 / レスポンシブ / 遷移） / 顕在化条件 / 暫定対応 / 実装・QA への申し送り`
- 典型カテゴリ:
  - ローディング状態でユーザーが同じ操作を何度も実行してしまう（二重送信・データ不整合）
  - 空状態の CTA が誤解を招く（「まだデータがない」のか「権限がない」のかが区別されていない）
  - 権限判定が画面側だけで行われ、サーバ側の再判定が漏れる（設計上の前提として I/F 側再検証が必要）
  - フォーム動的挙動（自動計算・選択肢絞込）の発火タイミングが遅く、ユーザーが旧い値でサブミットする
  - レスポンシブ変形で主要操作が視界から消える（特にテーブルのカード化時のアクションボタン）
  - 多言語化で長文が画面を崩す（特にボタン・タブ・カードヘッダ）
  - モーダルのフォーカストラップ不備でキーボード操作が画面下部に抜ける
  - 無権限・存在しないの区別がセキュリティ的に不適切（情報漏洩兆候）
  - 楽観的更新が失敗したときのロールバック挙動が未定義
  - 画面内で新しい視覚パターンが必要になったが、スタイルガイドに昇格させるかをまだ決めていない

#### 10.2 代替案と採らない理由
- `ALT-NNN / 対象判断 / 代替案概要 / 採らない理由 / 再検討条件`
- 最低でも以下については検討の痕跡を残す:
  - **レイアウトの骨格**: サイドバー常時表示 vs 折りたたみ vs なし
  - **テーブルの表示手段**: フラット表示 vs ページネーション vs 無限スクロール
  - **ローディング表現**: スケルトン vs スピナー vs 楽観的更新
  - **エラーの出し方**: モーダル vs インライン vs トースト
  - **フォームのサブミット先挙動**: 同一画面に残る vs 一覧画面へ戻る vs 詳細画面へ遷移
  - **確認モーダルの採否**: すべての破壊操作で採る vs undo 可能な操作では省略
  - **モバイル時のテーブル**: 横スクロール vs カード化 vs 列の優先度順に省略

#### 10.3 後続工程への申し送り事項
- 本画面詳細では決め切らない論点を、**工程別**に分けて記録する。

**実装への申し送り**: 表形式。列: `HO-I-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- 具体のコンポーネントライブラリ props への対応
- 画面固有の微調整値（パディング具体 px 値等）のトークン化要否
- 画面内で一度だけ使う視覚パターンのスタイルガイド昇格要否
- 状態管理ストア構造（グローバル / 画面ローカル）
- URL 設計の最終形（クエリパラメータ vs パスパラメータ）
- データ取得戦略（SSR / CSR / ISR / SWR）

**QA・テスト設計への申し送り**: 表形式。列: `HO-T-NNN / 内容 / 想定選択肢 / 決定責任者 / 相談先`。典型:
- 状態別（`ST-NN`）のビジュアルリグレッション対象
- 権限別表示差分の網羅テスト
- フォーム動的挙動のインタラクションテスト
- アクセシビリティ検証（スクリーンリーダー・キーボード操作）
- レスポンシブ検証の対象ブレークポイント

**スタイルガイドへの昇格候補**: 本画面で新たに発生した視覚パターンのうち、再利用可能性があるもの。列: `CAN-NNN / パターン概要 / 本画面での使用箇所 / 再利用可能性の見立て / 昇格時の CMP 候補名`。

**HCD / UI・UX 設計への逆流候補**: 表形式。列: `HO-U-NNN / 内容 / 逆流理由 / 相談先`。典型:
- 画面詳細設計中に発見した、HCD 側の `FLW-NNN` と矛盾する画面構造（フローをやり直すべきか、画面側を曲げるべきか）
- HCD 側で対象外とされていた代替フロー（中断再開・権限変化時のフォールバック）が、実装上必ず必要になった
- ペルソナの想定環境（例: モバイル主体）と画面の情報量（例: 大量テーブル）のギャップ
- `UXI-NNN` として記録されていない新しい UX 課題が、画面詳細設計中に浮上した

## 図解の記法ルール
要件・アーキ・データ・IF・コンポーネント・クラス設計と同様、図は Mermaid コードブロック（` ```mermaid ` 〜 ` ``` `）で記述し、画像ファイルや外部ツール固有形式は使わない。

- **レイアウトのワイヤフレーム**: `flowchart TB` または `flowchart LR` で領域分割を示す（「図解的」な位置関係までで、ピクセル精度は不要）。ASCII アート風の罫線表で代替してもよい。
- **画面状態遷移**: `stateDiagram-v2` で `ST-NN` 間の遷移を示す。トリガ（ユーザー操作・API 応答）を矢印ラベルに付ける。状態数が 4 個以下で自明なら省略可。
- **権限別表示差分**: 図よりも表の方が網羅しやすいので、原則として表で示す。
- **フォーム動的挙動**: 項目間の依存が多い場合は `flowchart` で項目→項目の関係を示してもよい。
- **レスポンシブ変化**: ブレークポイント別のワイヤを複数貼るか、変化点だけを表にする。
- **画面間遷移**: I/F 側の画面遷移図を参照し、本ドキュメントで重複して描かない。本画面を中心とした入口・出口だけを書くなら簡潔な `flowchart` でよい。

## 上流設計書との紐付け
- すべての**画面詳細ファイル**は、I/F 側に存在する `UI-NNN`（種別「画面」）と 1 対 1 で対応する。対応する `UI-NNN` がない画面ファイルは作らない（必要ならインタフェース設計側に戻って `UI-NNN` を追加する）。
- 画面の入力項目・出力項目は I/F 側から**参照のみ**とし、本ドキュメントで再定義しない。差分があれば I/F 側を修正し、本ドキュメントは追従する。
- 画面のイベントから起動される `API-NNN` は I/F 側で定義済み。本ドキュメントは呼出中の UI 挙動（ローディング・トースト・遷移）を追記するに留める。
- 画面状態一覧（`ST-NN`）のエラー状態は、I/F 側の `ERR-NNN` のうち本画面で表出しうるものを受け止める。I/F 側 4 章の「利用者向け提示の I/F 別方針」（画面: モーダル / トースト / ページ遷移 / フォーム再表示）に沿って具体化する。
- フォーム動的挙動（`DYN-NN`）の条件付き必須や自動計算は、I/F 側の `VR-NNN` やデータ側の `RULE-NNN`・`BRU-NNN` を参照する。本ドキュメントで新しい業務ルールを発生させない。
- 権限別表示差分は、要件側のユースケース事前条件・データ側の `RULE-NNN`（所有関係・状態遷移の制約）を根拠にする。本ドキュメントで新しい権限モデル・ロールを定義しない。
- スタイルガイドの `DTK-NNN`・`CMP-NNN` は、要件側の非機能要件（ユーザビリティ・アクセシビリティ・ブランド）および HCD 側の `PER-NNN`・`SCN-NNN`・1 章 UX 設計方針を根拠にする。根拠のないトークン・コンポーネント（「流行っているから」「慣れているから」）は採用しない。
- 画面詳細 1 章で明示する「画面の主 CTA」と「主要経路の位置付け」は、HCD 側の `JOB-NNN`・`FLW-NNN` に一致すること。主 CTA が曖昧な画面は、HCD 側のフロー設計が曖昧である兆候なので注意事項に記録する。
- 画面状態一覧（`ST-NN`）の応答時間区分と見せ方は、HCD 側 `FB-NNN` の方針に沿うこと。HCD 側と矛盾する独自方針を本ドキュメントで発生させない。
- アクセシビリティ方針（スタイルガイド 4 章）は、HCD 側の `A11Y-NNN`（論理方針）に対応し、具体値（WCAG 準拠レベル・コントラスト比・最小寸法 等）に落とすものであること。`A11Y-NNN` にない新しい観点を本ドキュメントで発生させない（発生させたら HCD 側への逆流候補として注意事項に記録する）。
- 画面詳細で `UXI-NNN`（UX 課題）の解消に寄与する設計（フォーム動的挙動・状態遷移・権限差分 等）を入れた場合、該当箇所で `UXI-NNN` を参照して「HCD 側の課題意識とつながっている」ことを示す。

## Checklist（出力前の自己チェック）
出力直前に以下を順に確認し、満たさない項目があれば修正する。曖昧なまま残すより、未確定である旨を「注意事項」に明記して残すほうがよい。スタイルガイドと画面詳細の両方を作る場合は、両方について該当項目を確認する。

### 1. I/F 側と画面詳細の整合（画面詳細側のチェック）
- 本画面詳細ファイルは、I/F 側の `UI-NNN`（種別「画面」）と 1 対 1 で対応しているか。対応する `UI-NNN` がない画面ファイルになっていないか。
- 画面の入力項目・出力項目を本ドキュメント内で再定義していないか（I/F 側への参照に留めているか）。
- 画面イベントから起動する `API-NNN` の対応付けを本ドキュメントで変更していないか。
- I/F 側で宣言された「利用者向け提示の I/F 別方針」（モーダル / トースト / ページ遷移 / フォーム再表示）が、本画面の各 `ERR-NNN` に対して具体化されているか。
- I/F 側の画面遷移図での入口・出口と、本ドキュメント 8 章の遷移記述が矛盾していないか。

### 1.5 HCD / UI・UX 側との整合（画面詳細側のチェック）
- 画面詳細 1 章（画面概要）に、関連 `PER-NNN` / `SCN-NNN` / `JOB-NNN` / `FLW-NNN` が明示されているか。
- 本画面の「主 CTA」が HCD 側の `JOB-NNN`・`FLW-NNN` と整合しているか。曖昧な場合、HCD 側のフロー設計に戻す申し送りが記録されているか。
- 画面状態一覧（`ST-NN`）の応答時間区分・見せ方が、HCD 側の対応する `FB-NNN` と一致しているか。
- 破壊的操作の確認方針が、HCD 側 `FB-NNN` の確認強度（軽確認 / 再入力 / 二要素 / 時間差）と矛盾していないか。
- HCD 側の `UXI-NNN`（UX 課題）が本画面に関連する場合、本画面詳細のどこで解消策が設計されているかが追跡できるか。
- スタイルガイドのアクセシビリティ方針の具体値が、HCD 側 `A11Y-NNN` の論理方針を過不足なくカバーしているか。独自観点を発生させていないか。

### 2. スタイルガイドと画面詳細の整合（両ドキュメントに跨るチェック）
- 画面詳細で参照している `DTK-NNN`・`CMP-NNN` が、スタイルガイドに実在するか（採番ミスがないか）。
- 画面詳細で新しい視覚パターンを**画面内にローカルに**定義していないか。再利用性があれば 10.3 の昇格候補に記録されているか。
- スタイルガイドで宣言した方針（密度レベル・ダークモード採否・モバイルファースト等）と、画面詳細の記述が矛盾していないか。
- ブレークポイント（スタイルガイドで定義）が、画面詳細 7 章のレスポンシブ挙動表で参照されているか。

### 3. 状態と権限の網羅
- 画面の状態一覧（`ST-NN`）が、「初期 / 読込中 / 空 / 正常 / サブミット中 / エラー / 無権限」のうち本画面で発生しうるものを漏れなく列挙しているか。発生しないものは「該当なし」と明記しているか。
- 各状態に対する**発生契機・見え方・次の操作**が揃っているか。
- 権限別表示差分について、ロール × 業務状態の組合せで表示が変わる箇所が表に網羅されているか。
- 「無権限」と「存在しない」の表示切替方針が、セキュリティ上の判断として明示されているか。
- 動的な権限変化（セッション中の剥奪・管理者による変更）に対するフォールバックが宣言されているか。

### 4. フォームとバリデーションの整合
- すべてのフォーム入力項目について、I/F 側の `VR-NNN` とのマッピングが確認できるか。
- 条件付き必須・自動計算・選択肢絞込の発火タイミングが宣言されているか。
- リアルタイム検証の粒度（onBlur / onChange / debounced）が明示されているか。全項目 onChange のような過剰設定になっていないか。
- サーバ側再検証が最終判断である原則が破られていないか（画面側検証だけで業務判定を完結させていないか）。
- サブミット時の二重送信防止・送信ボタン disable・サーバ応答待ち中の状態（`ST-05`）との連携が明示されているか。

### 5. レスポンシブの網羅
- スタイルガイドで定義された全ブレークポイントについて、本画面のレイアウト変化が記述されているか（記述不要なブレークポイントは「変化なし」と明記）。
- モバイル時に主要 CTA が視界から消える・テーブルが横にはみ出すといった、典型的な崩壊パターンの対処が宣言されているか。
- 崩してはいけない要素（画面タイトル・主 CTA）が明示されているか。

### 6. アクセシビリティの確認
- キーボード操作の Tab 順序が意図通りか（特にモーダル内のフォーカストラップ、Escape キャンセル原則）。
- スクリーンリーダー向けのラベル・ライブリージョン方針が、状態変化に対応しているか（トースト表示はスクリーンリーダーにも通知されるか）。
- コントラスト比がスタイルガイドの基準を満たす組合せのみを使っているか。
- 画像・アイコンの alt テキスト方針が本画面に適用されているか。
- タッチターゲットの最小寸法・余白が守られているか。

### 7. 粒度の侵食が起きていないか
- **下向きの侵食**（本ドキュメントに実装が紛れている）: 具体の CSS 変数名・Tailwind クラス名・React / Vue 固有構文・ピクセル完全値がベタ書きされていないか。紛れていたら「10.3 実装への申し送り」に切り出す。
- **上向きの侵食（HCD / UI・UX 設計）**: ペルソナ・シナリオ・JOB・フロー・UXI・FB 方針・A11Y 方針の**論理決定**を本ドキュメントで発明していないか。HCD 側にない新しい方針を発生させていたら、HCD 側への逆流候補として注意事項に記録する。
- **横向きの侵食（インタフェース設計）**: `UI-NNN` の入出力項目・`API-NNN` の対応・`VR-NNN` の条件・`ERR-NNN` の分類・画面遷移の存在を本ドキュメントで再定義していないか。
- **横向きの侵食（データ設計）**: `ENT-NNN` の属性定義・`RULE-NNN` の制約内容を本ドキュメントで再定義していないか。
- **上向きの侵食（要件）**: 新しい `BRU-NNN` や画面外からの要件が、本ドキュメントで黙って発生していないか。発生していたら「10.1 リスク・懸念点」に記録し、要件側・I/F 側への波及候補とする。
- **スタイルガイドの空洞化**: コンポーネント仕様が「default のみ」で状態別（hover / focus / disabled / loading / error）が未定義のまま残っていないか。
- **画面詳細の空洞化**: 状態一覧・権限差分・フォーム動的挙動・レスポンシブが「実装で決める」に丸投げされていないか。ここで決め切る。

### 8. 図と表の整合
- レイアウト図（画面詳細 2 章）に登場する `LAY-NN` が、3 章のコンポーネント配置表にすべて現れているか。
- 状態遷移図（画面詳細 4 章、書いた場合）に登場する `ST-NN` が、すべて表側に存在するか。
- 画面詳細 3 章のコンポーネント配置で参照する `CMP-NNN` が、すべてスタイルガイドのコンポーネントカタログに存在するか。
- 画面詳細 7 章のレスポンシブ挙動で参照するブレークポイントが、スタイルガイド 2.6 に存在するか。
- スタイルガイドで「採用する」と宣言したトークン種別・コンポーネント種別が、2〜3 章の個別記述と矛盾していないか。

## 実行の進め方（推奨）
1. HCD / UI・UX 設計書（`docs/design/uiux/uiux-design.md`）が存在しない場合は、まず `/generate-hcd-uiux-design` を先行させることを推奨する。存在しないまま本スキルを走らせても、ペルソナ・フロー・FB・A11Y 方針が暗黙前提として本ドキュメント側で散発的に発生してしまう。上流の欠落は注意事項に記録し、HCD 側への逆流候補として残す。
2. スタイルガイド（`docs/design/screen/style-guide.md`）が存在しない場合は、画面詳細より先に**スタイルガイドを完成させる**。上流（要件・HCD の 1 章 UX 方針・ブランド要件・`A11Y-NNN`）から方針・トークン・コンポーネントを順に固める。
3. スタイルガイドが存在する状態で、画面詳細を `UI-NNN` 単位に 1 ファイルずつ作成する。I/F 側の `UI-NNN`（種別「画面」）を全て網羅する必要があるが、1 度に全画面を書く必要はない。主要な画面（HCD 側で優先度の高い `JOB-NNN` に関連する画面・権限差分が多い画面・状態遷移が複雑な画面・複数 UXI-NNN が関連する画面）から優先して着手する。
4. 画面詳細を書く中で新しい視覚パターンが必要になった場合、無断で画面側に書かず、スタイルガイド側に `DTK-NNN` / `CMP-NNN` を追加してから画面側で参照する。昇格判断に迷う場合は、画面側に仮配置しつつ 10.3 の昇格候補に記録し、他画面でも必要になった時点でスタイルガイドに昇格させる。
5. スタイルガイドと画面詳細はレビュー単位を分ける。スタイルガイドはデザイナー・UX・アクセシビリティ・ブランドの観点を中心にレビュー、画面詳細は業務担当・開発者・QA の観点を中心にレビューすると噛み合いやすい。
