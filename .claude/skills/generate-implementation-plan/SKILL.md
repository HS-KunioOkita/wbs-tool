# Goal

設計書群をもとに、レビュー可能・テスト可能・リリース可能な実装工程計画書を 1 本作成する。

この Skill の目的は、タスクをただ列挙することではなく、
「この計画通りに進めれば、設計と一致した品質でリリースまで到達できる」と判断できる工程設計を行うことである。

---

# Scope

対象:

- 環境構築・基盤整備
- DB / バックエンド / フロントエンド / 外部連携 / インフラ作業の実装タスク分解
- タスクの依存関係と実装順序
- 各工程に紐づく品質ゲート（Formatter / Linter / 型 / 単体 / E2E / レビュー）
- 実装レビュー計画とテストレビュー計画
- 単体テスト計画と E2E テスト計画の実施計画（既に test-design がある場合はそれを実施計画に翻訳する）
- リリース判定基準

対象外:

- 詳細な実装コードの作成
- スケジュール（日付・人月）の算定（要員数や稼働率に依存するため、本計画では「順序」と「依存」のみ扱う）
- 詳細なテストケースの再設計（test-design の責務）
- 詳細な画面・API 仕様の再設計（screen / interface 設計の責務）
- 本番運用手順書の作成

---

# Role

あなたは、テックリード兼実装計画担当として振る舞う。

次の観点を重視する:

- 設計とのトレーサビリティ（どの設計項目がどのタスクで実装されるか）
- レビュー可能サイズへのタスク分解
- 依存関係の明示と Critical Path の特定
- 品質ゲートの工程組み込み（後付けにしない）
- リリース可否の判断基準
- 過剰計画を避け、リスクと業務影響に応じた重点化

---

# Input

以下の情報を読み取る。

- 要件定義（機能要件 / 非機能要件 / ユースケース）
- アーキテクチャ設計
- コンポーネント設計
- クラス設計
- データ設計
- インタフェース設計（画面 I/O・API・外部連携）
- HCD / UIUX 設計
- 画面設計
- インフラ設計
- テスト設計（あれば実施計画に翻訳する）
- 未決事項・前提・仮定

入力が不足している場合は、計画の精度に影響する重要事項のみ最大 5 件まで質問する。
入力が膨大な場合は、まず一覧化（機能・画面・API・データ・外部連携）し、それを土台に分解する。

# Quality Standards References

このスキルは、計画を組む際に以下の品質基準ファイル群を参照する。
プロジェクト側に `.claude/rules/*.md` があればそれを優先的に読み、なければ本スキル同梱の `references/*.md` を読むこと。

| 観点                                                                          | プロジェクト側ファイル（優先）      | スキル同梱ファイル（フォールバック） |
| ----------------------------------------------------------------------------- | ----------------------------------- | ------------------------------------ |
| 品質ゲート（Formatter / Linter / 型 / 単体 / E2E / Review / Release Blocker） | `.claude/rules/quality-gate.md`     | `references/quality-gate.md`         |
| レビュー基準（観点・分類・ブロッキング条件）                                  | `.claude/rules/review-standard.md`  | `references/review-standard.md`      |
| テスト基準（単体・E2E・カバレッジ方針・必須ケース）                           | `.claude/rules/testing-standard.md` | `references/testing-standard.md`     |
| コーディング基準（責務分離・命名・関数粒度・禁止事項）                        | `.claude/rules/coding-standard.md`  | `references/coding-standard.md`      |

## 参照タイミング

- **計画着手前**: 4 ファイルすべてを軽く目を通し、本プロジェクトの品質方針を把握する。
- **§5 品質ルール / 品質ゲート作成時**: `quality-gate.md` を読み、Required Quality Gates と Release Blockers を計画に展開する。
- **§6 実装レビュー計画作成時**: `review-standard.md` を読み、観点とブロッキング条件を引き写す。
- **§7 単体テスト計画 / §8 E2E テスト計画作成時**: `testing-standard.md` を読み、必須観点とカバレッジ方針を反映する。
- **§3 タスク分解時のレビュー観点書き出し**: `coding-standard.md` を読み、責務分離・命名・依存方向・禁止事項を反映する。

## 重要

これらの基準は「計画書に何を書くか」「リリース可と判断する閾値」を直接決める。計画書の §5 / §6 / §7 / §8 / §10 は、参照ファイルに書かれた内容と矛盾しないように書くこと。
参照ファイルに記載のない基準を勝手に追加せず、追加が必要な場合は「未決事項・リスク」に挙げて確認を求める。

# Workflow

## 1. 設計情報の読み取り

設計書から以下を抽出する。

- 機能一覧 / ユースケース一覧
- 画面一覧（UI-NNN）
- API / 外部 I/F 一覧
- データモデル（主要エンティティ・更新パターン）
- コンポーネント / クラス（MOD-NNN / CLS-NNN）
- 権限・ロール
- 非機能要件（性能 / 可用性 / セキュリティ / 監視 / 運用）
- インフラ構成（実行環境・ネットワーク・デプロイ方針）
- リリース上のリスク・未決事項

## 2. タスク分解

抽出した内容を、以下のレイヤに沿って分解する。タスク ID は `T-NNN` 形式。

| レイヤ         | 例                                                                           |
| -------------- | ---------------------------------------------------------------------------- |
| 環境構築       | リポジトリ / ローカル環境 / CI / lint / formatter / test runner / pre-commit |
| 基盤           | 認証基盤 / ログ / 監視 / 共通エラー / 設定管理                               |
| データ         | スキーマ / マイグレーション / シード / バックアップ方針確認                  |
| バックエンド   | ドメインモデル / ユースケース / API / バリデーション / 認可                  |
| フロントエンド | 共通レイアウト / 画面別実装 / 状態管理 / フォーム / エラー表示               |
| 外部連携       | クライアント / リトライ / タイムアウト / モック                              |
| インフラ       | ネットワーク / シークレット / デプロイ / ロールバック                        |
| 観測性         | 構造化ログ / メトリクス / アラート                                           |
| テスト実施     | 単体テスト実装 / E2E 実装 / テストデータ整備                                 |
| レビュー       | 実装レビュー / テストレビュー / 設計乖離レビュー                             |
| 仕上げ         | 修正 / ドキュメント反映 / リリース判定                                       |

タスクは「レビュー可能サイズ」（目安: 半日〜2 日程度で 1 PR に収まる粒度）に分割する。
大きすぎるタスクはサブタスクに分解する。

## 3. 依存関係と実装順序

- タスク間の依存（前提タスク・並行可能タスク）を明示する。
- Critical Path（リリースを律速する経路）を特定する。
- 基本順序は以下を骨格とし、依存に応じて調整する。

1. 環境構築 → 2. 基盤 → 3. データ → 4. バックエンド → 5. フロントエンド → 6. 統合 → 7. 単体テスト整備 → 8. E2E 整備 → 9. レビュー → 10. リリース判定

「テストを後付けにしない」ため、テスト実装タスクは対応する実装タスクと近接配置するか、TDD を採用する場合は実装タスクに含めて表現する。

## 4. 品質ゲートの工程組み込み

各工程に品質チェックを紐づける。後付けの「最後にまとめてテスト」は禁止。

| 工程       | 紐づく品質チェック                               |
| ---------- | ------------------------------------------------ |
| 実装中     | Coding Standard 準拠（命名・責務・副作用明示）   |
| Commit     | Formatter / Linter（pre-commit）                 |
| PR 作成    | Type Check / Unit Test（CI）                     |
| Merge 前   | 実装レビュー / テストレビュー / 設計乖離レビュー |
| Release 前 | E2E / 非機能確認 / Release Blocker 不在の確認    |

## 5. レビューとテストの計画

- 実装レビュー観点（設計一致 / セキュリティ / エラー処理 / 保守性）をタスク群ごとに用意する。
- テスト計画は、単体テストと E2E テストの責務を分けて記述する。
- E2E は「壊れるとリリースできない経路」に絞り、増殖させない。
- test-design がある場合は、その優先度と本計画の優先度を一致させる。

## 6. リリース判定

リリース可と判断するための最終ゲートを定義する。

- すべての Required Quality Gate を通過
- 主要 E2E シナリオが成功
- Release Blocker が存在しない
- 未決事項がリリース判断者に明示されている

# Planning Rules

- タスクはレビュー可能サイズ（目安: 半日〜2 日 / 1 PR）に分割する。
- すべてのタスクに「関連設計」を明示し、設計とのトレーサビリティを確保する。
- 実装順序には依存関係の理由を併記する。
- テストを「後でまとめて」配置しない。実装と近接させるか、TDD として実装タスク内に含める。
- E2E を増やしすぎない。リリースブロッカー経路に絞る。
- Critical Path 上のタスクを優先する。
- 環境構築・基盤・観測性を後回しにしない。
- 仮の前提や未決事項は「未決事項・リスク」に必ず記載する。

---

# Editing Policy

- 網羅性よりも「リリース可否を判断できる計画」を優先する。
- タスク数を増やすことが目的ではない。レビュー可能性を優先する。
- 設計書に書かれていることをコピーせず、「実装の観点で何をやるか」に翻訳する。
- 曖昧な要件は曖昧なまま計画に含めず、未決事項として切り出す。
- 既存の設計書 ID（UC / UI / MOD / CLS / API など）が存在する場合は必ず引用する。

---

# Final Rule

「実装できる」だけでは不十分。

以下を満たす計画であること。

- 設計と一致している（トレーサビリティが取れる）
- レビュー可能である（タスクが適切な粒度）
- テスト可能である（品質ゲートが組み込まれている）
- リリース可能である（判定基準とブロッカーが明示されている）
