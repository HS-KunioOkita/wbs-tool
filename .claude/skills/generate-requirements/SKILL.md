# 要件定義書の作成
以下の入力から、要件定義書を作成してください。

## 要求モデリングの原則
要件定義はソフトウェアエンジニアリングにおける問題解決の第一歩であり、以下の 5 原則に従って記述する。各原則は本スキルが生成する成果物（`functional.md` / `usecase/{UC-NNN}/usecase.md` / `non-functional.md`）のどこで満たされるかとセットで意識すること。

### 第1原則: 情報ドメインを表現する
問題の情報ドメインを表現し、理解しなければならない。情報ドメインには以下が含まれる:
- システムへの入力データ（エンドユーザ、他システム、外部デバイス等から与えられる）
- システムからの出力データ（ユーザインタフェース、ネットワークインタフェース、帳票や図等）
- 収集したデータを永続的に維持するためのデータストア

本スキルでの反映:
- `functional.md` の「データ定義（ENT-NNN）」でデータストア相当の情報塊を列挙する
- `functional.md` の「インタフェース要件」で入出力の接点を 4 分類（UI-NNN / SIF-NNN / HIF-NNN / CIF-NNN）で俯瞰する
- 各 `usecase.md` の「アクターがCRUDする情報」で入出力データを ENT-NNN に紐付けて明示する
- 各 `usecase.md` の「関連インタフェース」でそのユースケースが利用する UI/SIF/HIF/CIF を ID で明示する

### 第2原則: ソフトウェアの実現する機能を定義する
ソフトウェアが実現する機能を定義しなければならない。機能には以下が含まれる:
- エンドユーザに直接的な利益をもたらす機能
- 利用者の目に見えるフィーチャを裏で支援する機能
- 入力データを変換する機能
- 内部処理や外部システムの制御を司る機能

本スキルでの反映:
- `functional.md` の「ユースケース一覧」でユーザに見える機能群を俯瞰する
- 各 `usecase.md` の「主要なタスクや機能」で、ユーザ可視の機能と、それを支援する裏側の機能（データ変換・制御・外部連携など）の両方を記載する

### 第3原則: 外部イベントへの反応を表現する
システムの外部で発生したイベントに対する反応を表現しなければならない。コンピュータソフトウェアの振る舞いは、外部環境とのやりとり（エンドユーザの入力、外部システムからの制御データ、ネットワーク経由の監視データ等）により決定される。

本スキルでの反映:
- 各 `usecase.md` の「基本フロー / 代替フロー / 例外フロー」を「アクターの動作 → システムの反応」の連鎖として記述する
- `sequenceDiagram` でアクターとシステム間のやり取り（イベントと反応）を可視化する
- 状態を持つ対象は `stateDiagram-v2` でイベント契機の状態遷移として表現する
- 「外部システム連携」ではイベント契機（同期 / 非同期）と、連携失敗時の取り扱い方針を明示する

### 第4原則: 層状（階層的）構造で詳細を隠蔽する
情報・機能・振る舞いを表現するモデルは、層状の（あるいは階層的な）構造で詳細を隠蔽しなければならない。複雑な問題はそのまま解決せず、「分割（partitioning）」「関心事の分離（separation of concerns）」により、比較的小さく理解しやすい問題まで繰り返し分割する。

本スキルでの反映:
- 全体俯瞰（`functional.md`）→ ユースケース詳細（`usecase/UC-NNN/usecase.md`）→ 設計工程成果物（`docs/design/` 配下の機能・画面単位）という階層で詳細を隠蔽する
- `functional.md` のデータ定義は「データの塊」粒度に留め、属性詳細・型・正規化は設計工程に委ねる
- エンティティ関連図 (`erDiagram`) は多重度・依存関係レベルに留め、属性は記載しない
- ユースケース単位でディレクトリを分けることで、追加・変更の影響範囲を局所化する

### 第5原則: 本質から実装詳細へ進める
分析タスクは、本質的な情報から実装の詳細へと進めよ。問題の「本質（essence）」は、解決策をどのように実装するのか考えずに、エンドユーザの視点で記述する。実装の詳細は設計モデルの一部として、その本質の実現方法を示す。

本スキルでの反映:
- 要件定義書はユーザ / 業務視点で「何をしたいか（What / Why）」を記述する
- 技術選択・UI の具体的操作方法・通信プロトコル・データ属性詳細・API 仕様・ロック方式などの「どう実現するか（How）」は要件に含めない
- 要件定義段階で確定できないが設計以降で決めるべき論点は、各 `usecase.md` の「設計工程への申し送り事項」に切り出す（決定すべき内容・想定選択肢・決定責任者を併記）

## 出力ファイル
1. `docs/requirements/functional.md` — 機能要件概要（プロジェクト全体像とユースケース一覧）
2. `docs/requirements/usecase/{ユースケースID}/usecase.md` — ユースケース毎の詳細（ID 例: `UC-001`）
3. `docs/requirements/non-functional.md` — 非機能要件

ユースケース毎にファイルを分割するのは、要件定義レベルの成果物をユースケース単位で増やしていけるようにするためです。1 つのユースケースには複数の機能・画面が関与し得るため、設計工程以降の成果物（画面設計・機能設計・テストケース等）は本ディレクトリには置かず、別途 `docs/design/` 配下に機能単位・画面単位で配置します。

`usecase/{ユースケースID}/` 配下に追加してよいのは、要件定義工程内で発生する補助資料に限ります（例: 詳細なフロー図、ユースケース固有の業務ルール補足、関係者ヒアリングメモ、トレーサビリティ表など）。

新規ユースケース追加時は、既存ファイルに手を入れずに新しいディレクトリを作るだけで拡張できます。

## 図解の記法ルール
要件定義書中のすべての図解（ユースケース図、フロー図、シーケンス図、ER 図、状態遷移図など）は、Markdown 内の Mermaid コードブロック（```mermaid ... ```）で記述する。画像ファイル（PNG / JPG / SVG）や外部ツール固有形式（drawio など）は使用しない。

用途と推奨ダイアグラム:
- ユースケース全体俯瞰: `flowchart` または `graph` でアクターとユースケースの関連を図示
- 基本フロー / 代替フロー: `sequenceDiagram` でアクターとシステム間のやり取りを図示
- エンティティ関連: `erDiagram`
- 状態遷移: `stateDiagram-v2`

## functional.md の構成
- プロジェクト概要（背景・目的・スコープ）
- ステークホルダー定義
- ユースケース一覧（表形式: UC-NNN / 名称 / アクター / 概要 / 詳細へのリンク）
 - 詳細列には `usecase/UC-NNN/usecase.md` への相対リンクを記載する
- データ定義（エンティティ概要）
 - システムが扱う「データの塊」を粒度として列挙する（例: ユーザー情報 / 顧客情報 / 注文情報 / 商品情報）。論理データモデル相当の属性詳細・型・正規化は記載しない（その粒度は設計工程で扱う）。
 - 表形式で記載: ENT-NNN / 名称 / 概要 / 主な保有情報（代表的な要素を箇条書きで 3〜5 個程度）/ 関連UC
 - エンティティ間の関連は Mermaid の `erDiagram` で記載する。多重度・依存関係のレベルに留め、属性は記載しない。
- インタフェース要件（システム全体のインタフェース一覧）
 - システムが外部（人・他システム・機器・ネットワーク）とやり取りするすべての接点を、以下 4 分類で一覧化する。詳細仕様（画面項目・電文フォーマット・端子ピン配・暗号スイート等）は設計工程で確定するため、要件定義では「何と接続するか」「目的」「概要レベルの方式」までを記述する。
 - **ユーザインタフェース（UI-NNN）**: 表形式で記載: UI-NNN / 画面・帳票名 / 種別（画面 / 帳票 / 通知）/ 対象利用者 / 概要 / 関連UC。併せて、システム全体で共通する UI 要件を箇条書きで記載する:
  - 対応デバイス（PC / タブレット / スマートフォン）と最小画面サイズ
  - 対応ブラウザ・OS バージョン
  - 多言語・ロケール対応（対応言語 / 日付・通貨・タイムゾーン表記）
  - 印刷・帳票出力要件（様式 / 用紙サイズ / PDF 等）
  - 画面遷移の全体像は Mermaid `flowchart` で記載可能（粒度は画面単位、遷移契機のみ）
 - **システム間インタフェース（SIF-NNN）**: 表形式で記載: SIF-NNN / 連携先システム名 / 連携方向（送信 / 受信 / 双方向）/ 目的 / 連携手段（REST / ファイル / メッセージング等、想定範囲で）/ 同期 or 非同期 / 連携頻度・概算データ量 / 関連UC。詳細仕様は各 `usecase.md` の「外部システム連携」から SIF-NNN を参照する。
 - **ハードウェアインタフェース（HIF-NNN）**: 接続する物理機器がある場合のみ記載。表形式: HIF-NNN / 機器種別（プリンタ / スキャナ / バーコードリーダ / IC カードリーダ / IoT センサ等）/ 接続方式（USB / Bluetooth / LAN / シリアル等、想定範囲で）/ 目的 / 関連UC。
 - **通信インタフェース（CIF-NNN）**: ネットワーク越しの通信要件を記載。表形式: CIF-NNN / 通信相手 / プロトコル（HTTPS / SFTP / MQTT 等）/ 暗号化・認証方式（想定範囲で）/ ネットワーク条件（固定 IP / VPN / 専用線 等）/ 関連UC・SIF。
- ビジネスルール（表形式: BRU-NNN / 内容 / 関連UC）
- 用語集
- 参照ドキュメント

## usecase/{ユースケースID}/usecase.md の構成
ユースケース 1 件につき 1 ファイル。以下を記載:
- ユースケースID / 名称
- アクター（主アクター・副アクター）
- 概要・目的
- 事前条件
- 事後条件（成功時 / 失敗時）
- 主要なタスクや機能
- 基本フロー（番号付きステップ）
- 代替フロー（分岐条件と差分ステップ）
- 例外フロー（発生条件と例外時の振る舞い）
- アクターがCRUDする情報は何か
 - `functional.md` のデータ定義（ENT-NNN）を参照し、ユースケースの中で C（作成）/ R（参照）/ U（更新）/ D（削除）のどれを行うかを表形式で記載する（列: ENT-NNN / エンティティ名 / 操作 / 操作の概要）。
- 関連インタフェース
 - `functional.md` のインタフェース要件一覧から、本ユースケースで利用する ID を列挙する: UI-NNN（操作する画面・出力する帳票）/ SIF-NNN（連携する外部システム）/ HIF-NNN（使用する物理機器）/ CIF-NNN（経由する通信路）。
 - 各 ID ごとに、本ユースケース内での使い方・契機・連携データの概要・失敗時の取り扱い方針を補足する（詳細仕様：画面項目・電文項目・認証方式・エンドポイント等は設計工程で確定するため記載不要）。
 - ここで新たに発見したインタフェースは、`functional.md` 側にも対応 ID を採番・追記し、双方向に参照を張る。
- 関連ビジネスルール（BRU-NNN への参照）
- 関連非機能要件（NFR-NNN への参照、特に該当する場合）
- 設計工程への申し送り事項
 - 要件定義段階では確定できないが、モデリング・設計以降で必ず明確化すべき論点を箇条書きで列挙する。例: 「同時編集時のロック方式（楽観 / 悲観）は設計で決定」「外部 API のリトライ回数・タイムアウト値は性能試験結果を踏まえて確定」「権限判定の実装位置（フロント / API ゲートウェイ / サービス層）は方式設計で決定」。
 - 各申し送り事項には、決定すべき内容・想定される選択肢（分かれば）・決定の責任者または相談先を併記する。
- 補足・備考

`functional.md` のユースケース一覧と相互にリンクできるように、見出しと ID を一貫させてください。


## non-functional.md の構成
非機能要件は以下の 3 つのレンズで網羅する。いずれのレンズも ISO/IEC 25010（JIS X 25010）および実務観点に基づく。重複する論点はいずれか一つに集約し、他のレンズからは ID で相互参照する（重複記載しない）。

- **(A) 製品品質モデル**: システム自身が備える品質属性（8 特性 31 副特性）。プロダクトを作り手側から見た品質。
- **(B) 利用時の品質モデル**: 利用者が特定の利用状況で目標を達成するときに体感する品質（5 特性 11 副特性）。HCD（人間中心設計、ISO 9241-210）と親和性の高いレンズ。
- **(C) 運用・制約観点**: ISO 25010 では体系化されていない、実務で問われる運用・移行・環境制約（IPA 非機能要求グレード相当）。

### (A) ISO/IEC 25010 製品品質モデル（8 特性・31 副特性）
ISO/IEC 25010 の製品品質モデルは 8 つの品質特性と 31 の品質副特性から成る。要件定義では、各特性の定義と「検討観点（典型的に問うべき質問）」を手掛かりに、該当するものだけを具体化する（該当しない副特性はスキップしてよい。ただし「なぜ該当しないか」を一行メモしておくと後工程で有用）。

以下、各特性の定義は JIS X 25010 / IPA『つながる世界のソフトウェア品質ガイド』(2015) の記述に基づく。

#### A-1. 機能適合性 (Functional Suitability)
**定義**: 明示された状況下で使用するとき、明示的ニーズ及び暗黙のニーズを満足させる機能を、製品又はシステムが提供する度合い。機能がステークホルダのニーズにどの程度うまく適合しているか。
- **機能完全性 (functional completeness)**: 機能の集合が、明示された作業及び利用者の目的の全てを網羅する度合い。／観点: 必要な機能が漏れていないか
- **機能正確性 (functional correctness)**: 必要な精度で正しい結果を提供する度合い。／観点: 計算・精度・丸め処理・データ交換の正確性は十分か
- **機能適切性 (functional appropriateness)**: 明示された作業及び目的の達成を、機能が促進する度合い。／観点: 業務の流れに機能が適切に寄与しているか（単に実装されているだけでなく）

#### A-2. 性能効率性 (Performance Efficiency)
**定義**: 明記された状態（条件）で使用する資源の量に関係する性能の度合い。システムの実行性能が効率的か、効率的に資源を使っているか。
- **時間効率性 (time behaviour)**: 応答時間・処理時間・スループット速度が要求事項を満足する度合い。／観点: 画面応答 N 秒以内、バッチ処理 N 時間以内、ピーク時 N rps 等
- **資源効率性 (resource utilization)**: 使用する資源の量及び種類が要求事項を満足する度合い。／観点: CPU・メモリ・ストレージ・帯域の上限
- **容量満足性 (capacity)**: パラメータの最大限度（最大ユーザ数、最大データ件数、最大トランザクション数など）が要求事項を満足させる度合い。／観点: 同時接続数、蓄積データ量、ピーク時件数

#### A-3. 互換性 (Compatibility)
**定義**: 同じハードウェア環境又はソフトウェア環境を共有する間、製品・システム・構成要素が他と情報を交換できる、及び／又は要求された機能を実行できる度合い。他のシステムと適切につながるか、共存できるか。
- **共存性 (co-existence)**: 他の製品に有害な影響を与えずに、共通の環境・資源を共有しながら効率的に動作できる度合い。／観点: 同一サーバ上の他サービスとの資源競合、他ソフトとの干渉
- **相互運用性 (interoperability)**: 二つ以上のシステム・構成要素が情報を交換し、既に交換された情報を使用することができる度合い。／観点: 外部システム連携（SIF）、標準フォーマット・プロトコル準拠

#### A-4. 使用性 (Usability)
**定義**: 明示された利用状況において、有効性・効率性・満足性をもって明示された目標を達成するために、明示された利用者が製品又はシステムを利用できる度合い。
- **適切度認識性 (appropriateness recognizability)**: 製品が利用者のニーズに適切かを、利用者が認識できる度合い。／観点: 製品紹介・UI・マニュアルから「自分の目的に合うか」が判断できるか
- **習得性 (learnability)**: 利用者が製品を使えるようになるまでの学習容易さ。／観点: 初学者が基本操作を N 時間で習得できるか
- **運用操作性 (operability)**: 運用・操作しやすく、制御しやすい度合い。／観点: 画面操作・ショートカット・バッチ投入などの操作効率
- **ユーザエラー防止性 (user error protection)**: 利用者が間違いを起こさないよう、システムが保護する度合い。／観点: 入力バリデーション、確認ダイアログ、取り消し（Undo）可能性
- **ユーザインタフェース快美性 (user interface aesthetics)**: 利用者にとって楽しく満足のいく対話を提供する度合い。／観点: UI の一貫性、視覚デザイン、ブランドトーン
- **アクセシビリティ (accessibility)**: 幅広い範囲の心身特性・能力の人々が使用できる度合い。／観点: WCAG 準拠レベル、スクリーンリーダ対応、色覚多様性対応

#### A-5. 信頼性 (Reliability)
**定義**: 明示された時間帯で、明示された条件下に、システム・製品・構成要素が明示された機能を実行する度合い。
- **成熟性 (maturity)**: 通常運用下で信頼性ニーズを満たす度合い（欠陥の少なさ）。／観点: 既知障害件数、MTBF、欠陥密度
- **可用性 (availability)**: 使用を要求されたとき、運用操作可能・アクセス可能な度合い。／観点: 稼働率目標（例: 99.9%）、計画停止時間
- **障害許容性 (fault tolerance)**: ハードウェア又はソフトウェア故障にもかかわらず、意図したとおりに運用操作できる度合い。／観点: 冗長化、縮退運転、グレースフルデグラデーション
- **回復性 (recoverability)**: 中断時・故障時に、直接影響を受けたデータを回復し、システムを希望する状態に復元できる度合い。／観点: RTO（目標復旧時間）、RPO（目標復旧時点）、バックアップ・リストア手順

#### A-6. セキュリティ (Security)
**定義**: 人間又は他の製品・システムが、認められた権限の種類及び水準に応じたデータアクセスの度合いをもてるように、情報及びデータを保護する度合い。
- **機密性 (confidentiality)**: アクセスすることを認められたデータだけにアクセスが可能であるように、データへのアクセスを確実に防ぐ度合い。／観点: アクセス制御、暗号化（保管時 / 伝送時）
- **インテグリティ (integrity)**: コンピュータプログラム又はデータへの認可されていないアクセス又は修正を防ぐ度合い。／観点: 改ざん検知、入力検証、トランザクション整合性（※データ品質の「完全性」と混同を避けるため、JIS 訳では「インテグリティ」と表記）
- **否認防止性 (non-repudiation)**: 事象・行為が後になって否認されることがないように、行為・事象が引き起こされたことを証明できる度合い。／観点: 電子署名、監査ログ、タイムスタンプ
- **責任追跡性 (accountability)**: 実体（ユーザ・システム）の行為が、その実体に一意に追跡可能である度合い。／観点: 操作ログ・監査証跡、ユーザ ID の一意性
- **真正性 (authenticity)**: ある主体又は資源の同一性が、主張したとおりであることを証明できる度合い。／観点: 認証方式（パスワード / MFA / SSO / 証明書）
- 補足: ISO 25010 のセキュリティ副特性に「認証（Authentication）」「認可（Authorization）」は独立項目としては存在しない。認証は「真正性」、認可は「機密性」の実現手段として位置付けられる。

#### A-7. 保守性 (Maintainability)
**定義**: 意図した保守者によって、製品又はシステムが修正することができる有効性及び効率性の度合い。システム保守・修正が容易か。
- **モジュール性 (modularity)**: 一つの構成要素への変更が他に与える影響が最小になるように、別々の構成要素から構成されている度合い。／観点: 疎結合、関心事の分離
- **再利用性 (reusability)**: 一つ以上のシステムに、又は他の資産作りに、資産を使用することができる度合い。／観点: 共通ライブラリ化、API 設計
- **解析性 (analysability)**: 変更が与える影響の総合評価、欠陥・故障の原因診断、修正箇所の識別を効率的に実施できる度合い。／観点: ログ品質、トレーシング、ドキュメント整備
- **修正性 (modifiability)**: 欠陥混入や既存品質低下を起こさずに、効率的に修正できる度合い。／観点: リグレッション防止策、テスト整備
- **試験性 (testability)**: 試験基準を確立でき、それが満たされているかを試験で確認できる有効性・効率性の度合い。／観点: 自動テスト容易性、テスト用 I/F の提供

#### A-8. 移植性 (Portability)
**定義**: 一つのハードウェア・ソフトウェア・他の運用環境・利用環境から、その他の環境に、システム・製品・構成要素を移すことができる有効性及び効率性の度合い。
- **適応性 (adaptability)**: 異なる、又は進化していく環境（OS バージョン、クラウドリージョン、言語・ロケール等）へ適応できる度合い。／観点: 環境依存の分離、設定外出し
- **設置性 (installability)**: 明示された環境において、うまく設置及び／又は削除できる度合い。／観点: インストール手順、アンインストール手順、前提環境の明示
- **置換性 (replaceability)**: 同じ環境において、同じ目的の別の明示された製品と置き換えることができる度合い。／観点: データエクスポート、API 互換、標準準拠

#### 記述時の指針
- 各要件には「どの品質特性 / 副特性に該当するか」をタグとして明示する（例: 「該当: A-5 / 可用性」）。複数にまたがる場合は主特性を記載する。
- 副特性の JIS 正式名称をそのまま使うか、プロジェクト固有の短縮名を使うかは統一する。短縮名を使う場合は用語集に JIS 名称との対応を記載する。
- 記述が抽象的なら「観点」列の例示を呼び水に、具体的・定量的な要求に落とし込む（例: 「可用性を確保する」→「稼働率 99.9%、計画停止月 1 回 2 時間以内」）。

### (B) ISO/IEC 25010 利用時の品質モデル（5 特性・11 副特性）
(A) がプロダクトそのものの品質を扱うのに対し、(B) は「**特定の利用者が、特定の利用状況で、特定の目標を達成したときに体感する品質**」を扱う。同じプロダクトでも利用者や利用状況が変われば、利用時の品質は変動する。HCD（人間中心設計）の観点はこのレンズで扱う。

利用時の品質を要件として明示することで、「システムは稼働したが現場で使われない」「操作は可能だが業務効率が上がらない」といった製品品質だけでは捕捉できない失敗を防ぐ。要件定義では、主要な利用者セグメント（ペルソナ）と主要な利用状況（利用シナリオ）ごとに、該当する特性を具体化する。

#### B-1. 有効性 (Effectiveness) [4.1.1]
**定義**: 明示された目標を利用者が達成する上での正確さ及び完全さの度合い。該当システムを利用すると、どの程度うまく、実施したい事柄のニーズの内容を達成できるか。
- 観点: タスク完了率、タスク成果物の正確性、目標達成までの到達度
- 記述例: 「想定ペルソナ（現場作業員）が、実地環境下で検査報告書の作成タスクを 95% 以上完了できる」

#### B-2. 効率性 (Efficiency) [4.1.2]
**定義**: 利用者が特定の目標を達成するための正確さ及び完全さに関連して、使用した資源の度合い。業務資源（作業時間、作業要員、エネルギー、材料等）の使い方がどの程度効率的か。
- 観点: タスク所要時間、操作ステップ数、必要な習熟期間、紙やエネルギーの削減量
- 記述例: 「受注入力業務を、従来の紙運用比で 50% の時間短縮」「1 件あたりの平均操作ステップを 7 以下」
- 注意: A-2「性能効率性」は*システムの資源使用量*、B-2「効率性」は*利用者の業務資源*を指す（対象が異なる）。

#### B-3. 満足性 (Satisfaction) [4.1.3]
**定義**: 製品又はシステムが明示された利用状況において使用されるとき、利用者ニーズが満足される度合い。
- **実用性 (usefulness)** [4.1.3.1]: 利用の結果及び利用の影響を含め、利用者が把握した目標の達成状況によって得られる利用者の満足。／観点: 「このシステムは自分の仕事に役立つ」という体感評価（SUS / NPS / UMUX 等）
- **信用性 (trust)** [4.1.3.2]: 利用者又は他の利害関係者がもつ、製品又はシステムが意図した通りに動作するという確信。／観点: データ正確性への信頼、障害時の挙動の透明性、AI 出力の信頼度表示
- **快感性 (pleasure)** [4.1.3.3]: 個人的なニーズを満たすことから利用者が感じる喜び。／観点: 達成感・ゲーミフィケーション・創造性の発揮
- **快適性 (comfort)** [4.1.3.4]: システム利用時の身体的・心理的快適さ。／観点: 身体負荷、視覚・聴覚疲労、長時間利用への耐性

#### B-4. リスク回避性 (Freedom from risk) [4.1.4]
**定義**: 製品又はシステムが、経済状況、人間の生活又は環境に対する潜在的なリスクを緩和する度合い。利用によって出会うかもしれないリスクが低く抑えられているか。
- **経済リスク緩和性 (economic risk mitigation)** [4.1.4.1]: 財政状況・効率的運用操作・商業資産・評判等に対する潜在的リスクを緩和する度合い。／観点: 誤操作による経済損失の上限、ブランド毀損リスクの抑制
- **健康・安全リスク緩和性 (health and safety risk mitigation)** [4.1.4.2]: 人々に対する潜在的リスクを緩和する度合い。／観点: 医療・交通・産業機器での安全インターロック、過労防止、誤操作による人身事故防止
- **環境リスク緩和性 (environmental risk mitigation)** [4.1.4.3]: 環境に対する潜在的リスクを軽減する度合い。／観点: エネルギー消費、廃棄物、CO2 排出、電子廃棄物

#### B-5. 利用状況網羅性 (Context coverage) [4.1.5]
**定義**: 明示された利用状況及び当初明確に識別されていた状況を超越した状況の両方において、有効性・効率性・リスク回避性・満足性を伴って製品又はシステムが使用できる度合い。
- **利用状況完全性 (context completeness)** [4.1.5.1]: 明示された全ての利用状況において、利用時の品質を伴って使用できる度合い。／観点: 想定した全ペルソナ × 全利用シナリオで目標達成できるか
- **柔軟性 (flexibility)** [4.1.5.2]: 初めに明示された状況を*逸脱した*状況（未想定の利用者・環境・利用方法）においても使用できる度合い。／観点: 当初想定外の障害者利用、想定外の端末・ネットワーク環境、業務の想定外変化への対応

#### HCD（人間中心設計）との接続
ISO 9241-210 の HCD プロセスは、「利用状況の理解と明示」→「ユーザ要求事項の明示」→「設計解の作成」→「設計解の評価」を反復する。要件定義段階では次を明示することで、HCD 実践の土台を作る:
- **ペルソナ**: `functional.md` のステークホルダー定義で、利用者セグメントを「役割」だけでなく「能力・熟練度・身体特性・利用目的・利用頻度」まで含めて記述する。
- **利用状況（コンテキスト）**: 各 `usecase.md` の事前条件に、想定する物理環境（屋外 / 騒音下 / 片手操作）、時間制約、同時並行タスクなどを記載する。
- **利用時の品質目標**: 本セクション (B) に、ペルソナ × 利用状況ごとの有効性・効率性・満足性の数値目標を記載する。
- **評価計画の申し送り**: ユーザビリティテスト / フィールド調査 / 受入テスト（UAT）での評価実施は、各 `usecase.md` の「設計工程への申し送り事項」で明示する（要件定義書内では計画までは立てない）。

#### 記述時の指針（(B) 固有）
- (B) の要件は必ず「**誰が（ペルソナ）** × **どの利用状況で** × **何を達成するとき** に、**どの水準**」の形で記述する。主語なしの「使いやすい」は採用しない。
- (A) 使用性（A-4）との違い: A-4 はプロダクト属性（UI の作り）、B はプロダクトを使った結果（利用者の目標達成度）。UI が整っていても業務目標を達成できなければ B は未達。両方をバランスよく記述する。

### (C) 運用・制約観点（一般的な非機能要件）
以下を網羅する。数値目標は (A) (B) の該当特性と重複する場合、どちらで扱うかを決めて片方にまとめる。
- 可用性・SLA: 運用スケジュール（24h×365 / 平日日中等）/ 計画停止の頻度と所要時間 / 稼働率目標（例: 99.9%）/ RTO（目標復旧時間）/ RPO（目標復旧時点）
- 運用要件:
 - ジョブ・バッチ: 実行スケジュール / 多重起動制御 / 異常終了時の再実行方針
 - バックアップ: 対象データ / 取得頻度 / 世代数 / 保管場所 / リストア手順の検証頻度
 - 監視: 監視対象（リソース / アプリ / 業務 / 外形）/ 閾値 / 通知先 / エスカレーションフロー
 - ログ: 種類（アクセス / 操作 / 監査 / エラー / システム）/ 保管期間 / 保管先 / 検索性要件
- 保守・サポート体制: 保守時間帯 / 問い合わせ窓口（一次・二次）/ 対応 SLA（初動 / 恒久対応）/ 保守契約のスコープ（障害対応 / 法令改正対応 / 機能改善）
- 移行要件: 移行対象（データ / システム / 業務）/ 移行方式（一括 / 段階 / 並行稼働）/ 移行時期・所要期間 / 移行時の業務停止要否 / リハーサル実施方針 / 切戻し（ロールバック）条件と手順
- システム環境・構成制約: 稼働環境（オンプレ / パブリッククラウド / ハイブリッド）/ OS・ミドルウェア・DB の指定バージョン / ネットワーク構成・帯域要件 / 冗長化構成（HA / DR サイト）/ データセンタ・リージョン要件
- 規格・法規制への適合: 業界標準（PCI DSS / HIPAA 等）/ 関連法令（個人情報保護法 / GDPR / 電子帳簿保存法 等）/ 社内規程 / 監査要件
- 教育・トレーニング: 対象者（エンドユーザ / 運用担当 / 保守担当）/ 実施形態（集合研修 / e-learning / ハンズオン）/ 提供ドキュメント種別（操作マニュアル / 運用手順書 / 障害対応手順書）
- 前提条件・制約事項: 発注者・利用部門が準備する前提リソース / スコープ外とする事項 / 既存システムとの役割分担

## 作成時のチェック観点

各要件は、以下のすべてを満たすように記述すること。記述後、各項目を順にチェックし、不足があれば修正してから出力する。

### 1. 明確性
- 要件文は一文一意で記述する。複数の意図を一文に含めない。
- 「等」「など」「適切に」「必要に応じて」といった曖昧表現を使わない。使う場合は対象を列挙する。
- 主語（誰が）と動詞（何をする）を省略しない。

### 2. 根拠の明示
- 各要件には「根拠」を併記する。根拠は次のいずれかで特定する: 依頼者・関係者名、法令・規制名、参照ドキュメント名（章節番号まで）、業界標準。
- 根拠が不明な要件は「根拠未確定」と明記し、確認すべき相手を併記する。

### 3. 定量化
- 性能・容量・時間・件数などの制約は、数値と単位で記述する（例: 「3 秒以内」「同時 1000 接続」）。
- 数値が決まらない場合は「TBD（決定者: ◯◯）」と明記する。「高速に」「大量に」のような定性表現で済ませない。

### 4. 関連付け
- 要件 ID（FR-NNN / NFR-NNN / UC-NNN / BRU-NNN / ENT-NNN / UI-NNN / SIF-NNN / HIF-NNN / CIF-NNN）を付与し、相互参照は ID で明示する。
- 関連要件がある場合、各要件文の末尾に「関連: UC-001, NFR-005, SIF-002」のように列挙する。

### 5. ドメイン整合性
- 入力で与えられた業務領域・前提・既存システムの制約に反していないか確認する。逸脱がある場合は「制約逸脱の可能性」として注記する。

### 6. 検証可能性
- 各要件に「検証方法」を併記する（例: 「ユニットテストで検証」「負荷試験で 1000rps を確認」「受け入れ基準: ◯◯画面で△△が表示される」）。
- 検証手段が定義できない要件は受け入れ不可とみなし、定量化または分割し直す。

### 7. トレーサビリティ
- 各要件は、上位の目的（ビジネス目的・ユースケース・ステークホルダーの要求）のいずれかに紐付ける。紐付け先 ID を要件に併記する。
- どの上位要素にも紐付かない要件は出力しない（不要な要件として除外する）。

### 8. 構造と参照性
- 見出し・表・ID 体系を整え、目次から目的の要件に到達できるようにする。
- 設計フェーズに渡せるよう、要件文は技術的な構成要素（API・画面・データ項目など）にマッピングしやすい粒度に分割する。

### 9. 識別子付与
- すべての要件・ユースケース・ビジネスルール・エンティティ・インタフェースに一意の ID を付与する（FR-NNN / NFR-NNN / UC-NNN / BRU-NNN / ENT-NNN / UI-NNN / SIF-NNN / HIF-NNN / CIF-NNN）。
- ID は採番後に変更しない。

### 10. 暗黙要件の顕在化
- 性能・運用・障害時の振る舞い・セキュリティなど、入力に明示されていなくても通常想定される要件は、`non-functional.md` に追加し「暗黙要件として追加」と注記する。
- 入力に書かれていないからといって省略しない。
