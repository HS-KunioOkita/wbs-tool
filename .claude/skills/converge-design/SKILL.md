# 設計ドキュメントの収束（基本設計書の生成）

要件定義・アーキテクチャ・コンポーネント・データ・インタフェース・画面・HCD/UIUX・インフラなど、複数工程で発散した設計ドキュメントを統合し、**意思決定に必要な情報だけを残した、簡潔で一貫性のある基本設計書**を作成してください。

---

## 🎯 Goal
発散した複数の設計ドキュメントから意思決定の核心だけを抽出し、レビュー可能な 1 本の基本設計書に収束させる。

「意思決定に必要な情報だけを残す」とは、**その情報がなくても意思決定できるなら削る**、という基準を一貫して適用することを指す。判断に迷ったら常にこの問いに戻る：

> 「この情報がなくても意思決定できるか？」
> → YES → 削除
> → NO → 残す

これは単なる要約ではない。次の 3 つを必ず同時に行う：

- **削る**（情報を減らす）
- **決める**（暫定 / 未決事項を明示する）
- **再構成する**（意思決定の流れに沿って並べ替える）

---

## 🧭 Role
あなたは「**設計の編集長兼レビューファシリテーター**」である。

- 著者ではなく **編集者** として、既存の決定を整理・選別・配列する。
- 新しい設計判断を勝手に下さない。原文に書かれていない決定を本書で初めて生まないこと。
- 原文の意図を尊重しつつ、読み手の意思決定を最短距離で支える。
- 矛盾を見つけたら「未決事項」として明示する（その場で勝手に解消しない）。

---

## 位置付け（他工程との関係）
本スキルは設計工程の **最終整理工程** に位置し、上流成果物を集約してレビュー用に再編する。設計判断は上流に委ねる。

- 上流（必須参照）
  - 要件定義: `docs/requirements/functional.md` / `usecase/UC-NNN/usecase.md` / `non-functional.md`
  - 基本設計: `docs/design/architecture/architecture.md`
  - 基本設計: `docs/design/component/component-design.md`
  - 基本設計: `docs/design/data/data-design.md`
  - 基本設計: `docs/design/interface/interface-design.md`
  - 基本設計: `docs/design/hcd-uiux/hcd-uiux-design.md`
  - 基本設計: `docs/design/screen/screen-design.md`
  - 基本設計: `docs/design/infrastructure/infrastructure-design.md`
  - その他、`docs/design/` 配下に存在する基本設計レベルの成果物
- 下流
  - 詳細設計（クラス設計・画面詳細・実装手順など）: 本書の対象外。**リンク参照のみ**で扱う。

---

## 入力
- 既定では `docs/requirements/` と `docs/design/` 配下に存在する全設計ドキュメントを入力とする。
- $ARGUMENTS でファイル / ディレクトリが指定された場合は、その範囲に限定する。
- 入力に含まれない領域（章）は出力で **「未着手」として明示** する（勝手に内容を埋めない）。

---

## 出力ファイル
- `docs/design/basic-design.md` 1 ファイルに集約する。
- 既にファイルがある場合は差分更新（章単位で追記・修正）し、既存の章構成と参照リンクは可能な限り維持する。

1 ファイルに集約する理由: 「全体の辻褄」を読み手が 1 本の流れで検証できることが、収束工程の最重要価値であるため。

---

## 🪜 Workflow

以下の 8 ステップを **この順序で** 実行する。順序を入れ替えると、削減判断・整合性チェックの根拠が失われるため固定する。

### 1. 全体把握（Inventory）
入力された全ドキュメントを読み取り、各記述要素を以下に分類する。分類結果は内部メモとして保持し、本文には書かない。

- **決定事項**（確定している設計判断）
- **仮定**（暫定的に置かれている前提）
- **未決事項**（明示・暗黙含めて未確定なもの）
- **説明・補足**（決定事項の理由付け・背景）
- **詳細すぎる内容**（基本設計レベルを超えた実装ディテール）

### 2. 重要度評価（Prioritization）
各要素について以下を評価する：

- 意思決定に影響するか？
- 非IT読者に必要か？
- 将来変更されにくいか？
- 基本設計レベルか（詳細設計に属さないか）？

4 項目すべて NO に近いものは削減候補とする。

### 3. 削減（Reduction）

#### 削除対象
- 実装レベルの詳細（クラス名・メソッドシグネチャ・変数名・SQL 個別文）
- 重複した説明（複数ドキュメント間で同義の記述）
- 読者に価値がない補足（自明・冗長・蛇足）
- 変更頻度が高い細部（インスタンスタイプ・台数・URL など、実環境で変動する値）

#### 簡略化対象
- 長い説明 → 箇条書き化
- 複雑な構造 → Mermaid 図化
- 分散情報 → 1 箇所に集約

### 4. 統合（Integration）

- 同じ意味を持つ複数記述を 1 箇所に統合する
- UI ↔ API ↔ データ の対応関係を **同一の ID 体系**（`UI-NNN` / `API-NNN` / `ENT-NNN` 等）で接続する
- コンポーネント（`COMP-NNN` / `MOD-NNN`）と インフラ配置 の対応関係を表で明示する
- 技術スタックと設計判断の整合（言語・FW・DB・通信方式の選定理由）を確認する

### 5. 再構成（Re-structuring）

以下の固定章構成で再構成する。順序は「全体像 → 前提 → 構成 → 中身 → 体験 → 運用 → 未決」に揃えるため、固定する。

1. 概要（非IT向け）
2. スコープ
3. 前提・制約
4. 技術スタック / 方針
5. システム構成
6. インフラ設計
7. コンポーネント設計
8. データ設計
9. インタフェース設計
10. 画面設計
11. HCD / UIUX
12. 非機能 / 運用
13. 未決事項

### 6. 圧縮（Compression）

各章は **以下の 4 ブロックのみ** で構成する。これ以上書かない：

1. **概要**（3〜5 行）— その章で何が決まっているかの要旨
2. **重要ポイント**（箇条書き、5〜10 個程度）— 意思決定に直結する事項
3. **図**（必要なら Mermaid 1〜2 枚）— 構造・関係性が文章より図で速く伝わる場合のみ
4. **詳細設計への参照**（リンク）— 詳しくは元ドキュメントへ誘導

詳細を貼り付けるのではなく、**詳細への入り口** を提供する。

### 7. 整合性チェック（Consistency）

最終出力前に必ず以下を確認する。1 つでも不整合があれば「未決事項」に退避させる：

- UI ↔ API ↔ データ の項目・型・有無が一致しているか
- コンポーネント間で責務が重複していないか
- インフラ構成が非機能要件（`NFR-NNN`）を満たしているか
- 技術スタックと設計判断が矛盾していないか
- 上流ドキュメントへのリンクが切れていないか

### 8. 未決事項の整理（Decision Queue）

未決事項は本文末尾の表に集約する：

| 項目 | 内容 | 影響範囲 | 優先度 |
|---|---|---|---|

- **影響範囲** は影響を受ける章 / ID（例: `第9章 / API-003, ENT-002`）で記載する
- **優先度** は High / Mid / Low の 3 段階。次回レビューで決めるべき順序を表す

## 🚫 Anti-pattern（禁止事項）

以下に該当したら必ず差し戻す：

- 単純な要約に終わっている（削減・再構成がされていない）
- 全情報を残そうとしている（圧縮の意図が読み取れない）
- 詳細をそのまま貼り付けている（リンクで参照すべき内容を本文に展開している）
- 構造を変えずに短くしただけ（章構成が原文のまま）
- 矛盾をその場で勝手に解消している（未決事項として明示すべき）
- 上流に存在しない決定を本書で新規に生んでいる（編集者の越権）

---

## ✅ Good Output の条件

以下を **すべて** 満たすこと：

- 10 分で全体を理解できる
- 非IT読者でも読める
- 設計判断が明確（決定 / 暫定 / 未決の区別がつく）
- レビュー可能（章単位でコメントできる粒度）
- 重複がない（同義記述が複数箇所に散らばっていない）
- 上流ドキュメントへのリンクが機能している

---

## 💡 判断ルール（最重要）

迷ったらこの問いに戻る：

> **「この情報がなくても意思決定できるか？」**
>
> → YES → 削除
> → NO → 残す

この問いだけで、削減判断の 80% は解決する。

---

## 🔧 編集ポリシー

優先順位は次のとおり。複数原則が衝突したら左を優先する：

1. **読みやすさ > 網羅性**
2. **構造 > 詳細**
3. **意思決定 > 説明**
4. **一貫性 > 個別最適**

---

## 📎 補足

- 詳細設計は別ドキュメントとして扱い、本書からはリンク参照のみ行う。
- Mermaid 図は積極的に活用するが、1 章につき最大 2 枚までを目安とする（多すぎると読みづらくなる）。
- 入力ドキュメントが部分的にしか存在しない場合、欠損章は **「未着手」と明示** し、勝手に内容を補わない。
